Day 1 — 环境搭建 + 第一个 C# 程序（C# ≈ 带类型的 TS）

📌 技术来源：🟦 C# 语法（using/class/var/字符串插值）+ 🟩 BCL（Console）

一句话讲清楚

C# 就是"编译期强类型 + 真正面向对象"的 TypeScript，跑在 .NET 上（≈ TS 跑在 Node 上）。

前端类比秒懂

C# / .NET 前端 说明
.NET Runtime Node.js Runtime 代码的运行环境
BCL（基础类库） Node 内置模块（fs/http…） 官方自带，不用装
NuGet 包 npm 包 第三方库
Visual Studio 2022 VS Code IDE（VS 更重、更强）
dotnet run npm start 编译并运行
.csproj package.json 工程/依赖配置

分点精讲

① 程序入口：🟦 传统写法要 static void Main()，但 .NET 6+ 支持"顶级语句"，可以像 JS 一样直接写：

// Program.cs —— 顶级语句，不用写 class/Main
Console.WriteLine("DAQ Monitor 启动");

② 变量声明：🟦 var 是类型推断（≠ JS 的 var，更像 TS 的 let）：

var name = "DAQ";      // 推断为 string，之后不能赋别的类型
string title = "监控"; // 显式类型，等价于 TS: let title: string
int port = 502;        // 值类型，默认 0，不能是 undefined

⚠️ C# 没有 undefined，只有 null；而且默认变量不能为 null（要可空得写 int?）——这是比 JS 安全的地方。

③ 字符串插值：🟦 用 $"..."，等价于 JS 反引号模板：

var v = 25.6;
Console.WriteLine($"温度 = {v} ℃");   // JS: `温度 = ${v} ℃`
Console.WriteLine($"{name} v1.0");

⚠️ 重点 & 易踩坑

项 说明
⭐ 一切皆类型 变量必须有明确类型（var 只是让编译器帮你推断，不是"任意类型"）
⭐ 无 undefined 只有 null，且非可空类型默认不能为 null
🔥 var ≠ JS var C# var 是块级 + 类型固定，别用 JS 直觉理解
🔥 大小写敏感 Console 不是 console，类名/方法名首字母大写（PascalCase）

Day 2 — 类型系统：值类型 / 引用类型 / 可空 / struct / enum

📌 技术来源：🟦 C# 类型系统（全部内置语法，不装包）

一句话讲清楚

值类型 = "复印件"（赋值就拷一份，互不影响）；引用类型 = "共享文档链接"（赋值只是多一个人拿到同一份地址）。

前端类比秒懂

C# 前端 赋值行为
值类型 int/double/bool/struct/enum primitive number/boolean 拷贝值本身
引用类型 string/class/数组/List<T> object/array 共享地址
可空 int? number \| null 允许为 null
struct 无直接对应（≈ 轻量 object 但按值拷贝） 值类型
enum enum（TS 有） 命名常量

分点精讲

① 值 vs 引用，看这段就懂：

int a = 5;
int b = a;      // 拷贝
b = 99;
// a 仍是 5（互不影响）

int[] arr1 = { 1, 2, 3 };
int[] arr2 = arr1;   // 共享地址
arr2[0] = 99;
// arr1[0] 也变成 99！（同一份数据）

② 可空类型：🟦 加 ? 表示可为 null：

int age = null;    // ❌ 编译报错，非可空不能为 null
int? age2 = null;  // ✅ 可空
int real = age2 ?? 0;   // ?? 是空合并（JS 也有）：null 就取 0
Console.WriteLine(age2?.ToString());  // ?. 空条件调用（JS 也有）

③ struct —— 上位机点位的天然载体：🟦 轻量值类型，适合"坐标/点位/寄存器"这类小数据：

public struct SensorPoint
{
    public int Id;          // 点位编号
    public double Value;    // 数值
    public DateTime Time;   // 采集时刻
}

④ enum —— 状态/功能码用它：🟦 命名常量，比 magic number 可读：

public enum DeviceState { Offline, Connecting, Online }
public enum AlarmLevel  { Normal, Warning, Critical }

var s = DeviceState.Online;
if (s == DeviceState.Online) Console.WriteLine("设备在线");

⚠️ 重点 & 易踩坑

项 说明
⭐ 值 vs 引用 面试必考。判断标准：struct/基础数值/enum 是值，class/string/数组/集合 是引用

public class RingBuffer<T>       // 环形缓冲，后面存历史数据用

一句话讲清楚

前端类比秒懂

C# 前端 说明

① Action / Func —— 内置委托，99% 不用自己写 delegate：🟩

② 事件 —— 设备层→UI 层单向通知：🟦🟩

// 事件参数（携带数据）
public class DataEventArgs : EventArgs
{
    public int PointId { get; init; }
    public double Value { get; init; }
}

public abstract class DeviceBase
{
    // 声明事件（EventHandler<T> 是 BCL 标准委托）
    public event EventHandler<DataEventArgs>? DataReceived;

    // 受保护的触发方法，供子类采到数据时调用
    protected void RaiseData(int pointId, double value)
        => DataReceived?.Invoke(this, new DataEventArgs { PointId = pointId, Value = value });
}

// 订阅方（比如 UI）
device.DataReceived += OnData;          // 订阅 ≈ addEventListener
void OnData(object? s, DataEventArgs e) => Console.WriteLine($"点{e.PointId}={e.Value}");
// 销毁时：device.DataReceived -= OnData;   // 退订，防内存泄漏

⚠️ 重点 & 易踩坑

项 说明
⭐ 事件为什么解耦 设备不认识 UI，只管"喊一声"(Invoke)，谁订阅谁收到，UI 可随时增减
🔥 忘了 -= 退订 对象销毁前不 -=，会导致内存泄漏（企业级必查项，面试常问）
🔥 ?.Invoke 判空 没人订阅时事件为 null，直接 Invoke 会崩，要写 DataReceived?.Invoke(...)
🔥 跨线程触发事件改 UI 后台线程触发的事件里不能直接改 UI，要 Dispatcher.Invoke（见 Day 7）

Day 7 — 多线程 / async-await / 锁（重头戏 ⭐⭐⭐）

📌 技术来源：🟦 async/await/lock/Task/Thread 语法 + 🟩 BCL（Task/Thread/ConcurrentQueue/SemaphoreSlim）

一句话讲清楚

多线程 = 多个工人同时干活，锁 = 抢厕所时排队（同一时刻只放一个人进去改数据）。前端 JS 是单线程没这问题，C# 是真多线程——两个线程同时改一个变量，数据就乱了，这就是锁存在的意义。

前端类比秒懂

C# 概念 前端类比 说明
Thread Web Worker 最底层的新线程，干独立任务
Task Promise 更高级的异步，推荐用这个
async/await async/await 几乎一样，但 C# 有坑（见下）
lock 前端没有！ 保护共享数据不被同时改
ConcurrentQueue 前端没有！ 自带锁的线程安全队列
SemaphoreSlim 前端没有！ 更高级的限流锁

⚠️ 核心区别：前端单线程，异步只是"排队等结果"，不会真并行改数据；C# 是真并行，多个线程能同时执行、同时读写内存，所以需要锁。

分点精讲

① Thread —— 最基础的多线程：🟩

// 前端类比：new Worker('worker.js')

{
    Console.WriteLine($"后台线程 Id={Thread.CurrentThread.ManagedThreadId}");
});
t.IsBackground = true;   // 后台线程：主程序退出它也退出（否则程序关不掉）
t.Start();
Console.WriteLine($"主线程 Id={Thread.CurrentThread.ManagedThreadId}");
// ⚠️ 输出顺序不固定！多线程执行顺序不可预测

② Task —— 现代 C# 推荐（≈ Promise）：🟩

});

// int r2 = calc.Result;   // ❌ .Result/.Wait() 会阻塞线程，UI 里用会死锁！

③ async/await —— 最像前端的写法：🟦

④ ⚠️ 为什么需要锁 —— 经典竞态 Bug：🟦

// ❌ 没锁：结果不是 10000！
private int _count = 0;
for (int i = 0; i < 10000; i++)
    Task.Run(() => _count++);   // 上万个线程同时 ++
// 结果可能是 8234、9567... 随机

为什么？ _count++ 不是原子操作，实际分三步：①读值→②+1→③写回。两个线程同时读到 5，各自 +1 都写回 6，就丢了一次 +1。

// ✅ 加锁就对了：一定是 10000
private int _count = 0;
private readonly object _lock = new object();   // 锁对象，随便 new 一个
for (int i = 0; i < 10000; i++)
    Task.Run(() =>
    {
        lock (_lock)   // 同一刻只有一个线程能进
        {
            _count++;
        }              // 出了 lock，别的线程才能进
    });

⑤ 生产者-消费者（上位机最高频场景）：🟩

串口每秒收 100 条（生产者），UI 慢慢刷新（消费者），中间用线程安全队列缓冲。

using System.Collections.Concurrent;

// ConcurrentQueue 自带锁，不用手动 lock（前端类比：自动管理的消息队列）
private ConcurrentQueue<SensorPoint> _queue = new();

// 生产者：后台采集线程
private void OnDataReceived(SensorPoint p) => _queue.Enqueue(p);   // 线程安全

// 消费者：WPF DispatcherTimer 定时刷 UI
private void UiTimer_Tick(object? s, EventArgs e)
{
    while (_queue.TryDequeue(out var p))   // 一条条取
    {
        DataGrid.Items.Add(p);
        if (DataGrid.Items.Count > 200)
            DataGrid.Items.RemoveAt(0);    // 只留最近 200 条，防内存爆
    }
}

⚠️ 前端转 C# 多线程四大坑

坑 说明 解决
跨线程改 UI 后台线程直接改 TextBlock.Text 会抛异常 WPF：Dispatcher.Invoke(() => txt.Text = "x")；WinForms：Invoke(...)
死锁 两线程互等对方的锁 / await 里用 .Result 锁顺序一致；UI 里永远 await，别用 .Result/.Wait()
async void 吞异常 异常静默丢失、程序莫名崩 只在事件处理器用 async void，其他用 async Task
竞态条件 多线程同时读写同一变量 lock 或用 ConcurrentQueue/Interlocked

② CRC16 校验（🟦，Modbus 也会用，先打好基础）

public static class Crc16
{
    public static ushort Modbus(byte[] data)
    {
        ushort crc = 0xFFFF;
        foreach (var b in data)
        {
            crc ^= b;
            for (int i = 0; i < 8; i++)
                crc = (crc & 1) != 0 ? (ushort)((crc >> 1) ^ 0xA001) : (ushort)(crc >> 1);
        }
        return crc;
    }
}

③ 完整帧示例：AA 55 | Len | Payload... | CRC_L CRC_H

🔬 掰开揉碎：CRC16 到底在算什么（新手最卡的一关）

代码只有 8 行，但「为什么是 0xA001」「为什么初始 0xFFFF」「右移/异或在干啥」——不讲清楚你永远只会抄。 - 它算的是「数据指纹」：发送方把整帧(除 CRC 本身)算出一个 16 位校验值附在末尾；接收方用同样算法重算一遍，比对一致才说明传输没出错（类比：你给文件算个 MD5，对方再算一次对不对得上）。 - 初始值 0xFFFF：所有位先置 1 再开始异或，是为了让「全 0 数据」也能产生非零校验（否则 0 数据校验也是 0，分不清是没传还是传错了）。 - 右移 + 异或 0xA001（每一步在干啥）： 把当前字节和 crc 低 8 位异或 → 看 crc 最低位是不是 1： 是 1 → 右移一位 再 异或 0xA001 （0xA001 是多项式 0x8005 的「按位反转」形式，Modbus 用反转写法） 是 0 → 只右移一位 重复 8 次 = 处理完 1 个字节，循环每个字节

直觉理解：每右移一次，就把数据「喂」进校验寄存器一位；碰到 1 就「搅拌」一下多项式，保证任何 1 个 bit 翻转都会导致最终结果不同。 - 线序坑（本项目测试踩过）：算出的寄存器值是 0x0A84，但 Modbus 先传低字节84、再传高字节0A，所以线上字节顺序是 84 0A，人们常写成「0x840A」。寄存器真值是 0x0A84，本项目 Crc16.Modbus 返回的就是这个（测试断言 0x0A84，不是 0x840A）。 - 查表法为什么快：上面是「计算法」每字节循环 8 次；工业用「256 项预计算表」，每字节直接查表异或，快一个数量级。本项目 FrameParser 用计算法够用，真高频场景再换表。

🔬 掰开揉碎：为什么会有「半包 / 粘包」（现场最难查的 bug 源头）

串口是字节流，不保证「你发一次、我收一次」： - 半包：下位机一次发 20 字节，你 DataReceived 可能先收到 5 字节、再 15 字节（系统缓冲没攒够就通知你了）。 - 粘包：下位机连发两帧，你一次收到 40 字节（两帧粘一起）。 - 后果：直接按「收到=一帧」解析 = 偶发乱码/丢数据，现场几周才复现一次，极难查。 - 正解（本项目 FrameParser 的做法）：维护一个 _buffer，来啥都 AddRange 进去，然后循环尝试拆帧（TryTakeFrame 找帧头→读长度→够长才取出），拆不出就留着等下一波；注意：永远拆不出完整帧时（比如收到垃圾头）要清空缓冲，否则缓冲无限增长 = 内存泄漏。

🔬 掰开揉碎：SerialPort 真实项目里的「坑」（光会 Open/Read 不够）

  • DataReceived 在某些机器/某些 USB 转串口上不触发：这是 .NET SerialPort 的已知老毛病（基于 Win32 事件，不稳定）。企业级写法是用 BaseStream.ReadAsync 自己开一个读循环，不依赖 DataReceived： csharp // 现代/稳健写法：不依赖 DataReceived 事件 var buf = new byte[1024]; while (!ct.IsCancellationRequested) { int n = await port.BaseStream.ReadAsync(buf, 0, buf.Length, ct); // 阻塞等数据，异步不卡 UI OnBytes(buf.AsMemory(0, n)); // 喂给帧解析器 }
  • 硬件流控 DTR/RTS：有些下位机要求上位机拉高 DtrEnable/RtsEnable 才肯通信，连不上时检查这个。
  • 跨线程 Close() 崩溃：DataReceived 在后台线程，若在 UI 线程直接 port.Close() 可能和后台读冲突。统一用 CancellationToken 先停止读循环、再 Close()。
  • BytesToRead 一次性读不完：循环读直到 BytesToRead == 0，别只 Read 一次。

⚠️ 重点 & 易踩坑

项 说明
⭐ 一定要处理半包 / 粘包 不处理 = 偶尔丢数据，现场最难查的 bug
⭐ CRC 用查表法更快 上面是计算法，工业可用查表优化
🔥 大小端 下位机可能是小端，读 int 用 BinaryPrimitives.ReadInt32LittleEndian
🔥 缓冲无限增长 永远拆不出完整帧时要清空缓冲，防内存泄漏

✏️ 练习

实现 TryTakeFrame：从 _buffer 找 AA 55 开头、按第 3 字节长度取出完整帧并移除缓冲；校验 CRC。

✅ 答案（骨架）

private bool TryTakeFrame(out byte[] frame)
{
    frame = Array.Empty<byte>();
    int idx = _buffer.IndexOf(0xAA);
    if (idx < 0 || _buffer.Count < idx + 3) return false;
    if (_buffer[idx + 1] != 0x55) { _buffer.RemoveAt(idx); return false; }
    int len = _buffer[idx + 2];
    int total = 3 + len + 2;                 // 头+长+载荷+CRC
    if (_buffer.Count < idx + total) return false;
    frame = _buffer.GetRange(idx, total).ToArray();
    _buffer.RemoveRange(0, idx + total);
    return true;
}

一句话讲清楚

🔬 掰开揉碎：Modbus 帧结构（你必须懂，才能排错）

NModbus 帮你封好了帧，但现场数据对不上时，你得知道线长什么样才能查： - RTU 帧（走串口）：[从站地址 1B][功能码 1B][数据 N 字节][CRC 低 1B][CRC 高 1B] - 例：01 03 00 00 00 0A C5 CD = 从站1 + 读保持寄存器(0x03) + 起始0 + 读10个 + CRC - 注意帧头没有固定 AA 55 那种标志，靠「地址+功能码+长度隐性约定」+ CRC 来切分 —— 所以 RTU 对字符间隔(帧间超时)敏感，串口参数错了整帧废。 - TCP 帧（走网口）：[MBAP 头 7B][功能码 1B][数据]。MBAP 头含「事务号/协议号=0/长度/单元标识」，多了长度字段就不用 CRC了（TCP 本身可靠）。 - 功能码全集（记常用的）： | 码 | 含义 | 本项目 | |---|---|---| | 0x01/0x02 | 读线圈 / 读离散输入 | 布尔量 | | 0x03 | 读保持寄存器 | ✅ 模拟量主用 | | 0x04 | 读输入寄存器 | 传感器只读量 | | 0x05/0x06 | 写单线圈 / 写单寄存器 | 下发设定值 | | 0x0F/0x10 | 写多线圈 / 写多寄存器 | 批量下发 | - 异常码（真实设备会回，必须 catch）：从站不回正常数据、而回 功能码|0x80 + 异常码。常见： | 异常码 | 含义 | 现场对策 | |---|---|---| | 0x01 | 非法功能 | 这设备不支持该码，换功能 | | 0x02 | 非法数据地址 | 地址超范围，检查 ±1 偏移 | | 0x03 | 非法数据值 | 写的值超设备允许范围 | | 0x04 | 从站设备故障 | 设备内部错，重试/查设备 | | 0x0B/0x0C | 忙 / 不允许 | 设备正忙，退避重试(见 M9) | NModbus 会把它抛成 ModbusSlaveException，务必 try-catch 区分「通信断」和「设备拒」。

⚠️ 重点 & 易踩坑

① 连接 + 读字节（🟧）

🔬 掰开揉碎：S7 错误模型（现场高频坑 + 面试高频）

和串口/Modbus 不同，S7.Net 很多失败「不抛异常」，而是返回错误状态——这是新手最容易栽的地方： - plc.IsConnected 不可全信：Open() 成功只代表「握手成功」，线中途掉了 IsConnected 可能还是 true。正确做法：每次读后检查 plc.LastErrorCode（0 = OK，非 0 = 出错），或读之前 ReadStatus() 探活。 - 读失败要判错误码再决定重试： csharp var buf = plc.ReadBytes(DataType.DataBlock, 1, 0, 4); if (plc.LastErrorCode != 0) // 非 0 即出错（如 0x0005 地址错、0x000A 对象不存在） { Log.Warning("读 DB1 失败 错误码{Code}", plc.LastErrorCode); // 用 M9 的 Retry 退避重连，别裸 throw } - 常见错误码：0x0005 地址/长度非法（DB 号或偏移写错）、0x000A 对象不存在（DB 没下载/被删除）、0x7000+ 通信层错误（断线/PLC 停止）。 - 类比修正：之前说「DB块号+偏移 = 表名+字段偏移」不够准——DB 块是「结构化变量容器」，更像「一个 class 实例」，DB1.DBW2 是「实例的字段」，不是裸字节表。读字节后用 S7.GetRealAt(buf,0) 这种带类型的解码方法才是正道（类比 ORM 把行映射成强类型对象）。

public class SensorRecord
{

    public double Value { get; set; }
    public DateTime Time { get; set; }

public class AppDb : DbContext
{

    protected override void OnConfiguring(DbContextOptionsBuilder b)
        => b.UseSqlite("Data Source=daq.db");   // 单文件数据库

🔬 掰开揉碎：DbContext 到底在管什么（变更追踪 Change Tracking）

很多人 SaveChanges() 调得好好的，但被面试官问「它怎么知道哪些改了」就懵。拆开讲： - DbContext 是个「工作单元 + 缓存」：你 db.Records.Add(x) 或改 r.Value=99，它并不立刻写库，而是把实体记进内部「追踪缓存」并标记状态（Added/Modified/Deleted）。 - SaveChanges() 才一次性比对、生成 SQL、提交事务。这就是为什么你改了属性不调 SaveChanges 数据库没变化。 - 为什么要「短生命周期」：追踪缓存会一直持有实体引用，一个 DbContext 用一辈子 = 缓存无限膨胀 + 并发写冲突。正确：每次操作 new AppDb() 用完 Dispose（using），或 DI 里用 Scoped（一次请求/一次批量任务一个实例）。 - 高频写入策略：每秒几千条别每条 SaveChanges（每次都开事务，慢 10 倍）。攒一批（如每秒 500 条）一次 AddRange+SaveChanges；或用 SQLite 的 WAL 模式（PRAGMA journal_mode=WAL）提升并发读写。

🔬 掰开揉碎：迁移（Migration）是干什么的

  • 问题：你改了 SensorRecord 加个字段，数据库表结构不会自动变。手动改表易错、不可复现。
  • 迁移 = 把「模型变化」记成一份可版本化的脚本，一路 Up/Down： bash dotnet tool install --global dotnet-ef # 装 CLI（一次性） dotnet add package Microsoft.EntityFrameworkCore.Design dotnet ef migrations add Init # 生成第一版迁移（建表） dotnet ef database update # 把迁移应用到数据库 # 以后改模型 → dotnet ef migrations add AddColumnX → update
  • 为什么 15K 必须会：企业项目表结构随需求变，靠迁移才能「代码和库结构同步、可回滚、可部署到客户机自动建库」。本项目为演示用了 Code First 运行时建库，真项目请用迁移。

③ 实时追加（事件→入队→定时批量）（呼应 M0 Day 7 跨线程 + M5② 批量刷新）

🔥 修正说明：早期版本在 DataReceived 里用 Dispatcher.Invoke 逐点刷新 UI —— 100Hz×多设备时直接卡死。正确做法是：事件只负责入队，UI 用定时器批量刷新。

// 1) 事件只做“入队”这件极轻的事（线程安全，不阻塞采集线程）
var ch = System.Threading.Channels.Channel.CreateUnbounded<SensorPoint>();
device.DataReceived += (s, e) =>
    ch.Writer.TryWrite(new SensorPoint { Id = e.PointId, Value = e.Value, Timestamp = DateTime.Now });

// 2) UI 线程用 DispatcherTimer 每 500ms 定时“批量拉取”一批，一次性画曲线
var timer = new DispatcherTimer { Interval = TimeSpan.FromMilliseconds(500) };
timer.Tick += (_, _) =>
{
    var batch = new List<SensorPoint>();
    while (ch.Reader.TryRead(out var p)) batch.Add(p);   // 取出这一批
    if (batch.Count == 0) return;
    var series = (LineSeries<ObservablePoint>)vm.Series[0];
    foreach (var p in batch)                              // 批量追加，不是逐点
        series.Values.Add(new ObservablePoint(p.Timestamp.Second, p.Value));
    while (series.Values.Count > 200) series.Values.RemoveAt(0); // 限长防内存涨
};
timer.Start();

📌 更完整的企业级封装见 M9 统一采集架构（AcquisitionPipeline）：用 Channel<T> + Timer 把“可视化 / 报警 / 上云”统一成「事件→入队→定时批量」一条流水线，避免每个模块各写一套逐点刷新。

🔬 掰开揉碎：为什么用 Channel<T> 而不是直接 ObservableCollection.Add

直觉上「收到点就 series.Values.Add 不行吗？」在低频(1Hz)下可以，但工业是 100Hz×多设备： - ObservableCollection.Add 会立刻通知 UI 重绘：每加 1 个点，WPF 就重画一次曲线。100Hz = 每秒重绘 100 次，UI 线程直接被打满 → 卡死/掉帧。 - Channel<T> 是无锁队列缓冲：Writer.TryWrite 是 O(1)、线程安全、几乎零开销，只把点存进去，不碰 UI。然后 DispatcherTimer 每 500ms 一次性「取出这一批 → 批量 Add」，重绘频率从 100 次/秒降到 2 次/秒。 - 一句话：Channel 把「高频生产」和「低频消费」解耦，这正是 M9 统一采集管道的核心思想（可视化/报警/上云全从 BatchReady 批量取）。

⚠️ 重点 & 易踩坑

项 说明
⭐ 事件里只入队 DataReceived 是高频率后台回调，里面只做极轻操作，重活交给定时器
⭐ 跨线程改 UI 要回 UI 线程 DispatcherTimer 的 Tick 自动在 UI 线程；若订阅后台线程事件（如 M9 的 BatchReady）要用 Dispatcher.Invoke
⭐ 限制点数 曲线无限增长 = 内存泄漏 + 卡顿，固定窗口(如 200 点)
🔥 绑定没生效 Series 要 public 属性 + 实现通知，或用 ObservableCollection
🔥 高频刷新卡 别每毫秒刷新，定时(100~500ms)批量更新

Day 1 — 报警引擎 + 事件总线

分点精讲

① 规则模型 + 引擎（🟦）

public class AlarmRule
{
    public int PointId { get; set; }
    public double Threshold { get; set; }
    public AlarmLevel Level { get; set; }      // M0 Day2 的 enum
    public bool IsHigh { get; set; } = true;   // true: 超上限报警；false: 低于下限
}

public class AlarmEngine
{
    private readonly List<AlarmRule> _rules = new();
    public event EventHandler<AlarmEvent>? AlarmTriggered;

    public void Add(AlarmRule r) => _rules.Add(r);

    public void Evaluate(SensorPoint p)
    {
        foreach (var r in _rules)
            if (r.PointId == p.Id && (r.IsHigh ? p.Value > r.Threshold : p.Value < r.Threshold))
                AlarmTriggered?.Invoke(this, new AlarmEvent { PointId = p.Id, Level = r.Level, Value = p.Value });
    }
}

② 接到数据流（呼应 M0 Day 6）

device.DataReceived += (s, e) =>
{
    var p = new SensorPoint { Id = e.PointId, Value = e.Value };
    engine.Evaluate(p);          // 自动判警
};
engine.AlarmTriggered += (s, a) => Console.WriteLine($"⚠ 点位{a.PointId} 报警{a.Level} 值={a.Value}");

🔬 掰开揉碎：回滞（Hysteresis）—— 生产报警的「必做题」

讲义之前把回滞标成「可选进阶」，但本项目的 AlarmEngine.cs 真实代码已经用了它，你必须会写，否则你写不出和项目一致的实现。 - 问题场景：阈值 100，真实温度在 99↔101 之间抖动（工业常态，噪声导致）。没有回滞时：101 报警 → 100 不报 → 101 又报 → 100 又不报……一秒内刷几十次「报警/恢复」，这就是报警风暴，值班人直接无视。 - 回滞解法：设两个阈值——触发 100 / 恢复 95。只有「超过 100」才报；之后要「降到 95 以下」才算恢复，中间抖动区间（95~100）保持原状态不变。类比：空调设 26°，到 26° 停机，但回到 28° 才重启，避免频繁启停。 - 本项目 AlarmRule 的真实字段（代码里就有）： csharp public double Threshold { get; set; } // 触发阈值（如 100） public double Hysteresis { get; set; } // 回滞带（如 5 → 恢复阈值 = 95） public bool IsHigh { get; set; } = true; // true: 超上限报警；false: 低于下限报警 - 边沿触发（本项目也做了）：即使值持续超阈值，也只报一次（记录「已报警」状态，恢复前不再重复触发），这就是之前 M9 测试 Evaluate_FiresOnlyOnRisingEdge 验证的行为——避免「持续超阈还每秒刷屏」。

⚠️ 重点 & 易踩坑

⭐ 防抖 / 回滞 值在阈值附近抖动会狂报警，用"恢复区间"避免（可选进阶）
🔥 报警风暴 一秒内上千点超限，要限流/聚合再通知

🔬 掰开揉碎：OPC UA 别用 .Result 同步阻塞（本项目已改为异步）

🔬 掰开揉碎：[ObservableProperty] 到底生成了什么（源生成器 Source Generator）

手写 INotifyPropertyChanged 又臭又长（每个属性要 OnPropertyChanged）。CommunityToolkit.Mvvm 用 Roslyn 源生成器在编译期帮你生成样板代码： - 你写：[ObservableProperty] private double _currentValue; - 编译后自动生成：public double CurrentValue { get => _currentValue; set { _currentValue = value; OnPropertyChanged(); } } + 实现 INotifyPropertyChanged。 - [RelayCommand] 同理生成 StartCommand 属性和 ICommand 实现。 - 为什么比手写好：零样板、不会漏写 OnPropertyChanged、编译期就检查类型。进阶阅读：源生成器原理 https://learn.microsoft.com/dotnet/csharp/roslyn-sdk/

🔬 掰开揉碎：DI 生命周期怎么选（WPF + EF Core 场景）

AddSingleton / AddScoped / AddTransient 选错会出诡异 bug： - Singleton（全局唯一）：PointStore、AlarmEngine、AcquisitionPipeline——整个程序就一份，所有窗口/线程共享。 - Scoped（一次作用域一份）：DbContext 必须用 Scoped（或每次 new）。原因见 M4「变更追踪缓存」——一个 DbContext 用太久缓存膨胀、并发冲突。在 WPF 里常手动开 using var scope = provider.CreateScope() 包住一次数据库操作。 - Transient（每次都新建）：轻量无状态工具类用，别给有状态的服务用（会各自一份、不共享）。 - 循环依赖：A 构造函数要 B、B 又要 A → 启动即炸，拆出公共依赖到第三个类。

Day 3 — 统一采集架构（Channel + 定时批量）

一句话讲清楚

所有设备数据走同一条流水线：事件只做"入队" → Channel<T> 缓冲 → Timer 定时把一批取出来 → 一次性推给"可视化 / 报警 / 上云"。彻底消灭"每个模块各写一套逐点刷新"的混乱。

🔥 为什么必须这样（修正 M5③ / M7② 的坑）：早期在 DataReceived 里 Dispatcher.Invoke 逐点刷曲线、或 await PublishAsync 逐点发云——100Hz × 多设备时 UI 线程被刷爆、MQTT 抖动。正确姿势：事件里只入队，重活交给定时器批量做。

前端类比秒懂

上位机（C#） 前端
device.DataReceived += ... emitter.on('data', ...)
Channel.Writer.TryWrite 消息入队（queue.push）
Timer 定时 Flush setInterval 批量消费
BatchReady 事件 发布到订阅者（事件总线）

分点精讲

① 统一管道 AcquisitionPipeline（本项目真实代码）（🟦 System.Threading.Channels）

public sealed class AcquisitionPipeline : IDisposable
{
    private readonly Channel<SensorPoint> _channel = Channel.CreateUnbounded<SensorPoint>();
    public event EventHandler<IReadOnlyList<SensorPoint>>? BatchReady;   // 批就绪，后台线程触发

    public AcquisitionPipeline(TimeSpan flushInterval, int maxBatch = 500)
        => _flushTimer = new Timer(_ => Flush(), null, flushInterval, flushInterval);

    public void Register(IDevice device)
        => device.DataReceived += (s, e) =>
            _channel.Writer.TryWrite(new SensorPoint { Id = e.PointId, Value = e.Value, Timestamp = e.Timestamp });

    private void Flush()
    {
        List<SensorPoint>? batch = null;
        lock (_gate) { if (_pending.Count > 0) { batch = _pending; _pending = new(); } }
        if (batch is not null) BatchReady?.Invoke(this, batch);   // 一批推给所有订阅方
    }
}

② 可视化 / 报警 / 上云 统一订阅 BatchReady（🟩 WPF）

// 可视化（M5）：后台线程事件 → Dispatcher 回 UI 线程批量画曲线
_pipeline.BatchReady += (s, batch) => Application.Current.Dispatcher.Invoke(() =>
{
    foreach (var p in batch) chart.Add(new ObservablePoint(p.Timestamp.Second, p.Value));
});
// 报警（M6）：批量送进 AlarmEngine 评估

// 上云（M7）：批量发布（不再逐点 PublishAsync）
_pipeline.BatchReady += async (s, batch) => { foreach (var p in batch) await _mqtt.PublishAsync(p); };

③ 限流（maxBatch）：_pending 攒满 maxBatch（如 500）也立刻出队，防突发洪峰堆爆内存。

⚠️ 重点 & 易踩坑

项 说明
⭐ 事件里只做极轻操作 TryWrite 是 O(1) 无锁入队，绝不写文件/刷 UI/发网络
⭐ BatchReady 在后台线程 订阅方若要改 UI 必须 Dispatcher.Invoke，否则跨线程异常
⭐ 单一数据源 可视化/报警/上云都读同一批 SensorPoint，天然一致
🔥 忘记 Flush 间隔 间隔太长曲线"跳变"，太短失去批量意义（200~500ms 通常合适）
🔥 Dispose 要退订 Dispose 里 _channel.Writer.TryComplete() + 退订 DataReceived，防内存泄漏

Day 4 — 生产级容错与重试（Retry）

一句话讲清楚

工业现场通信必出错（串口松动、PLC 忙、网络闪断）。合格做法是：失败自动重试 + 指数退避 + 抖动，而不是把异常直接甩给用户或默默吞掉。

前端类比秒懂

上位机（C#） 前端
Retry.ExecuteAsync(action, 3) axios-retry / fetch 重试封装
指数退避 base * 2^n 重试间隔翻倍，避免雪崩
Random 抖动 错开多个客户端的重试时刻
CancellationToken 超时 AbortController / setTimeout 取消

分点精讲

① 为什么裸 try/catch 不够（🟦） 裸 catch 要么"失败就抛"（用户体验差），要么"catch 后啥也不干"（故障被藏起来）。重试 + 退避才是正解。

② 本项目真实 Retry（指数退避 + 抖动）（🟦）

public static async Task ExecuteAsync(Func<Task> action, int maxRetries = 3, int baseDelayMs = 200, CancellationToken ct = default)
{
    var attempt = 0;
    while (true)
    {
        try { await action(); return; }
        catch (Exception) when (attempt < maxRetries && !ct.IsCancellationRequested)
        {
            attempt++;
            var delay = (int)(baseDelayMs * Math.Pow(2, attempt - 1))   // 200→400→800ms 指数退避
                        + Random.Shared.Next(0, baseDelayMs);           // 加随机抖动，避免多设备同时重试
            await Task.Delay(delay, ct);
        }
    }
}

③ 用在"会失败的地方"（🟧 串口/Modbus/PLC/网络）

// 连接设备：失败重试 3 次（首试+3次=共4次），指数退避
await Retry.ExecuteAsync(() => Task.Run(() => device.Connect()), maxRetries: 3);
// 上云发布：断线重连用 Retry（呼应 M7②）
await Retry.ExecuteAsync(() => client.PublishAsync(msg), maxRetries: 5);

④ 配合超时（CancellationToken）（🟦）

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5)); // 5s 超时
await Retry.ExecuteAsync(() => ReadWithTimeout(addr, cts.Token), maxRetries: 2, ct: cts.Token);

⚠️ 重点 & 易踩坑

项 说明
⭐ 只对"瞬时故障"重试 网络抖、设备忙可重试；参数错/权限错重试也没用，要快速失败
⭐ 退避别用固定间隔 固定间隔会让上千设备同时重试把服务端打挂，必须指数+抖动
⭐ 设上限 + 超时 重试次数和总时长要有上限，否则卡死在重试里
🔥 吞异常 catch{} 空捕获是事故温床；至少记日志或上抛
🔥 重试幂等 写操作（如下发指令）重试前确认可重复执行，避免重复写入

企业报表的本质：把海量原始记录，按"维度+时间窗"聚合成少量统计行。

① 聚合服务（🟦 LINQ + 🟩 DateTime，纯计算、可单测）

// DaqMonitor.Core/Reporting/ReportService.cs
public sealed class ReportService
{
    public IReadOnlyList<PointStat> Aggregate(IEnumerable<SensorPoint> points, DateTime from, DateTime to)
    {
        return points
            .Where(p => p.Timestamp >= from && p.Timestamp <= to)  // 时间窗过滤
            .GroupBy(p => p.Id)                                    // 按点位分组
            .Select(g => new PointStat(
                PointId: g.Key,
                Count: g.Count(),
                Min:   g.Min(p => p.Value),
                Max:   g.Max(p => p.Value),
                Avg:   g.Average(p => p.Value),
                First: g.Min(p => p.Timestamp),
                Last:  g.Max(p => p.Timestamp)))
            .OrderBy(s => s.PointId)
            .ToList();
    }
}

一、先搞懂：上位机在跟什么硬件打交道

1.1 上位机 / 下位机（一句话 + 类比）

二、硬件基础科普（不懂硬件也能懂，全用类比）

2.1 串口：RS232 vs RS485（最容易混的两个）

🟦 C# 语法天生物 · 🟩 .NET 类库（System.IO.Ports）· 🟧 第三方（无，串口是系统自带）

串口 = 计算机和外设之间一根线一根线传字节的古老但极可靠的通信方式。工业现场 90% 的简单设备都靠它。

维度 RS232 RS485
连接拓扑 点对点（1 对 1，像一根 USB 直连线） 总线（1 根线挂 N 个设备，像一根网线接多个设备）
信号方式 单端（对地电压 ±12V） 差分（A、B 两线电压差，抗干扰强）
距离 短（< 15 米） 远（1200 米）
节点数 1 对 1 32+ 个设备挂同一条总线
前端类比 localhost 直连（只有你和我） 公司内网（一个交换机挂一堆电脑）

为什么工业爱 RS485？ 工厂里传感器离电脑几十米、电机干扰大，RS232 早被干扰搞死；RS485 用"差分信号"（A 比 B 高就是 1，低就是 0），电磁噪声同时打到 A 和 B 上会被抵消，天生抗干扰。你的 USB 转 485 线（¥20）插电脑上，电脑就多出一个 COM 口，当 RS485 用。

串口"三件套"参数（双方必须完全一致，否则乱码/连不上）： | 参数 | 常见值 | 类比 | |---|---|---| | 波特率 (Baud) | 9600 / 19200 / 115200 | 网速（双方必须同速，否则"鸡同鸭讲"） | | 数据位 | 通常 8 | 每个"字节"几位 | | 停止位 | 通常 1 | 帧之间的间隔位 | | 校验 (Parity) | None / Odd / Even | 简单的"校验和"，防传错 |

🔥 坑：下位机手册写"9600,8,N,1"就是 波特率9600、8数据位、无校验、1停止位。你设错一个就全乱码——这是现场第一高频故障。

2.2 传感器信号：设备在"用什么语言"告诉你数值

🟦 概念科普 · 🟩 无需代码 · 🟧 无

真实世界的物理量（温度、压力）要变成上位机能读的数字，中间有"变送"过程。常见信号：

信号类型 含义 前端类比 为啥这么设计
4–20mA 电流环：4mA=量程最低，20mA=最高 用电流大小当数值 抗干扰最强；断线时电流=0mA，立刻知道"线断了"（不像电压会被干扰）
0–10V 电压：0V=最低，10V=最高 用电压高低当数值 简单便宜，但线长易受干扰
PT100 热电阻：0°C 时电阻正好 100Ω，温度变电阻变 一个"会随温度变阻值的电阻" 测温度经典方案，需变送器转成 4–20mA
热电偶 两种金属接合产生毫伏级电压（K 型等） 温差→微小电压 测高温（上千度），需冷端补偿
数字量 DI/DO 开关量：24V=通(1)，0V=断(0) true / false 按钮、限位开关、继电器

🔑 你作为上位机工程师要知道的：绝大多数仪表把"物理量"先变成 4–20mA 或 0–10V，再用 RS485+Modbus 把数字传给你的软件。所以你只管读 Modbus 寄存器里的数字，不用自己处理电流电压——那是仪表厂的事。你只要知道"这个寄存器的值 × 量程系数 = 真实温度"就行。

2.3 PLC 是什么（你最大的陌生点，掰开讲）

🟦 概念科普 · 🟩 无需代码 · 🟧 S7.Net（M3）

PLC = 现场的一台专用小电脑，专门用来控制机器（比你的笔记本皮实，能在电柜里 7×24 跑十年）。

PLC 概念 是啥 前端类比
DB 块（数据块） PLC 里一块命名的内存区，存变量 一个 const config = {...} 对象 / 一块共享内存
地址（如 DB1.DBD0） 变量在内存里的具体位置 对象属性路径 config.temp
I / Q / M 输入(I) / 输出(Q) / 中间标志(M) 区 读传感器 / 控制执行器 / 临时变量
S7 通信 西门子私有的"读 DB 块"协议 一个专用的 readDb(block, offset) API
TIA Portal 西门子官方编程软件（写 PLC 程序用） PLC 的"IDE"

🔑 你写上位机，不是写 PLC 程序。你的工作是：用 S7.Net（或 Modbus）去读 PLC 的 DB 块里已经算好的数值。PLC 程序员负责把温度传感器的值算好放进 DB1 的第 0 个浮点数——你只管 ReadFloat("DB1", 0) 拿走。这就是"上位机对接 PLC"的全部日常。

2.4 接线与抗干扰（现场最容易翻车的地方）

🟦 经验科普 · 🟩 无需代码 · 🟧 无

问题 现象 解决
A/B 接反（RS485） 完全不通 / 疯狂乱码 把 A、B 两根线对调
没共地（两端电源不同） 时通时断、偶发乱码 把两端 GND 地线连起来（参考电位）
终端电阻缺失 远距离 / 高波特率时乱码 总线两端各并一个 120Ω 电阻（防信号反射）
强电干扰 电机一启动就掉线 信号线和动力线分开走线，用屏蔽双绞线，屏蔽层单端接地

🔥 真实现场口诀："连不上先查线，乱码先查地（共地）和终端电阻，偶发掉线查干扰和电源。"——这比任何协议都重要，因为 80% 的"通信故障"是物理层，不是代码。

🟩 T1 纯软件方案（零硬件，随时可练）

① SimulatedDevice（项目里已经有了！） - 它实现 IDevice，后台线程周期产点，就是个"假数据源"。 - 你之前跑 dotnet run 看到的跳动点位，就是它产的。 - 用途：练通"采集→管道→存储→报警→界面"全链路，完全不需要硬件。

② Moq 虚拟设备（M9 教过）

var device = new Mock<IDevice>();
device.Setup(d => d.Connect()).Raises(d => d.DataReceived += null,
    new DataEventArgs { PointId = 1, Value = 36.5 });
  • 单元测试里用，隔离硬件，测你的逻辑。

③ 数据回放（最像现场） - 录一段真实数据到 CSV/JSON，回放器逐行 RaiseData。 - 好处：能反复复现"那天凌晨 3 点报警"的 bug，不用等真机再出一次。

💡 企业真实做法：很多上位机团队先无硬件开发（用 SimulatedDevice 把界面、报警、报表全做完），等真机到了只换一个 Device 实现，一天接入。你现在的 DAQMonitor 就是这路数——M1–M7 只需把 SimulatedDevice 换掉。

🟩 T2 虚拟接口方案（代码和真机一模一样，只是对端是软件）

① 虚拟串口对（M1 练手必备） 🟧 com0com / VSPD - 是什么：装一个驱动，虚拟出 COM3 ↔ COM4 一对"背靠背"的串口。你的 DAQ Monitor 开 COM3，另一个小程序（或串口调试助手）开 COM4 发数据，数据从 COM4 流进 COM3，完全模拟"仪表连着电脑"。 - 怎么用： 1. 装 com0com（Win10/11 需测试模式签名，见外链）→ 建 COM3<->COM4。 2. DAQ Monitor 把 SerialDevice 注册到 COM3。 3. 用"串口调试助手"或 10 行 Python 往 COM4 发一帧 AA 55 ...。 4. 看 MainWindow 是否出现对应点位。 - 真实度：⭐⭐⭐⭐ 你的串口代码和连真仪表一行都不用改。

② Modbus 从站模拟器（M2 练手） 🟧 QModMaster / Modbus Slave / diagslave - 是什么：一个跑在你电脑上的"假仪表"，监听某个串口或 TCP 端口，响应你主站的读请求。 - 怎么用： 1. 开 diagslave -m tcp -p 502（TCP 从站）或 QModMaster 当从站。 2. DAQ Monitor 用 NModbus 主站连 localhost:502，读保持寄存器。 3. 你在模拟器里改个值，软件里立刻变——和真电表一模一样。

③ PLCSIM + NetToPLCSim（M3 练手） 🟧 - 是什么：西门子官方 PLCSIM 在电脑里仿真一台 PLC；NetToPLCSim 把它的通信"透传"到网络端口，这样 S7.Net 能像连真 PLC 一样连它。 - 怎么用：TIA 里写个简单 DB 块 → 下载进 PLCSIM → 开 NetToPLCSim 映射 → DAQ Monitor 用 S7.Net 连 127.0.0.1 读 DB。 - 限制：需有 TIA Portal + PLCSIM（学生版/试用版可）。

④ OPC UA 模拟服务器 / 本地 MQTT（M7 练手） 🟧 - OPC UA：Prosys OPC UA Simulation Server 本地跑，提供随机变化的节点，你的 UA 客户端去订阅。 - MQTT：本地装 Mosquitto broker，mosquitto_pub 发消息，你的 MQTTnet 客户端订阅——和真上云代码一致。

四、连不上的万能排查清单（真实现场经验，背下来）

无论虚拟还是真机，按这个顺序查，能解决 95% 的"通信失败"：

1. 物理层（先查线！）
   □ 串口：COM 口号对吗？（设备管理器看）
   □ 485：A/B 接反了吗？（对调试一下）
   □ 共地接了吗？（两端 GND 连起来）
   □ 远距离/高波特率：总线两端 120Ω 终端电阻有吗？
2. 参数层（双方必须一致）
   □ 波特率 / 数据位 / 停止位 / 校验 对吗？
   □ 流控 DTR/RTS 要不要拉高？（部分设备必须）
3. 网络层（TCP/OPC/MQTT 类）
   □ IP / 端口对吗？防火墙放了吗？
   □ PLC：DB 号/偏移和 TIA 一致吗？该 DB "优化访问"关了吗？
   □ PLC 在 RUN 吗？允许 PUT/GET 通信吗？
4. 协议层
   □ Modbus：寄存器地址 ±1 偏移对吗？（手册 40001 vs 代码 0）
   □ 从站地址（站号）对吗？
5. 软件层
   □ 你的 Device 注册进 Bootstrapper 了吗？
   □ 异常信息是啥？（看 Serilog 日志，别瞎猜）

🔥 血的教训：新手 80% 时间花在"代码没错但线没接对/参数没对齐"。先看物理层和参数层，再看代码。

五、🏗️ 动手练习（从零搭虚拟环境跑通，零硬件）

练习 1：用虚拟串口让 DAQ Monitor 收到"假仪表"数据

目标：不买任何东西，让 M1 的串口代码真正跑起来。 1. 装 com0com，建虚拟对 COM3<->COM4。 2. 在 DaqMonitor.Core/Devices/ 写 SerialDevice : DeviceBase，Connect() 里 new SerialPort("COM3", 9600, Parity.None, 8, StopBits.One) 并 Open()，DataReceived 里把字节喂给帧解析器，RaiseData 抛出点位。 3. 注册进 Bootstrapper 替换 SimulatedDevice。 4. 用任意"串口调试助手"开 COM4，发一帧 AA 55 02 00 1E 3C 9E（示意帧）。 5. 运行 DAQ Monitor，dotnet run，看 MainWindow 是否出现点位。

✅ 答案要点： - SerialPort 来自 🟩 System.IO.Ports（.NET 8 需 dotnet add package System.IO.Ports）。 - 必须用 DataReceived 事件 + 字节缓冲解决半包/粘包（见 M1 帧解析器），不能"收到就当一帧"。 - 收不到先查：COM 号对不对、DataReceived 在某些机器不触发 → 改用 BaseStream.ReadAsync 循环读。 - 跑通 = 你已经会写工业串口程序了，和连真仪表代码一致。

练习 2：用 Modbus 从站模拟器读"假电表"

目标：练 M2 主站。 1. 下载 diagslave，命令行 diagslave -m tcp -p 502 -a 1 起一个 TCP 从站（站号 1）。 2. DAQ Monitor 用 NModbus TcpClient 连 127.0.0.1:502，读保持寄存器 0 起 5 个值。 3. 在 diagslave 里改寄存器值，看软件是否同步变化。

✅ 答案要点：注意地址偏移（手册 40001 → 代码 0）；NModbus 是 🟧 第三方包；这就是真实智能电表的读法。

练习 3：画出"你家的通信拓扑"

画一张图：电脑 →（USB-485）→ 智能电表 →（RS485 总线）→ PLC →（网线）→ 你的 DAQ Monitor。标注每个环节的接口、协议、参数。这是面试常考的"你懂不懂现场"题。

六、📌 温故知新 / 跨模块联动

  • 关联 M0：M0 教的"后台线程 + 事件 + 并发"在这里直接用到——SerialPort.DataReceived 是后台线程回调，你处理字节时绝不能跨线程碰 UI（复习 M0 Day7 的 Dispatcher/批量原则）。
