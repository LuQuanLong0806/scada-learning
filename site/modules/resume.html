三、项目经验(STAR 法)

项目一(主项目):DAQMonitor — 工业数据采集监控系统 ★★★★★

S(背景):某 3C 行业产线设备(PLC + 温控仪表 + 能耗表 + IO 模块)需统一接入 MES,要求 7×24 稳定运行、毫秒级采集、报警实时推送、报表自动导出、双向远程控制。

T(任务):作为唯一开发者,从协议层 → 数据层 → UI 层 → 部署文档独立完成全套系统。技术栈:C#/.NET 8 / WPF / Prism / EF Core 8 + SQLite / Serilog / LiveCharts2。

A(行动):

  • 协议层抽象:基于"设备抽象 + 协议插件"模式,封装 5 种设备驱动(Modbus RTU 仪表 / Modbus TCP IO / S7-1200 PLC / OPC UA / MQTT 网关),通过 IDevice<TConfig> 接口统一读写,新增设备只需实现接口 + 配 JSON;
  • 采集引擎:基于 Channel<T> 实现生产者-消费者,采集线程 → Channel → 解析线程 → 入库 + UI 推送,主线程零阻塞;背压用 BoundedChannel(10000) 控制,满载丢弃旧数据并记 Serilog 告警;
  • 报警引擎:基于回滞算法(Hysteresis)避免阈值抖动误报,每条报警绑定 Ack 确认 + 复位 + 推送规则(声光 / 邮件 / MQTT 上报);
  • 协议细节:Modbus RTU 手算 CRC16 + 异常码 01-06 全覆盖;S7.Net 用 Plc.Read("DB1.DBD4") 读浮点,字节序 ABCD/CDAB 自动识别;OPC UA 用 Subscription 模式订阅;
  • 稳定性:基于 Polly 实现"重试 + 熔断 + 超时"三件套,设备掉线自动重连(指数退避,1s → 2s → 4s → ... → 30s 封顶);事件订阅全部退订(DeviceHost 模式统一释放),7×24 跑 3 天内存稳定在 280 MB,无泄漏;
  • 数据可视化:LiveCharts2 10 万点曲线秒级渲染(基于降采样 + Geared 优化),轴缩放 / 区间选择 / 多 Y 轴;
  • 报表系统:ClosedXML 流式导出 Excel,模板 + 数据绑定模式,产线日报 5 分钟自动生成;
  • MES 对接:MQTT 双向通信(订阅命令 / 发布状态),Payload 用 JSON + Protobuf 兼容,QoS=1 保证命令必达;
  • 测试与文档:xUnit 单元测试 20+ 用例全绿(覆盖 CRC / 字节序 / 报警回滞 / 协议解析),配套《部署手册》《协议规范》《排障 Runbook》3 份文档。

R(结果):

  • 20+ 单元测试全绿,核心协议层覆盖率 85%+;
  • 7×24 持续运行 3 天,内存稳定 280 MB,GC 次数 < 5/小时;
  • 5 种设备统一抽象,新增设备类型平均 2 小时接入;
  • 报警从触发到 UI 推送 < 200 ms;
  • Excel 报表生成 < 3 秒(1 万行 / 10 列)。

钩子 1:你前端 5 年,为什么转上位机?

"前端做了 5 年,我在架构、性能、工程化上都到了瓶颈。而上位机领域强类型 + 工程化 + 性能调优是稀缺能力——绝大多数上位机工程师偏协议和业务,工程素养弱。我做了 30 天调研,发现工业互联网、新能源、3C 装备、半导体这些行业的上位机岗位缺口巨大,而且前端做上位机有天然优势:ECharts 经验直接复用到 LiveCharts,TypeScript 强类型无缝迁移到 C#,async/await 状态机思路一致。所以我决定把前端的工程能力带到工业领域,做有技术深度的产品,而不是再做 100 个表单页面。"

钩子 2:你的设备抽象接口是怎么设计的?(项目最核心)

"我用 interface IDevice<TConfig> 统一抽象,5 种设备(Modbus RTU/TCP、S7、OPC UA、MQTT)各自实现。核心方法 Task<ReadResult> ReadAsync(ReadRequest),ReadRequest 包含地址、长度、数据类型。每个设备实现内部各自处理 CRC、字节序、协议头。新增设备只需 2 步:实现接口 + 加一个 JSON 配置文件。这样上层采集引擎、报警引擎、UI 全部不感知具体协议——本质上是前端的 Adapter 适配器模式,我前端 5 年用过无数次,迁移到 C# 一模一样。"

钩子 3:7×24 跑 3 天,你怎么测的?怎么证明没漏?

"三层验证:第一层,日志层——Serilog 每分钟写一条心跳日志,3 天共 4320 条,我从 Seq 里查都没断;第二层,业务层——每条采集数据都有自增 ID + 时间戳,我从 SQLite 里 SELECT MIN(id), MAX(id), COUNT(*) 验证总数和 ID 连续性,确实 0 缺失;第三层,内存层——dotnet counters monitor --process-id <pid> 持续监控 GC / 堆大小,3 天从 180 MB 涨到 280 MB,第一次大涨我就抓 gcdump,定位到是一个 OPC UA 订阅没退订,修复后稳定。这套路就是前端排查内存泄漏的方法,我从 Cypress 调 ECharts 时积累的经验,直接套到 C# 上。"

九、投递策略 5 条

策略 1:关键词镜像法

把 JD 原文复制到简历左上角(自己看,不投出去),JD 写啥你写啥。

例如:JD 写"Prism 框架" → 简历绝对不要写"MVVM 框架",改写"Prism 9(RegionManager / EventAggregator / 模块化)"; JD 写"西门子 S7 通信" → 简历绝对不要写"PLC 通信",改写"西门子 S7.Net(S7-1200 / S7-1500)"; JD 写"EF Core" → 简历不要写"Entity Framework",改写"EF Core 8 + SQLite(Code First 迁移 + IDbContextFactory)"。

原因:HR 第一遍是 ATS 系统过简历(自动关键词匹配),第二遍才是人看。关键词不匹配,你连人眼都过不了。

策略 2:按 JD 调项目排序

JD 重点写什么,你的项目一就摆什么。

例如:JD 强调"上位机 + PLC" → 项目一摆 DAQMonitor,把"S7.Net / Modbus"提到第一行; JD 强调"上位机 + MES 对接" → 项目一摆 MES_Bridge,把"MQTT / MES"提到第一行; JD 强调"测试 / 半导体" → 项目一摆 PLC_Sim,把"S7 协议模拟器"提到第一行。

策略 3:预期薪资报法

面 HR 报薪资时,永远报区间,不报死数字:

  • HR 问:"你的期望薪资?" → 你:"我目前面了几家,基本都给到 14-15K,我这边期望 15K 左右,具体看岗位匹配度和加班强度。"
  • 绝对不要说"13K 也行"——这是底线泄露,HR 立刻砍价;
  • 绝对不要说"18K 起"——超出岗位预算直接 pass;
  • HR 压价到 13K 时,你:"13K 我可以接受,但需要试用期不打折 / 13 薪 / 期权 / 弹性工作制(选 1 个)。"

策略 4:反问 3 问(面试结尾必问)

面试官问"你还有什么问题吗"——绝对不要说"没有了",这是大忌。必问 3 问:

  1. "这个岗位主要负责哪个产品线 / 哪条产线?设备类型主要是西门子 / 三菱 / 欧姆龙?"(展示技术深度)
  2. "团队现在几个人?上位机和 PLC 工程师怎么分工?"(展示团队协作意识)
  3. "如果我能入职,前 3 个月主要做什么项目?有没有具体 KPI?"(展示目标感 + 主动)

⚠️ 绝对不要问:加班、薪资、五险一金(这些留到 HR 谈薪环节问)。

策略 5:面试后跟进

面试完当天晚上,LinkedIn / 邮件给面试官发一封简短感谢信:

"X 老师,今天感谢您的时间。聊到 S7 字节序的问题让我很有收获,回来我又查了下 —— 实际项目中我用 BinaryPrimitives.ReverseEndianness 处理 ABCD/CDAB 字节序,确实更优雅。期待您的好消息,如果对岗位还有任何问题欢迎随时沟通。"

这一步90% 求职者不做,你做了就是稀缺。别问"出结果了吗",要展示"聊完我还在思考"。
