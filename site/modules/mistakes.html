一、C# 语言基础

E01 · 接口 interface / 类 class / :base / 访问修饰符 🔴

你的原话:"接口 类 :base 访问修饰符"

一句话总纲:interface 定合同(能做什么),class 实现合同(怎么做),:base(...) 接通父子构造链,访问修饰符划可见边界——四个东西共同回答"类型之间怎么连接"。

1. interface —— 运行期真实存在的合同

public interface IDevice
{
    int Id { get; }                                   // 属性:只有签名
    void Connect();                                   // 方法:只有签名
    event EventHandler<DataEventArgs>? DataReceived;  // 还能声明事件
}
  • 接口成员不许写访问修饰符——写 public 直接编译错。合同条款天然全公开,不存在"半公开的条款"。
  • 接口不能有字段、不能有构造函数——它只描述"你能对我做什么",不描述"我肚子里的数据"。
  • 和 TS interface 的核心差异:TS 的 interface 编译成 JS 后不存在了(纯类型标注,擦除);C# 的 interface 编译后真实存在——能 is IDevice 判断、能当 DI 容器的注册类型、能多态分发。前端类比:像 TS interface 有了"运行期的灵魂"。

实现接口(和继承共用一个冒号):

public class SimulatedDevice : DeviceBase, IDevice
//                              ↑ 基类在前     ↑ 接口在后,逗号分隔

C# 单继承、多接口:基类最多 1 个,接口随便几个,顺序必须基类在最前。TS 的 extends B implements C, D 到 C# 里全部挤进冒号后面。

2. :base(...) —— 子类构造函数接通父类

项目实物(R2 的 DeviceBase → SimulatedDevice):

public abstract class DeviceBase : IDevice
{
    protected DeviceBase(int id, string name) { Id = id; Name = name; }
}

public class SimulatedDevice : DeviceBase
{
    public SimulatedDevice(int id, string name, params int[] pointIds)
        : base(id, name)                    // ← 就是 JS 的 super(id, name)
        => _pointIds = pointIds;
}
  • 为什么必须写:DeviceBase 只定义了带参构造(没写无参构造),子类构造必须显式替父类"传参"。不写 : base(...) 编译错 CS7036:"DeviceBase 不包含采用 0 个参数的构造函数"。
  • 执行顺序:子类字段初始化器 → :base(...) 父类构造体 → 子类构造体。ES6 同款规矩:super 先于 this。
  • base 的第二个用法:base.方法() 在子类里调父类成员,等价 super.method()——主要用于"重写之后还要调一次原版"。项目里子类直接调 RaiseData()(继承来的),不需要 base 前缀。

3. 访问修饰符 —— 六档可见性,先记三档

修饰符 谁能看见 前端类比
public 所有人 export
private 类成员默认! 本类内部 模块内不 export 的变量
protected 本类 + 子类 没直接对应;可理解为"专门留给子类碰的钩子"
internal 同一程序集(同一个编译出的 dll/exe) monorepo 包内可见、不对外发布的内部模块
protected internal / private protected 组合档,入门阶段不用碰 —

三个高频易错:

  1. C# 类成员默认 private,TS 默认 public——前端转过来最容易翻车的一处。C# 里不写修饰符的方法,出了这个类全不可见。
  2. 接口成员不能写修饰符(上面说过);但接口本身该写 public 还是要写(要对程序集外可见时)。
  3. 属性的读写可以拆开:public DeviceState State { get; protected set; }——读公开、写只留给子类。项目里 DeviceBase.State 就是这个设计:UI 只能看设备状态,只有设备自己(子类)能改,状态机的修改权收进设备内部。访问修饰符不只是"权限标注",是设计工具。

自测(全对再翻篇)

  1. interface 的方法写 public void Connect(); 会怎样?为什么?
  2. 基类只有 (int, string) 构造,子类构造不写 : base(...) 会怎样?
  3. class A : B, IC, ID 合法吗?B、IC、ID 各是什么?顺序能换吗?
  4. public int X { get; private set; } 和 public int X; 的区别?
  5. C# 类成员不写修饰符默认是什么?TS 呢?
答案(先自己答再看)
  1. 编译错——合同条款天然全公开,不需要再标 public。
  2. CS7036 编译错——父类没有无参构造,子类必须显式传参。
  3. 合法。B 是基类(最多一个),IC/ID 是接口(可多个);基类必须排在最前,不能换。
  4. 前者是属性:外部只读(set 私有);后者是公开字段,外部随便改。
  5. C# 默认 private;TS 默认 public。

二、异步与多线程

E02 · Task.Run / Task.Delay / 异步循环 🔴

你的原话:"Task.Run Task.Delay loop 等相关的我很不熟"

一句话总纲:Task 是"将来完成的工作"(≈ Promise),Task.Run 把工作丢线程池(≈ 真并行的 setTimeout),Task.Delay 异步睡不占线程(≈ sleep 但必须 await),异步循环 = "等一拍、走一步"。

1. 概念总表(对照 JS)

C# 是什么 JS 对照 本质差异
Task 一次将来完成的工作 Promise Task 可能跑在别的线程(真并行);JS 永远单线程
Task.Run(fn) 把 fn 丢线程池,立刻返回 setTimeout(fn, 0) setTimeout 还是原线程回头执行;Task.Run 是另一个核并行跑
await Task.Delay(ms) 异步等 ms,线程被释放 await sleep(ms) 完全同构;不 await 就什么都没发生
Thread.Sleep(ms) 阻塞当前线程干等 (JS 没有对应) UI 线程上 Sleep = 界面冻结;永远别在 UI 线程用

2. Task.Run —— "丢到后台,我继续干我的"

// R2 SimulatedDevice:Start() 立刻返回,采集循环在后台跑
_cts = new CancellationTokenSource();
_loop = Task.Run(() => LoopAsync(_cts.Token));   // 丢给线程池,这行立即往下走
  • 返回 Task:不 await 它,当前代码"发射后不管"(fire-and-forget);await 它,就等后台干完。
  • 最大的坑:Task.Run 里抛的异常装在返回的 Task 里——没人 await,异常静默消失。所以项目里 fire-and-forget 的循环体内自己 try-catch 兜底(AcquisitionPipeline.ConsumeAsync 整个包 try)。
  • 什么时候用:CPU 密集活、要一直转的后台循环。不要用来包"本来就是异步的 IO"(串口/网络读)——那些直接 await。

3. Task.Delay —— 异步的睡

await Task.Delay(500);    // 等 500ms,期间这个线程回线程池干别的
Thread.Sleep(500);        // 这个线程焊死 500ms,什么都干不了
  • Task.Delay(ms, token) 带取消令牌:外部 Cancel() 时它立刻抛 OperationCanceledException,睡到一半也能醒——急停/停止采集能立即生效,靠的就是这个。
  • 易错:写 Task.Delay(500); 忘了 await → 编译警告 CS4014,这一行等于没写(根本没等)。

4. 异步循环 —— 全项目的"心跳"骨架

MC1 模拟卡、R5 消费循环、R4 重连循环,全是同一个骨架:

Task.Run(async () =>
{
    try
    {
        for (var i = 1; i <= steps; i++)
        {
            await Task.Delay(_tickMs, cts.Token);   // ① 等一拍(可被取消打断)
            lock (_gate) _positions[axis] = ...;     // ② 推进一步
            PositionChanged?.Invoke(...);            // ③ 广播
        }
    }
    catch (OperationCanceledException) { /* 急停:就地冻结,不当错误 */ }
});

读法口诀:等一拍、走一步、可打断。await Task.Delay 让出线程(几百个这样的循环同时转,也不占几百个线程);token 让急停毫秒级生效;try-catch 把"取消"当成正常路径而不是崩溃。

5. 闭包捕获 —— C# 和 JS 的 var/let 同款坑

for (var i = 0; i < 3; i++)
{
    tasks.Add(Task.Run(() => Console.WriteLine(i)));   // 打印 3 3 3!
}

C# 的 for 循环变量是"整个循环共享一个变量"——行为等同 JS 的 var(MC1 教训:循环里先 var axis = i; 拷一份再进 lambda)。而 foreach 从 C# 5 起每轮是新变量(等同 let)。规则一句话:lambda 要捕获循环变量,先拷一份局部变量。

自测(全对再翻篇)

  1. UI 线程上 Thread.Sleep(2000) 和 await Task.Delay(2000) 各什么表现?
  2. Task.Run(() => throw new Exception()); 不接返回值,异常去哪了?
  3. 急停为什么能"立即"生效?哪个机制?
  4. CS4014 警告什么意思?
  5. for 循环里 Task.Run 捕获 i,为什么全打印 3?怎么修?
答案(先自己答再看)
  1. 前者界面冻结 2 秒(线程被焊死);后者界面流畅,2 秒后继续(线程期间被释放)。
  2. 装在返回的 Task 里,静默吞掉——必须 await 它,或循环体内部自己 try-catch 兜底。
  3. await Task.Delay(ms, token) 的令牌:Cancel() 一调用,Delay 立刻抛 OperationCanceledException,不用等这一拍睡完。
  4. Task 没被 await——最常见就是 Task.Delay 忘 await,那一行等于没写。
  5. for 的循环变量整个循环共享一个(同 JS var),lambda 执行时循环早结束 i=3;修法:循环内 var copy = i; 捕获副本。

三、通信协议

E03 · 串口通信基础:RS232/485、波特率 9600-8-N-1、字节流 🔴

你的原话:"通讯协议这块我都不熟"(一次报点拆三条登记:E03 串口物理层 → E04 Modbus 协议 → E05 粘包半包拆帧,正好是"线 → 协议 → 代码"三层)

一句话总纲:串口 = 两根线 + 双方约好的说话规则——波特率/数据位/校验/停止位是软件参数,RS232/485 是物理形态;它给你的永远是没有消息边界的字节流。

1. 为什么 2026 年了还在用串口

  • 工业设备寿命 20 年起:PLC、变频器、温控仪、电能表,出厂就带 RS485 口
  • 两根线、差分抗干扰、布线便宜,车间环境比以太网皮实
  • 面试常问"为什么不用 TCP":答案不是"串口更好",是"设备端只有串口——上位机是迁就方"。这也是为什么上位机岗位 JD 里"串口/Modbus"出现频率比 TCP 高得多

2. 串口参数 9600-8-N-1 —— 双方必须一字不差

项目实物(R4 ModbusDevice 构造里):

_port = new SerialPort(portName, baud, Parity.None, 8, StopBits.One);
//                                    ↑校验N  ↑数据位8 ↑停止位1;baud 默认 9600
参数 含义 常见值
波特率 Baud 每秒传多少位 9600 / 19200 / 115200
数据位 一个字节实际占几位 8
校验 Parity 附带 1 位奇偶校验 N(None)最常用 / E(偶)
停止位 字节之间的"换气" 1
  • 参数不一致的现象是乱码,不是报错——现场第一坑:收到一堆 FF FF 或无意义字节,先去和设备手册核对 9600-8-N-1(四项全对才算对,校验位最容易被漏掉)。
  • 算力账要会算(面试"报得出数字"的那种数字):9600bps、无校验 → 1 字节 = 1 起始 + 8 数据 + 1 停止 = 10 位 → 960 字节/秒。一条 8 字节 Modbus 请求 ≈ 8.3ms,一来一回 ~17ms → 主站 100ms 轮询一个点位绰绰有余。

3. RS232 vs RS485 —— 打电话 vs 对讲机群频道

RS232 RS485
拓扑 点对点(1 对 1) 总线(一主多从,32+ 台挂同两根线)
双工 全双工(收发各一线,可同时说) 半双工(一对差分线,分时收发)
距离 ~15m ~1200m
信号 单端对地,±3~15V 差分(两线电压差),抗干扰强
在哪见到 电脑 COM 口、USB 转 232 车间设备总线(Modbus 网的物理层)

前端类比:RS232 = 打电话(两人可同时说);RS485 = 对讲机群频道——一次只能一个人按着说话,所以必须有个主持人(主站)点名,被点到才能答。Modbus 一主多从的轮询模型,根子就是 RS485 的半双工:不是协议不想让从站主动上报,是物理层不允许抢话。

  • 半双工的代码级后果:请求写出去必须等响应/超时,不能连发——R4 PollOnce 就是"问一个点位、收完再问下一个"。
  • 电脑怎么连 RS485 设备:一根"USB 转 RS485"转换线,十几块钱,插上驱动出来一个 COM 口,代码里就是普通串口。

4. 串口给你的是字节流,不是"消息"

DataReceived 事件触发时,缓冲区里有多少读多少——可能是半条帧、可能一条半、可能三条粘一起。这个事实是 E05 整篇的出发点。

前端类比(记住这条就够了):串口像 ReadableStream 的 reader.read()——chunk 和消息边界毫无关系;不像 WebSocket 的 onmessage(一条就是一条,框架替你切好了)。前端转上位机最深的惯性,就是以为"收到一次 = 一条报文"。

易错点

  1. 参数不一致 → 乱码不报错;排查第一步永远是核对手册的波特率/校验位。
  2. COM 口被占用(串口调试助手没关)→ 打开串口抛 IOException;现场排查第一步"谁占着口"。
  3. RS485 两根线 A/B 接反 → 收到取反式乱码;对调 A/B 重试是基本操作。
  4. 波特率不是越高越好:线越长、干扰越大,稳定上限越低——手册写多少跑多少。

自测(全对再翻篇)

  1. 9600-8-N-1 四个字段各什么意思?9600bps 一秒大约多少字节,怎么算的?
  2. RS232 和 RS485 各适合什么场景?为什么 Modbus 网络几乎都是 RS485?
  3. 从站为什么不能主动上报?是协议规定还是物理层限制?
  4. 串口参数配错(校验 N 配成 E),现象是什么?
答案(先自己答再看)
  1. 波特率 9600(每秒 9600 位)、8 数据位、无校验、1 停止位;10 位/字节 → 9600÷10 = 960 字节/秒。
  2. RS232 点对点短距(电脑直连一台设备调试);RS485 总线一主多从、长距抗干扰(车间设备网)。Modbus 多从站结构正好用 485 总线承载。
  3. 根子是物理层:RS485 半双工,一对线分时收发,两台同时说就冲突——只能主站点名,协议顺势定成一问一答。
  4. 乱码(读到的字节无意义),不报错。

E04 · Modbus RTU:帧结构 / 功能码 / 40001 坑 / 字节序 / CRC 🔴

你的原话:"通讯协议这块我都不熟"(同 E03,拆分登记)

一句话总纲:Modbus RTU = 主站发问、从站应答的寄存器读写协议——读请求帧 8 字节可背、常用功能码就 3 个、CRC 收尾;两大高频坑:40001 是给人看的地址(进帧要减 1)、同一帧里 CRC 小端而数据大端。

1. Modbus 是什么(面试家谱)

1979 年 Modicon(现施耐德)为 PLC 通信设计,40 年不衰 = 免费公开 + 简单 + 够用。三个变种:

变种 载体 帧特点
RTU 串口(RS485 居多) 二进制紧凑帧,CRC16 收尾 —— 项目手搓的就是它
ASCII 串口 每字节转 2 个字符(0x01→"01"),LRC 校验,肉眼可读但慢一倍
TCP 以太网 MBAP 头 7 字节(含事务标识),无 CRC(TCP 自带校验和)

前端类比:主从模型 = HTTP 请求-响应,不是 WebSocket 推送。主站(上位机)是浏览器,从站(PLC/仪表)是一堆被动服务器;区别是 Modbus 从站永不主动开口(原因见 E03 半双工)。

2. 寄存器模型 —— 协议眼里只有四块内存

区 名字 宽度 读写 像什么 常用功能码
0x 线圈 Coil 1 bit 读写 开关量输出(继电器、启动位) 01 读 / 05 写
1x 离散输入 1 bit 只读 开关量输入(限位、按钮) 02 读
3x 输入寄存器 16 bit 只读 模拟量测量值(温度读数) 04 读
4x 保持寄存器 16 bit 读写 设定值/参数(温度设定) 03 读 / 06 写 / 10 写多

前端类比:一块远程 Redux store——外部只能通过固定 API 读写四个分区。项目只用了 03/06 两个(R4 PollOnce 读、WriteRegister 写),已覆盖采集+下发设定值的绝大多数现场需求——这也是"手搓不用库"的底气:常用的就这一小角。

3. 帧结构 —— 8 字节手工可背

项目实物(R3 BuildReadHoldingRequest 注释原话:[从站][0x03][地址2B大端][数量2B大端][CRC低前]):

01    03      00 00     00 02      84 0A
从站  功能码  起始地址   数量        CRC(低字节在前)
  • 抓包工具里看到 01 03 00 00 开头 = "1 号从站,读保持寄存器,从地址 0 开始"。
  • R3 测试用的经典向量:01 03 00 00 00 01 → CRC 值 0x0A84,线上低字节在前即 84 0A。
  • 响应帧(R3 ParseReadRegisters 的布局):[从站][0x03][字节数 N*2][数据 N*2 字节大端][CRC]——第三字节是"自带说明书",声明后面有几个数据字节;解析时不按它核对长度,就是给半包开门(截断帧→下标越界/读到垃圾)。

4. 异常响应 —— 功能码最高位置 1

从站拒绝时回 [从站][功能码|0x80][异常码]。例如 01 83 02:读 03 → 83(最高位置 1),异常码 02 = 非法数据地址。

异常码 意思 你最常撞见的场景
01 非法功能 设备不支持该功能码
02 非法数据地址 忘了减 40001(见下)
03 非法数据值 写入值超范围
04 从站故障 设备自身故障

项目实物:IsExceptionResponse——一个 & 0x80 就把"数据还是错误"分流,不用解析完才知道坏了(协议把"报错"设计成一个 bit,是给收方的快捷键)。

5. 40001 坑 —— 手册地址 ≠ 协议地址(现场坑 No.1)

手册写"温度在 40001":4 是区块号(保持寄存器),001 是第 1 个 → 协议帧里地址字段填 0x0000:

40001 → 0x0000     40002 → 0x0001     40108 → 0x006B(= 108 − 1)
30001 → 0x0000(输入寄存器区,功能码换 04)

R4 🏗️ 块里的真实案例:设备返回 0x02 异常码,对着手册查到"寄存器偏移没减 40001"——10 分钟定位 vs 半天猜。手搓全链路白盒的价值就在这(用库只能看到"读取失败")。

6. 字节序 —— 同一帧里两种端并存(最阴的坑)

  • 数据区大端(高字节在前):寄存器值 0x1234 → 线上 12 34
  • CRC 小端(低字节在前):CRC 值 0x0A84 → 线上 84 0A
  • float 跨 2 个寄存器,字序厂商各定:Modbus 只有 16 位寄存器,float 是厂商约定拆两个存,高低字谁在前没有标准——R4 RegisterMap 专门有 floatWordSwap 字段、ToFloatModbus 按序拼回,就是这个原因。

现场口诀:寄存器值拼出来不对,先怀疑字节序,再怀疑地址,最后怀疑人生。

7. CRC16 —— 为什么不是累加和

  • 参数是规范写死的:多项式 0xA001(反射)、初值 0xFFFF——R3 Crc16.Modbus 15 行手写 + 已知向量测试。
  • 累加和抓不住换序错误(A+B = B+A),CRC 的指纹特性保证任意 1 位翻转必然改变结果——车间干扰是连发位翻转,这是 Modbus 40 年选它的原因(R3 🏗️ 块)。
  • 算 CRC 时别把 CRC 自己算进去:算的是它前面那段载荷。

易错点

  1. 40001/30001 是人读格式,进帧要 −1;返回异常码 02 先想这个。
  2. CRC 低前 + 数据大端,同一帧并存——拼字节时两套规则各自记牢。
  3. float 拼出来离谱,先换 wordSwap 试,再查地址。
  4. 半双工:发完请求等响应(带超时),别连发;广播地址 0 的写请求没有响应。
  5. RTU 没有帧头字符,官方靠 3.5 字符静默期分帧(见 E05 方案 D)——主站一问一答模式可以绕开,但要知道有这回事。

自测(全对再翻篇)

  1. 默写"1 号从站,从地址 0x0000 读 2 个保持寄存器"的完整请求帧(含 CRC 的字节顺序)。
  2. 手册写 40108,帧里地址字段填多少?用什么功能码?
  3. 响应 01 83 02 什么意思?从哪个字节看出是异常?
  4. "CRC 低字节在前"和"数据大端"矛盾吗?各自指帧里哪部分?
  5. 温度 float 存 40001-40002,读出两个寄存器拼的值离谱,排查顺序?
  6. 为什么 Modbus 从站不能主动上报?
答案(先自己答再看)
  1. 01 03 00 00 00 02 + CRC(低字节在前);单寄存器经典向量 CRC=0x0A84 → 线上 84 0A(读 2 个的 CRC 值现场可由工具算,格式同为低前)。
  2. 40108 − 40001 = 107 = 0x006B;保持寄存器 → 功能码 0x03。
  3. 1 号从站、异常响应、非法数据地址;第二个字节 0x83 = 0x03|0x80,功能码最高位被置 1。
  4. 不矛盾,是规范规定的两套规则:CRC 字段低字节在前;数据区(寄存器值/地址/数量)高字节在前。
  5. 先换 float 字序(wordSwap)→ 再核对地址是否忘了减 40001 → 再核数据类型(是不是 word 不是 float)。
  6. 物理层 RS485 半双工,同时说话会冲突;协议顺势定成一问一答的轮询。

E05 · 粘包/半包:流式拆帧(蓄水池 Feed / TryTakeFrame)🔴

你的原话:"通讯协议这块我都不熟"(同 E03,拆分登记)

一句话总纲:串口/TCP 给的都是没有消息边界的字节流,拆帧必须做成流式蓄水池——Feed 进货、TryTakeFrame 循环切;半包等下批、粘包多切几条、垃圾头丢字节重找。

1. 半包/粘包是什么,为什么必然发生

  • 半包:一条报文分两次到达(先 5 字节、后 6 字节)
  • 粘包:两条(或多条)报文一次到达
  • 为什么必然发生:到达节奏由波特率/驱动缓冲/网络调度决定,和协议帧毫无对齐关系;发送端 write 一次 ≠ 接收端收一次(TCP 侧 Nagle 还会合并小包,加剧粘包)。这不是实现 bug,是字节流的本性。

前端类比(最贴的一次):fetch 流式读 ReadableStream——reader.read() 给的 chunk 和 JSON 消息边界无关,要自己按长度/分隔符切;WebSocket 的 onmessage 是少数自带消息边界的(框架替你切好了)。前端转上位机最深的惯性就是"收到一次 = 一条报文"——串口/TCP 上这个假设直接错。

2. 流没有边界 → 协议必须自带(帧格式设计四方案)

方案 做法 谁在用 短板
A 帧头+长度 AA 55 + 长度 + payload + CRC 项目 TCP 帧 / 绝大多数自定义协议 数据里出现 AA55 要靠"删 1 字节重找"容错
B 定长 固定 N 字节一帧 简单遥测 浪费、不灵活
C 分隔符 以 \r\n 结尾 AT 命令、Redis 协议 payload 含分隔符要转义
D 静默期 靠时间间隔分帧 Modbus RTU 官方(3.5 字符静默 t3.5) 要超时计时,高波特率有下限
  • HTTP/1.1 的 Content-Length、HTTP/2 的帧头(长度+类型),和方案 A 是同一道题——"在字节流上定义消息边界"是所有应用层协议的第一题。
  • Modbus RTU 没有帧头字符,官方靠 t3.5 静默期分帧(9600bps 下 ≈3.65ms 无数据即认为帧结束);但主站请求-响应模式可以绕开它:问了几个寄存器,响应多长是算得出的——按期望长度+第三字节字节数核对即可(项目 ParseReadRegisters 走的这条路)。

3. 蓄水池实现(项目实物 R3 FrameParser)

Feed(chunk):
    _buffer 追加 chunk             // 进货:字节全倒进池子
    while (TryTakeFrame(out f))    // 取货:能切几条切几条(粘包在此拆开)
        上层处理 f                 // 一条都切不动(半包)→ while 不进,字节安静等下批

TryTakeFrame 四条 return = 四种现场情况:
    ① 池里找不到帧头      → 清池(纯垃圾)
    ② 长度字段还没到齐    → false,等下一批(半包截在长度字段)
    ③ 长度超上限(假帧头) → 删 1 字节,重新找头(AA 恰好出现在数据里)
    ④ 帧身没到齐          → false,等下一批(半包截在帧身)
  • 为什么是 class 不是 static:缓冲要跨调用记忆——有状态就有实例(前端同款:有内部 state 的是组件实例,纯输入→输出的写工具函数;所以 Crc16 才是 static)。
  • 读协议代码先数 return 路径:每条 return = 流式解析的一种现场情况。面试让你讲半包粘包,把这 4 条讲全就是满分答案(R3 知识点原话)。

4. 两个防御细节

  • payload 上限(项目 8KB):垃圾长度字段 FF FF 会触发巨分配——上限防"乱码长度导致巨型缓冲"拖垮内存。
  • 拆不出帧要清池:缓冲永远拆不出完整帧时清空,防内存只进不出(R3 注释里写明的)。

易错点

  1. 把 DataReceived / TCP read 当"一条报文"→ 测试环境(整帧喂入)全绿,现场随机丢数据——最难排查的 bug 类(R3 🏗️ 块原话)。
  2. 忘了长度字段本身也可能被截断:半包可能正好断在帧头和长度字段中间。
  3. 假帧头清池会误杀真帧(数据里合法出现 AA55)→ 删 1 字节重找才对。
  4. 缓冲只进不出 → 内存慢慢涨;必须有清空策略。

自测(全对再翻篇)

  1. 半包、粘包各是什么?为什么必然发生(不是实现 bug)?
  2. 字节流没有边界,协议靠什么分帧?四种方案各举一个使用者。
  3. TryTakeFrame 四条 return 各对应什么现场情况?
  4. 假帧头为什么删 1 字节重找,而不是清空缓冲?
  5. 为什么 payload 要设上限?
  6. Modbus RTU 没有帧头,官方怎么分帧?我们的主站模式怎么绕开它?
答案(先自己答再看)
  1. 半包 = 一条报文分多次到达;粘包 = 多条报文一次到达。字节流的到达节奏由物理层/缓冲决定,与协议帧无对齐关系——是流的本性,只能靠解析层处理。
  2. 帧头+长度(项目 TCP 帧/自定义协议)、定长(简单遥测)、分隔符(AT 命令/Redis)、静默期(Modbus RTU t3.5)。
  3. 找不到帧头(垃圾,清池)/ 长度字段未到齐(半包,等)/ 假帧头长度超限(删 1 字节重找)/ 帧身未到齐(半包,等)。
  4. 清池会连后面可能存在的真帧一起丢;删 1 字节只跳过假帧头本身,后面字节仍有机会对齐出真帧。
  5. 防乱码长度字段(如 FF FF)触发巨型分配,拖垮内存。
  6. 官方靠 3.5 字符静默期;主站一问一答模式下,响应长度可由请求推算,按期望长度+响应里的字节数核对即可。
