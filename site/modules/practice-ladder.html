练习阶梯 · 从"简单操作"到"能跑的企业级项目"

你提的要求我们记住了：练习从最简单的做起（命名、建工程、跑命令），最后一定要汇成一个能正常跑起来的企业级项目。 所以每个模块都分三级，难度递增；所有模块的终点，是同一个能 dotnet run 起来的 DAQ Monitor。

怎么用这份阶梯

级别 含义 类比前端
L1 操作练习 只动手指：命名、建文件、跑命令、改配置 学会 npm init、建目录
L2 代码练习 写小块代码，配 ✅ 答案，照着改会 写一个组件 / 一个函数
L3 项目任务 把能力集成进 DAQMonitor，让它多一层企业级本事 把组件塞进真实项目并跑通

铁律：L1 不会就不碰 L2，L2 没做对就不做 L3。 企业项目不是背出来的，是一步一步"跑绿"跑出来的。

总验收（学完所有模块要达到）

打开 DAQMonitor/，依次执行，全部必须过：

dotnet build      # ✅ 0 错误 0 警告
dotnet test       # ✅ 28 测试全绿（含无界面集成冒烟测试 + CAN/USB/心跳监测）
dotnet run --project src/DaqMonitor.UI
                  # ✅ 弹出窗口，点"启动采集"→ 点位表跳动、偶发报警进日志

能同时做到这三条，说明你手里是一个真实能跑的企业级上位机项目，不是 demo 截图。

M0 · 脚手架与 C# 核心（地基）

  • L1：用 实操入门 第 2 节命令从零建出 Core/UI/Tests 三层；跑通 dotnet build。
  • L2：在 Core 写一个 struct SensorPoint { int Id; double Value; }，用 record 改写并对比（✅ record 自带相等比较与不可变）。
  • L3：把 DaqMonitor.Core 的 Models/SensorPoint.cs 跑通（已就绪），dotnet test 中 PointStoreTests 绿。

M1 · 串口通信

  • L1：dotnet add package System.IO.Ports 装官方串口库；在 appsettings 里写一个串口号配置（COM3, 9600）。
  • L2：写一个 FrameParser（半包/粘包处理），跑 FrameParserTests 绿。
  • L3：新增 SerialDevice : DeviceBase，把 RaiseData 接到串口收到的一帧上，注册进 Bootstrapper 替换 SimulatedDevice。

M2 · Modbus RTU/TCP

  • L1：dotnet add package NModbus；新建 DaqMonitor.Modbus 类库并 dotnet sln add + reference Core。
  • L2：用 NModbus 读一个保持寄存器，断言返回值类型正确。
  • L3：ModbusDevice : DeviceBase 实现 Read/Write，接管道；Bootstrapper 里按配置二选一。

M3 · PLC 通信（西门子 S7）

  • L1：dotnet add package S7.Net；新建 DaqMonitor.Plc 类库。
  • L2：连接 PLC 读 DB 块一个浮点，断言非空。
  • L3：PlcDevice : DeviceBase 接入管道，与串口/Modbus 并存的"多设备采集"达标。

M4 · 数据持久化（EF Core + SQLite）

  • L1：dotnet add package Microsoft.EntityFrameworkCore.Sqlite；新建 DaqMonitor.Persistence 类库。
  • L2：建 PointRecord 实体 + DbContext，EnsureCreated 后 Add 一条并 SaveChanges，再查回来。
  • L3：订阅 AcquisitionPipeline.BatchReady，把每批落库；加"历史查询/导出 CSV"按钮到 UI。

M5 · 实时可视化（LiveCharts）

  • L1：dotnet add package LiveChartsCore.SkiaSharpView.WPF；XAML 放一个 CartesianChart。
  • L2：用 ObservableCollection<ObservablePoint> 画一条会动的曲线（限长 200 点防内存涨）。
  • L3：把 MainWindow 的 DataGrid 旁加一张实时曲线；必须用 M9 的统一批量刷新，禁止逐点 Dispatcher.Invoke。

M6 · 报警引擎 + 规则 + 日志

  • L1：在 AlarmRule 加一条配置；dotnet test 跑 AlarmEngineTests 绿（边沿触发 + 回滞）。
  • L2：用 Serilog 把报警写文件（dotnet add package Serilog.Sinks.File）。
  • L3：UI 报警日志同时进文件；做"确认报警/静音"交互。

M7 · OPC UA / MQTT 上云

  • L1：dotnet add package MQTTnet；新建 DaqMonitor.Cloud 类库。
  • L2：连本地/公共 MQTT Broker，发布一条 JSON 点位。
  • L3：订阅 BatchReady 批量发布到 factory/line1/points 主题（同 M9 架构，禁止逐点 PublishAsync）；断线自动重连。

M8 · 工程化收尾（MVVM + 安装包 + 简历）

  • L1：装 CommunityToolkit.Mvvm，把 MainViewModel 的 OnPropertyChanged 手工代码换成 [ObservableProperty]/[RelayCommand]。
  • L2：抽 IAlarmService 接口，用 Moq 在测试里替换，证明界面与实现解耦。
  • L3：dotnet publish -c Release 出安装包/单文件；写 README.md + 简历描述（能讲清"为什么这么分层、为什么用管道+批量"）。

M9 · 工程素养（测试 / DI / 统一采集 / 容错）★ 串联所有模块

  • L1：dotnet test 看 DaqMonitor.Tests 里 28 个测试分别在测什么；运行 CompositionSmokeTests 理解"无界面也能证明项目能跑"。
  • L2：读 Core/AppServices/Bootstrapper.cs，画出"设备→管道→存储/报警→UI"的依赖图；给 Retry 写一个指数退避的单测。
  • L3：给 M1–M7 每加一个真实设备/能力，都补一个对应单元测试，让总测试数持续增长——这就是"企业项目越做越稳"的真功夫。

✏️ 通用小练习（每天打卡前做）

  1. 命名自检：新加的类/工程是不是 DaqMonitor.职责？测试是不是 .Tests？
  2. 命令自检：今天改完能不能 dotnet build 0 错误？dotnet test 全绿？
  3. 架构自检：我新写的代码有没有"穿透分层"（UI 直接 new 了 Core 的实现类）？有就改成从 Bootstrapper 取。

🏗️ 终极项目任务：学完 M0–M9，你的 DAQMonitor 应当同时具备—— 多设备接入（串口/Modbus/PLC 至少两种）· 并发采集无卡顿 · 实时曲线 · 历史库+导出 · 报警+日志 · 上云 · 分层+DI+MVVM+测试+能打包。 这就是简历上那个"13K~15K 企业级上位机项目"，而且是真能跑的。

✅ 自测脚本（每个模块做完都跑一遍）

# 1. 编译:期望 0 错误 0 警告(有警告不算达标 — 警告就是没爆的 bug)
dotnet build

# 2. 测试:期望全绿(项目做完应该 28+ 测试)
dotnet test

# 3. 运行:期望窗口能开、点"启动采集"数据跳、报警进日志
dotnet run --project src/DaqMonitor.UI

三条全绿 = 这一模块达标;有任意一条红,先把红消了再进下一模块,不要带病推进。 L3 项目任务的额外自测:打开 Bootstrapper.cs,确认你新加的设备/服务真的在 ConfigureServices 里注册了 — 没注册 = 等于没写。
