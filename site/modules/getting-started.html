实操入门 · 从零搭建企业级工程（给前端转上位机、零 .NET 基础）

你问"做练习要从做简单的做起，比如项目文件夹名称、如何创建等等操作"。 这页就是最简单、最先要会的东西：怎么起名字、怎么用命令行把一个工程从空文件夹敲出来、怎么确认它能跑。 学完这一页，你能在 10 分钟内从零还原出 DAQMonitor 的骨架。

0. 先建立心智模型（前端类比）

前端世界 .NET 上位机世界 一句话
npm / pnpm dotnet CLI 包管理 + 脚手架 + 构建都在一个命令里
package.json .csproj 工程描述文件（依赖、目标框架、输出类型）
node_modules/ bin/ + obj/ 编译产物，不要手改、不要提交 git
一个 src/ 目录装所有代码 一个 .sln 解决方桉 + 多个 .csproj 子工程 上位机讲究分层（Core / UI / Tests 各管各的）
npm run dev dotnet run 启动应用

1. 文件夹怎么命名（你最关心的"项目文件夹名称"）

企业级工程不是"随便建个文件夹塞代码"。命名守三条规定：

1.1 三条铁律

规则 说明 反例（别这样）
① 用英文 + PascalCase 类名/工程名首字母大写驼峰，见名知意 daqmonitor / 数据采集 / myApp
② 不用空格、不用中文做代码工程名 中文文件夹能建，但命令行、CI、NuGet 包名容易出幺蛾子 上位机项目/ 当解决方案名
③ 分层用子目录 src/ 下每个可独立编译的单位一个文件夹 所有 .cs 平铺在一个目录

💡 本项目的真实约定（你就照这个来）： F:\00_project\上位机学习\ ← 资料根目录（中文没关系，只是放资料） DAQMonitor\ ← 解决方案根（英文，正经工程名） DaqMonitor.sln ← 解决方案文件（统领下面所有子工程） src\ DaqMonitor.Core\ ← 核心层：领域模型/设备接口/管道/报警/协议 DaqMonitor.UI\ ← 界面层：WPF 主窗口 DaqMonitor.Tests\ ← 测试层：xUnit 单元测试 命名规律：DaqMonitor. + 层名，和命名空间（namespace）一一对应。

1.2 为什么这么分？（企业真实项目的理由）

  • Core 不依赖 UI：好处是——没有界面的服务器/服务/测试也能直接用 Core。你的报警引擎、采集管道在后台服务里照样跑。
  • Tests 只依赖 Core：测试不碰界面，跑得快、能上 CI（GitHub Actions / Jenkins 自动跑）。
  • UI 依赖 Core：界面是"壳"，换 WPF→Blazor→控制台都不影响核心逻辑。

这就是面试时能讲清楚的"分层架构 / 依赖方向单一"——13K 与 8K 的分水岭之一。

2. 从空文件夹，用命令行一步步建出来（照抄即可）

打开终端（PowerShell / CMD / Git Bash 都行），进到你想放工程的地方：

# ① 建解决方案根目录并进入
mkdir DAQMonitor && cd DAQMonitor

# ② 建解决方案文件（.sln 是把子工程"捆"在一起的清单）
dotnet new sln -n DaqMonitor

# ③ 建三个子工程（classlib=类库, wpf=WPF 界面, xunit=测试）
dotnet new classlib -o src/DaqMonitor.Core -n DaqMonitor.Core
dotnet new wpf      -o src/DaqMonitor.UI   -n DaqMonitor.UI
dotnet new xunit    -o src/DaqMonitor.Tests -n DaqMonitor.Tests

# ④ 把子工程"挂"到解决方案里
dotnet sln add src/DaqMonitor.Core/DaqMonitor.Core.csproj
dotnet sln add src/DaqMonitor.UI/DaqMonitor.UI.csproj
dotnet sln add src/DaqMonitor.Tests/DaqMonitor.Tests.csproj

# ⑤ 建依赖方向：UI 依赖 Core，Tests 依赖 Core（Core 谁都不依赖）
dotnet add src/DaqMonitor.UI/DaqMonitor.UI.csproj    reference src/DaqMonitor.Core/DaqMonitor.Core.csproj
dotnet add src/DaqMonitor.Tests/DaqMonitor.Tests.csproj reference src/DaqMonitor.Core/DaqMonitor.Core.csproj

🟩 以上全是 .NET SDK 自带的命令，不需要装任何第三方包。

跑完你会得到和本项目一模一样的骨架。此时你已经完成了"企业级工程的地基"——这比写第一行业务代码都重要。

2.1 想要某个第三方能力？dotnet add package

比如核心层要用依赖注入（Microsoft 官方库，🟧 要装）：

dotnet add src/DaqMonitor.Core/DaqMonitor.Core.csproj package Microsoft.Extensions.DependencyInjection

3. git 初始化 + 忽略编译产物（必做，否则仓库会炸）

git init

新建 .gitignore（直接要 .NET 官方的，别手敲）：

dotnet new gitignore        # 自动生成一份标准 .NET .gitignore

它会忽略 bin/、obj/、*.user 等。不忽略这些，你的 git 仓库会塞满编译垃圾。

提交一次地基：

git add .
git commit -m "chore: 搭建 DAQMonitor 分层骨架(Core/UI/Tests)"

4. 三板斧：build / run / test（每天都会用）

命令 作用 像前端的什么
dotnet build 编译整个解决方案 npm run build
dotnet run --project src/DaqMonitor.UI 启动 WPF 界面 npm run dev
dotnet test 跑全部单元测试 npm test

✅ 验收标准（你学每一步都要能回答）： - dotnet build → 0 错误 0 警告 - dotnet test → 全部绿灯 - dotnet run → 弹出 DAQ Monitor 窗口，点"启动采集"能看到点位跳动 + 偶发报警

⚠️ 本机只装了 .NET 10 运行时，工程目标框架是 net8.0。我们在 .csproj 里加了 <RollForward>Major</RollForward>，让 net8 程序滚动到 net10 运行。这是真实生产常用技巧，不是绕弯子。

5. ✏️ 练习（从最简单的动手）

练习 1（命名）：给下面这些起名，按"英文名 + PascalCase + 分层"规范： - 一个做"Modbus 串口通信"的类库 → ________ - 它的测试工程 → ________ - 一个"历史数据库"层 → ________

✅ 答案 - `DaqMonitor.Modbus`（或 `DaqMonitor.Communication`） - `DaqMonitor.Modbus.Tests` - `DaqMonitor.History`（或 `DaqMonitor.Persistence`） 规律：`DaqMonitor.` + 职责名；测试统一加 `.Tests` 后缀。

练习 2（创建）：在 F:\00_project\上位机学习\ 下，不复制本项目，自己用第 2 节的命令从空文件夹敲出一个 Playground 解决方案（含一个 classlib + 一个 xunit），跑通 dotnet test。

练习 3（验证地基）：打开本项目 DAQMonitor/，依次运行 dotnet build 和 dotnet test，确认 28 个测试全绿。把输出截图/贴到打卡表。
