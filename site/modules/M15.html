M15 — 工程协作与联调（Git + 敏捷 + 硬件调试工具 + 联调定位）⚫

优先级定位：🟢 再学（软技能）· 工程协作与联调（入职自然学，初级岗也要求） 技术来源：🟦 Git / 敏捷（方法论，不装包）；🟩 串口助手/示波器/逻辑分析仪（工具，部分免费）；🟦 C# SerialDevice.RawLog（联调落地，已落工程）。 给简历加的能力：企业招"初级"第一条硬要求往往不是某个协议，而是你能不能在团队里干活——会用 Git、懂敏捷、会用调试工具、能和下位机联调定位问题。这是"能不能交付企业"的门槛。 前端类比总纲：Git 像前端的 git 工作流（分支/PR/冲突）；敏捷像 Scrum 站会；调试工具像 Chrome DevTools 的 Network/Performance 面板——看"信号"而非猜。

⏱️ 阅读路径(按时间预算选入口) - 3 分钟:看「模块目标」— 知道这是"能不能在企业里干活"的软技能 - 30 分钟:加看 Day 1 Git 工作流(rebase vs merge / PR 流程) - 3 小时:全文精读 + Day 2 联调定位(串口助手/示波器/逻辑分析仪) + Day 3 敏捷站会 - 🎯 面试高频:Git rebase vs merge / 联调时怎么定位是上位机错还是设备错 / RawLog 调试法 - 🔁 配套复习:间隔重复表

📚 前置语法(M15 用到的,陌生请查 C# 语法速查 — 前端视角) - git init / git commit -m "..." / git branch feature-x — Git CLI(类似前端 git) - device.RawLog += (s, line) => Console.WriteLine(line) — 调试事件订阅,速查 §7 - [Conditional("RAW_LOG")] — 条件编译(只在 DEBUG 输出 RawLog) - Trace.WriteLine(...) / Debug.WriteLine(...) — 调试输出 - class FrameDumper — 联调辅助类(自封装)

Day 1 — Git 版本管理（初级岗 100% 要求）🟢

一句话讲清楚

Git = 代码的时光机和合并器。3 个人同时改 SerialDevice.cs，没有 Git 后保存的覆盖先保存的；有 Git 每个人的改动分开记录、能合并、能回退、能看出"谁在哪天改了啥、为什么改"。

前端类比秒懂

Git 前端类比
git commit 给代码拍快照，能回退
branch 开一条独立时间线，互不干扰
PR / merge 把功能分支合回主线，Code Review
.gitignore 不跟踪 node_modules/构建产物

分点精讲

① 在你的 DAQMonitor 上动手（先跑起来） 打开终端（/f/00_project/上位机学习/DAQMonitor 目录下）：

# ① 初始化仓库（只需一次）
git init
git add .
git commit -m "init: DAQ Monitor 工程基线"

# ② 以后每次写新功能，先开分支（关键习惯！）
git checkout -b feature/can-device      # 从当前分支切出"功能分支"
# ... 写代码 ...
git add src/DaqMonitor.Core/Devices/CanDevice.cs
git commit -m "feat: 新增 CAN 设备，实现 IDevice"

# ③ 回到主分支合并
git checkout main
git merge feature/can-device

运行后你会看到：git log 里多出一条带作者、时间、说明的提交记录；git status 告诉你哪些文件改了还没存。

② 逐行白话（每个命令在干嘛） | 命令 | 大白话 | |---|---| | git init | 在当前文件夹建一个".git 隐藏仓库"，开始记账 | | git add . | 把当前所有改动暂存（放进"待提交篮"） | | git commit -m "..." | 把篮子里的改动打包存盘，并写一句"这次干了啥" | | git checkout -b xxx | 新建并切换到分支 xxx（分支=一条独立时间线） | | git merge xxx | 把 xxx 分支的改动合并回当前分支 | | git status | 看当前哪些文件改了/暂存了/没跟踪 |

③ 面试/入职必懂的 3 个概念 - 分支(Branch)：不同功能各开一条线，互不干扰；做完再合回 main。避免"大家都在主线上乱改"。 - 冲突(Conflict)：两人改了同一行，Git 不会瞎合并，会标 <<<<<<< 让你人工决定留哪段。 - .gitignore：告诉 Git"这些文件别跟踪"（如 bin/、obj/、.user）。我们的工程应加一个：

bin/
obj/
*.user
.vs/

🟦 语法提醒：bin/、obj/ 是编译产物，每次 build 都会变，跟踪它们只会制造垃圾提交。

⭐ 重点 / 🔥 坑

内容
⭐ 重点 先开分支再写码；commit 信息写"干了啥+为什么"
🔥 坑 把 bin/obj 提交进仓库 → 冲突地狱
🔥 坑 长期不提交、一次提交几万字改动 → 回退困难
🔥 坑 git push 前先 pull 解决冲突，别硬推 -f

🟢 基础题

给 DAQMonitor 加 .gitignore（含上面 4 行），git add 并提交，提交说明写 chore: 加 .gitignore。

🟡 进阶题

新建分支 feature/usbhid，在分支上随便改一行注释并提交；切回 main，git merge feature/usbhid，观察合并结果。

🔴 挑战题

故意制造一次冲突：在 main 和 feature/x 各改 SerialDevice.cs 同一行的不同内容，合并时解决冲突并提交——体会"冲突不可怕，人工决策即可"。

✅ 答案（基础题自检） git log --oneline 能看到这两条提交；git branch 能看到两个分支名。

🏗️ 项目任务：把整个 DAQMonitor 工程用 Git 管理起来，建 main + 至少一个 feature/* 分支，至少有 3 次有意义的提交（对应你加过的设备/控件）。

🎓 工控导师说：我见过最惨的事故——一个学员三个月没提交，硬盘坏了，代码全没。Git 不要等"项目做完"才用，第一天就 git init。提交频率：一个功能点一提交，信息写清"为什么改"，将来回退/查 bug 救命。

💼 职业建议：Git 是初级岗的"一票否决项"——不会 Git 基本拿不到 offer。面试常被现场考 rebase/merge 区别、reset --hard 危险在哪，把这些基础答顺，软技能关直接过。

Day 2 — 敏捷开发流程（团队怎么协作）🟢

一句话讲清楚

传统做法：花 3 个月写需求文档 → 写代码 → 交付，结果客户说"我要的不是这个"。敏捷做法：把大项目切成 2 周一个迭代(Sprint)，每个迭代都交付一个能跑的小功能，客户尽早看到、尽早改方向。

前端类比秒懂

敏捷概念 前端类比
迭代 Sprint 一个开发周期（2 周）
用户故事 一个需求卡（As a ... I want ... so that ...）
看板 Trello/飞书 任务板
站会 每日 10 分钟同步进度

分点精讲

① 上位机团队里你每天/每迭代会碰到什么 | 概念 | 上位机场景举例 | |---|---| | 用户故事(User Story) | "作为工艺员，我想在历史曲线上框选时间段导出 Excel" → 这就是 M10 的一个故事 | | 看板(Kanban) | 任务卡在「待办→进行中→测试→完成」四列流动；你手上的卡别超过 2 张 | | 每日站会(Daily) | 早上 10 分钟：昨天做了啥、今天做啥、有啥卡住（卡住=联调不通、设备不回数据等） | | 迭代评审 | 每 2 周给客户/主管演示这轮做的采集+报警，当场收反馈 | | 燃尽图 | 横轴时间、纵轴剩余任务量，理想是一条下坡线；一直平=进度危险 |

② 对你的直接用处 - 面试：被问"了解敏捷吗"——能讲出"迭代/看板/站会/用户故事"，比背定义强。 - 入职：主管丢给你一个用户故事卡，你知道把它从待办推到完成，并在站会报进度。 - 自学本项目：把 DAQ Monitor 的 M0–M10 当成 10 个用户故事，每个做完"演示给自己看"，就是微型敏捷。

⭐ 重点 / 🔥 坑

内容
⭐ 重点 用户故事 = "角色+想要+价值"，不是技术任务
🔥 坑 把敏捷当"每天开会"——核心是"小步快跑+尽早反馈"
🔥 坑 看板卡堆积不流动 = 进度红灯

🟢 基础题

把 DAQ Monitor 的"实时曲线(M5)"写成一张用户故事卡：作为操作员，我想看温度实时曲线，以便发现异常趋势。

🟡 进阶题

把上面故事拆成 3 个任务（建 VM / 接 Channel / 绑 LiveCharts），画一个 4 列看板（文字即可），把任务从「待办」推到「完成」，标注每个任务对应哪个模块。

🔴 挑战题

给你一个真实需求"操作员要能导出昨天下午 2–4 点温度 CSV"，拆成用户故事 + 任务卡 + 估算（用"故事点"而非小时），并写一次"站会汇报"的口播稿。

✅ 答案（基础题示范） 作为操作员，我想看温度实时曲线，以便发现异常趋势（角色=操作员，想要=实时曲线，价值=发现异常）。

🏗️ 项目任务：把你正在做的 DAQ Monitor 各模块当成用户故事，用看板管理自己的学习进度——这本身就是"工程化素养"的软技能落地。

🎓 工控导师说：别把敏捷当形式主义。它的精华就一句："别憋大招，小步交付、尽早让客户看到、错了早改"。我管项目时，凡是"闷头写三个月一次性交付"的，十有八九返工；"两周一演示"的，方向永远偏不了多远。

💼 职业建议：面试被问"敏捷了解吗"，千万别只说"知道"。讲一个你怎么用（哪怕是自学项目用看板管进度），比背定义强十倍——这证明你"真在团队语境里工作过"。

Day 3 — 硬件调试工具（示波器 / 逻辑分析仪 / 协议分析仪 / 串口助手）🟡

一句话讲清楚

苏州初级 JD 原句："熟悉示波器或逻辑分析仪基本使用"。这是"硬件知识"的门槛，不要求你会设计电路，但要知道怎么用工具看信号、抓数据。

分点精讲

① 四件套分别看什么 | 工具 | 看什么 | 上位机里什么场景用 | |---|---|---| | 串口助手（如 SSCOM、友善串口助手、Putty） | 串口收发的原始字节 | M1 联调：发 01 03 00 00 00 01 看设备回啥；验证 CRC | | 示波器 | 电信号的电压随时间波形 | 看 RS485 的 A/B 差分波形、波特率对不对、有没有干扰毛刺 | | 逻辑分析仪（如 Saleae、DSLogic） | 多路数字信号的高低电平时序 | 抓 SPI/I2C/CAN/串口 的时序，看波特率、起始位、帧间隔 | | 协议分析仪（如 CANalyst、Bus Hound） | 把原始波形解码成协议报文 | M16 的 CAN：直接看到 ID=0x100, DLC=8, 数据=... 而不是波形 |

② 串口助手实战（你现在就能用虚拟串口练）

【操作】
1. 用 com0com 建一对虚拟串口 COM3↔COM4
2. 打开两个 SSCOM 窗口，分别连 COM3 和 COM4
3. COM3 发 01 03 00 00 00 01 CRC  →  COM4 收到同样的字节
4. 把 M1 的 SerialDevice 连 COM3，用另一个窗口当"假设备"回数据

这就是没有真实硬件时的联调替身——你之前学的"硬件替代方案"里 T2 层就是这个。

③ 示波器/逻辑分析仪能帮你定位的典型问题 - 波特率不对：波形每个 bit 太宽/太窄 → 设备实际 9600 你配了 19200，收到的全是乱码。 - 没共地：RS485 收不到 → A/B 电压差接近 0，示波器上看不到摆幅。 - 半双工冲突：你发的时候设备也在发，逻辑分析仪看到两根线同时拉高 → 总线打架。

🔬 掰开揉碎：为什么"看波形"比"猜"快 100 倍

代码里 Read 返回乱码，你改波特率试了 5 种还是乱——这时示波器一看，bit 宽度明显是 19200 的节奏，你配的却是 9600，一秒定位。调试的本质是"把看不见的信号变成看得见的波形/报文"，工具就是你的眼睛。

⭐ 重点 / 🔥 坑

内容
⭐ 重点 串口助手先手动连、能收发再上代码
🔥 坑 没共地导致 RS485 收不到（示波器看 A/B 摆幅）
🔥 坑 逻辑分析仪采样率不够，抓不到高频信号

🟢 基础题

用 com0com 建虚拟串口，开两个串口助手互发 A1 B2 C3，确认能收到（记录现象）。

🟡 进阶题

列出"设备不回数据"时，你会先用哪个工具、看什么？（答案参考 Day 4 排查清单）

🔴 挑战题

描述一个"用逻辑分析仪定位 RS485 半双工冲突"的实验步骤：怎么接线、抓哪两根线、看到什么现象说明总线打架。

✅ 答案（基础题） COM3 发 A1 B2 C3，COM4 窗口收到完全相同的字节，证明虚拟串口链路通——这就是 M1 联调的"外部眼睛"。

🏗️ 项目任务：装好 com0com + 一个串口助手，用虚拟串口把 M1 的 SerialDevice 和"假设备窗口"连起来跑通一次联调（零硬件）。

🎓 工控导师说：新手联调最爱"改代码试"，老手联调先"拿工具看"。我一上来就甩示波器/逻辑分析仪，5 分钟定位的问题，新手能瞎改一天。工具不贵（Saleae 几百块）、学习成本低，但它是你从"会写代码"到"能解决现场问题"的分水岭。

💼 职业建议：JD 点名"示波器/逻辑分析仪"不是要你当硬件工程师，而是要你"会用工具看信号、定位通信问题"。面试被问"设备不回数据你怎么查"，答出"先串口助手手动连、再示波器看波形/逻辑分析仪看时序"就是满分。

Day 4 — 联调定位：上位机 ↔ 下位机"万能排查清单"🔴

一句话讲清楚

真实项目里 80% 的时间花在"为什么设备不回数据 / 数据不对"。这一节给你一张可照做的清单，而不是靠玄学。

分点精讲

① 排查顺序（从软件到硬件，从近到远）

① 物理层：线接了吗？串口是 COM3 还是 COM4？USB 驱动装了没？
   → 看设备管理器有没有黄色感叹号
② 参数层：波特率/数据位/停止位/校验 和设备的说明书一致吗？
   → 串口助手先手动连，能发能收再上代码
③ 协议层：你发的帧格式对吗？功能码/地址/CRC 对吗？
   → 逻辑分析仪/协议分析仪抓一帧，逐字节核对 M2 的帧结构
④ 代码层：Write 之后等待时间够吗？ReadTimeout 设了吗？DataReceived 跨线程更新 UI 了吗？
   → 加日志（M6 的 Serilog）打印"发出去的是 XX，收到的是 YY"
⑤ 业务层：数值解析对吗？(hi<<8)|lo？大小端？工程量标定公式对吗？
   → 拿一个已知值（如 25.0℃）反向验证

② 把清单变成你项目的"调试开关"（已落地） DAQMonitor 的 SerialDevice 已加 RawLog 开关（接 M6 日志升级）：

// 在 SerialDevice 收发处
if (_rawLog) _logger.Debug("TX {Bytes}", Convert.ToHexString(buffer));
var rx = _port.ReadExisting();
if (_rawLog) _logger.Debug("RX {Bytes}", Convert.ToHexString(Encoding.ASCII.GetBytes(rx)));

运行后你会看到：日志里清清楚楚"我发了啥、收到了啥"，联调时一眼定位是发错还是收错。

③ 真实联调案例（讲透一个）

现象：上位机读温度，一直显示 0。 按清单走： - ① 线接了，COM 对 → 过 - ② 串口助手手动发 01 03 00 00 00 01 XX XX，设备回了 01 03 02 00 FA ... → 参数层过 - ③ 抓帧：回的 00 FA = 250，说明协议层对 → 过 - ④ 代码日志：发出去的对、收到的对 → 过 - ⑤ 业务层 bug：代码写成了 value = hi | lo（没左移 8 位），250 当成了 0x00 | 0xFA = 250 看似对，但另一点位是 hi<<8|lo 忘了 → 修正为 (hi<<8)|lo 后正常。 结论：问题在"字节拼数值"，不在通信。

🔬 掰开揉碎：RawLog 为什么是联调神器

没有日志时，你只能"猜"是发错了还是收错了；加了 RawLog，收发字节直接打印，问题立刻二分：发的不对→协议层；收的不对→设备/链路；收发都对但值错→业务层(字节拼值/标定)。一张日志顶你半天瞎改。

⭐ 重点 / 🔥 坑

内容
⭐ 重点 排查顺序：物理→参数→协议→代码→业务，从近到远
⭐ 重点 先串口助手手动通，再上代码
🔥 坑 跳过物理层直接改代码，结果线根本没插
🔥 坑 只信"代码逻辑对"，不拿已知值反向验证业务层

🟢 基础题

在 DAQMonitor 的 SerialDevice 加 RawLog 开关 + 打印收发字节（接 M6，已实现并配单测 RawLog_Fires_OnSendAndReceive）。

[Fact] public void RawLog_Fires_OnSendAndReceive()
{
    var logs = new List<string>();
    var dev = new SerialDevice(1, "T", new LoopbackSerialChannel(), logs.Add);

    Assert.Contains(logs, l => l.StartsWith("TX"));
