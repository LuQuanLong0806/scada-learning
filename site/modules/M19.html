M19 — 问题排查与调试（深度版）🔧

优先级定位：🔴 必学 · 工业现场 80% 时间在调试不是写新代码（13→15K 硬要求，面试必问"遇到过什么难 bug，怎么排查"） 技术来源：🟦 VS 调试器（条件断点 / 数据断点 / 调用栈 / Threads / Parallel Stacks / IntelliTrace）、🟧 dotnet 全局工具（dotnet dump / dotnet counters / dotnet trace / dotnet gcdump）、🟧 Wireshark + 串口监视器 + Modbus Poll、🟧 PerfView / dotMemory、🟦 Serilog（结构化日志 + TraceId 关联）。 前端类比总纲：前端有 Chrome DevTools 五件套（Elements / Console / Sources / Network / Memory），上位机这一套全是新东西——VS 调试器是 Sources 面板的超集，dotnet dump 是 Memory 快照的命令行版，Wireshark 是 Network 面板的物理层版，Serilog 是 Sentry 的本地版。前端的调试直觉 60% 能迁移，剩下 40% 是多线程 + 内存 + 协议三座大山，本模块就是翻这三座山。 给简历加的能力：能在面试讲出真实排过的三种难 bug —— "7×24 跑 3 天后内存从 100MB 涨到 1GB"、"现场设备偶发性掉线 30 秒自动恢复"、"UI 偶发卡顿 200ms"——并讲清用了什么工具、怎么定位、怎么修。这三句话顶得过你写十个 CRUD 模块。 前置：M0（多线程基础，Threads 窗口要看懂）、M9（DI 容器 + 异步容错，Serilog 已落地）。

⏱️ 阅读路径(按时间预算选入口) - 3 分钟:看「模块目标」— 知道这是 13K→15K 硬要求(面试必问"遇到什么难 bug") - 30 分钟:加看 Day 1 VS 调试器(条件断点/数据断点/Threads 窗口) - 3 小时:全文精读 + Day 2 异常/竞态 + Day 3 内存泄漏 4 种 + Day 4 性能 + Day 5 Wireshark/万用表 - 🎯 面试高频:条件断点 vs 数据断点 / dotnet counters + gcdump 抓内存泄漏 / Wireshark 抓 Modbus 字节 / Serilog + TraceId 跨线程关联 / "什么 bug 不在软件里要上示波器" - 🔁 配套复习:代码肌肉 B20 Serilog + TraceId · Debug C7/C8/C9 全二刷 · 间隔重复表

📚 前置语法(M19 用到的,陌生请查 C# 语法速查 — 前端视角) - try { ... } catch (Exception ex) { Log.Error(ex, "msg"); throw; } — 异常处理(注意 throw; vs throw ex;),速查 §9 - Log.Information("Point {Tag} = {Value}", tag, value) — Serilog 结构化日志(命名占位符) - LogContext.PushProperty("TraceId", traceId) — Serilog 上下文(用 using 自动弹出),速查 §13 - [Conditional("DEBUG")] — 条件编译 - Debugger.Break() — 编程式断点 - Interlocked.Exchange(ref _state, 0) — 原子操作排查竞态,速查 §14

模块目标

学完你能：① 用 VS 调试器高级功能（条件断点 / 数据断点 / 调用栈 / 多线程窗口）定位任意一处异常的"第一现场"；② 排查 4 类典型 bug（异常吞 / 多线程竞态 / 内存泄漏 / 性能瓶颈）；③ 抓包分析工业协议（串口字节 / Modbus TCP / CAN / OPC UA），分清是你代码错还是设备错；④ 知道什么时候该上万用表 / 示波器 / 逻辑分析仪——不是所有 bug 都在软件里；⑤ 用 Serilog 结构化日志 + TraceId 做跨线程、跨设备的关联追踪，把"现场偶发"变"日志里可查"。

Day 1 — VS 调试器高级功能（从 console.log 升级）🟡

一句话讲清楚

前端调试靠 console.log + Chrome DevTools 的 Sources 面板；上位机调试靠 VS 调试器——后者比前者强 10 倍：能下条件断点、能监视内存地址被谁改、能看所有线程的调用栈、能暂停时执行任意表达式、甚至能"时间倒流"回放（IntelliTrace）。不会 VS 调试器高级功能，等于戴着墨镜找 bug。

前端类比秒懂

VS 调试器 前端类比
断点（Breakpoint，F9） debugger 语句
条件断点（Conditional BP） if (id === 42) debugger
数据断点（Data BP） Object.defineProperty setter 监视 / Proxy
调用栈（Call Stack） console.trace()
Locals / Autos / Watch Chrome DevTools Scope 面板
Immediate Window Console REPL（暂停时执行）
Threads 窗口 （前端单线程，无）
Parallel Stacks （前端无）
Tasks 窗口 （前端无）
Exception Settings 全局 window.onerror + try-catch
IntelliTrace（企业版） 时间倒流回放（前端无）
Edit and Continue 热重载（Vite HMR 的近亲）

分点精讲

① 条件断点（⭐ 用得最多，节约 90% 时间） 右键断点 → Conditions → 输入表达式，比如 pointId == 42 && value > 100。工业现场一个轮询循环里 1000 个点位，你想看"点位 42 的值什么时候超 100"，没条件断点只能在 Console.WriteLine 几万行里翻。前端类比：if (id === 42 && value > 100) debugger;。

还能配 Hit Count（命中次数）："当本断点执行到第 500 次时断下"——排"循环跑到一定次数才出 bug"的神器；以及 Filter（只在某个线程断下）：ThreadId == 12345。

② 数据断点（🔥 排"字段被谁改了"的神器） 当某个变量的值"莫名其妙变了"，你不知道是哪行代码改的——这时右键变量 → "Break when value changes"。VS 会在该内存地址下硬件断点，任何线程只要改这个地址就断下。

⚠️ 限制：仅对值类型（int / double / struct）靠谱，引用类型（class）的"内容变"监视不了（因为地址没变）。栈变量函数返回后会失效。32 位进程最大 4 个硬件断点，64 位 8 个，超了 VS 会拒绝下断。

③ 调用栈（Call Stack）阅读姿势 抛异常 / 命中断点时，调出 Debug → Windows → Call Stack（Ctrl+Alt+C）。从下往上读：最底下是"入口"（Main / 事件触发），最顶上是"当前正在执行的行"。 - 找第一行"我写的代码"（不是 BCL / 第三方库），通常是 bug 现场； - 往下找调用者——"谁触发的"，能帮你理解数据流。

右键 → "Include External Code" 可看到 .NET 内部栈帧（默认隐藏），追 BCL bug 时打开。右键 → Run to Cursor 跳过中间几帧回溯到调用现场。

④ Immediate Window（暂停时的 REPL） 调试 → 窗口 → Immediate（Ctrl+Alt+I）。断点暂停时执行任意表达式：

_points.Count                     // 看集合大小
JsonSerializer.Serialize(p)       // 把对象序列化成 JSON 看内容
p.Children.Select(x => x.Name)    // LINQ 临时查询
_db.Records.ToListAsync().Result  // 临时查下库（EF Core 真 异步；.Result 死锁风险下面讲）

前端类比：Sources 面板暂停时在 Console 里输入变量。C# 的 Immediate 比 JS Console 强 10 倍——支持 LINQ、反射、泛型。

⑤ Edit and Continue（C# 10+ 大幅增强） 暂停时直接改代码 → 继续执行，VS 会热替换方法体，无需重启。前端类比：Vite HMR 但作用域是方法级别。

限制：改方法签名 / 加字段 / 改泛型参数要重启。Release 配置下不支持，必须 Debug。

⑥ Exception Settings（⭐ 异常排查第一手段） Debug → Windows → Exception Settings（Ctrl+Alt+E）。勾选 "Common Language Runtime Exceptions" → 任何 .NET 异常抛出的第一时机就断下（不管有没有 try-catch）。这能定位"哪一行抛的"，避免异常被层层 catch(Exception ex) { log; } 吞掉找不到源头。

进阶：勾选 "First-Chance Exceptions" 看被吞掉的；勾选 "Native Exceptions" 看 AccessViolation。只勾你关心的类型——全勾会让程序每秒断 100 次。

⚠️ 重点 & 易踩坑

项 说明
⭐ 关掉 "Just My Code" Tools → Options → Debugging → General → 取消 "Enable Just My Code"，才能断进第三方库源码
⭐ Debug ≠ Release Release 会优化（内联 / 死代码消除），断点行号乱跳、变量被优化掉；线上 bug 复现要 Debug 配置 + /debug:pdbonly
🔥 PDB 缺失 没符号文件断点不命中（"No symbols loaded"），发布时 .pdb 必须随包同目录
🔥 Source Link 配 <PublishRepositoryUrl>true</PublishRepositoryUrl> + NuGet 包带 source link，能直接断进 NuGet 源码
⭐ 关 JIT 优化 Release 调试时 [assembly: Debuggable(DebuggableAttribute.DebuggingModes.None)] 改 Default，或 attach 时勾 "Native code" + "Mixed mode"
⭐ 同步阻塞 Immediate _db.Records.ToListAsync().Result 在 UI 线程会死锁；切到非 UI 线程或用 .GetAwaiter().GetResult() 仍可能死，最好另起 Task
⭐ 符号缓存 Tools → Options → Debugging → Symbols → 勾 "Microsoft Symbol Servers"，否则看不懂 .NET 内部栈

🧪 三档练习

🟢 基础题：写一个循环 for (int i = 0; i < 1000; i++) { var x = i * 2; }，下一个条件断点让它在 i == 500 时断下；再用 Hit Count 让它在第 100 次迭代断下。

🟡 进阶题：写一个类有 public int Counter，被两个线程并发 Interlocked.Increment(ref c.Counter)。下一个数据断点监视 Counter 字段变化，观察哪个线程改它（用 Filter ThreadId == ... 区分）。

🔴 挑战题：开 VS Enterprise 的 IntelliTrace（Debug → Windows → Show IntelliTrack / 历史调试），跑一段会抛异常的代码，事件后退到异常抛出前，看当时的 Locals 值。简述它和普通调试的区别。

💡 工控导师说（真实战例）

新人刚来，给他排一个 50Hz 高频采集里"偶发某个点位值 > 100"的问题。他第一反应是 Console.WriteLine 打日志，跑了一晚上几十万行日志找花眼。我教他用条件断点 value > 100——3 秒断下，调用栈一看是 PLC 通信层某个寄存器映射错位，5 分钟搞定。从此他再也不写 Console.WriteLine 调试了。 铁律：能下断点别打日志——日志只是"现场不在身边"的妥协（生产环境）。

🎓 职业建议

面试官问"你怎么调试 bug"—— - 13K 答："打 Console.WriteLine，看哪一行报错。" → 难。 - 15K 答："VS 调试器条件断点 + 数据断点定位写入源头，Immediate Window 序列化对象看内容，Exception Settings 第一时机断下找异常第一现场，多线程问题开 Threads + Parallel Stacks 看互锁。" → 入职。

VS 调试器是 .NET 开发者的"主武器"，不会它就是赤手空拳上战场。

Day 2 — 异常排查 + 多线程竞态 🔴

一句话讲清楚

两类 bug 最难排：异常被吞（你看到的现象和真实异常隔了 5 层 try-catch）和多线程竞态（本地跑 100 次不出，现场跑 7 天必现）。前者靠 Exception Settings 找第一现场，后者靠 Threads / Parallel Stacks 看互锁。

前端类比秒懂

上位机排查 前端类比
Exception Settings 第一时机断 window.onerror + source map
Exception.ToString() 看 Inner Error.stack / Error.cause
$exception 在 Immediate 看 console 里 console.error 看完整 stack
AggregateException.Flatten() Promise.all 的 reject
async void 吞异常 Promise 没 catch（UnhandledPromiseRejection）
Threads 窗口 （前端单线程无）
Parallel Stacks （前端无）
Sync Block 死锁 （前端无）

分点精讲

1. 异常排查的标准套路

① Exception Settings 抛第一时机 勾"Common Language Runtime Exceptions"后，抛即断——不管有没有 catch。这能定位异常源头那一行。看完后取消勾选，免得后面每个 First-Chance 异常都打断你。

② Exception.ToString() 看完整链

catch (Exception ex)
{
    _log.Error(ex, "处理失败");           // Serilog 这样打，会自动带上 ToString
    _log.Error("{Exception}", ex.ToString());  // 或显式打完整链（含 InnerException）
}

坑：ex.Message 只看最外层一句话；ex.ToString() 才包含类型 + Stack + Inner 链。永远打 ToString 不打 Message。

③ $exception 隐式变量 刚抛异常还没 catch 时，在 Immediate Window 输入 $exception → 看当前异常对象。或在 Exception Settings 触发的断点里，Locals 窗口也看得到。

④ AggregateException.Flatten() 解包 Task 异常 多个 Task 并发出错，会包成 AggregateException，里面嵌套多个 InnerException。一次解包：

catch (AggregateException ae)
{
    foreach (var inner in ae.Flatten().InnerExceptions)
        _log.Error(inner, "Task 异常");
}

⑤ async void 异常吞（🔥 C# 最大的坑之一）

// ❌ 错：async void 异常会直接抛到 SynchronizationContext，进程崩 / 无法捕获
private async void OnClick(object sender, EventArgs e)
{
    await DoSomethingAsync();   // 内部抛异常 = 整个进程崩
}

// ✅ 对：async Task + 事件包装
private async void OnClick(object sender, EventArgs e)
    => await SafeCallAsync(DoSomethingAsync);

private async Task SafeCallAsync(Func<Task> action)
{
    try { await action(); }
    catch (Exception ex) { _log.Error(ex, "UI 异步操作失败"); }
}

详见 C# 陷阱讲义 陷阱 4。事件处理器只能 async void，所以必须自己包 try-catch。

2. 多线程竞态调试

① Threads 窗口：Debug → Windows → Threads（Ctrl+Alt+H）。看到所有线程的"当前位置"，双击切到任意线程查看其调用栈和 Locals。

② Parallel Stacks：Debug → Windows → Parallel Stacks（Ctrl+Shift+D, Q）。所有线程的调用栈同时画在一张图上——哪个方法上挤了一堆线程一目了然，能瞬间看出"线程都在等同一个锁"。

③ Tasks 窗口：看所有 Task 的状态（Scheduled / Running / Waiting / Faulted），Faulted 的能看到内部异常。

④ 死锁排查实战：Tools → Parallel Stacks 看到线程 A 卡在 lock(A) → 等 lock(B)，线程 B 卡在 lock(B) → 等 lock(A)，经典互等。改：全局统一锁顺序（按字母序上锁）。

3. SOS 命令行死锁检测（生产 dump 分析）

# 抓 dump（生产环境）
dotnet dump collect -p <pid> -o dump.dmp

# 分析
dotnet dump analyze dump.dmp
> syncblk                    # 查看所有 SyncBlock（监视器锁）
# 输出：
# Index SyncBlock MonitorHeld Recursion Thread Thread-Id
# 1     02c8f3c0 1            0         0a    12 abcd (持锁线程)
> ~*s clrstack                # 看所有线程的 .NET 调用栈
> dumpheap -stat              # 内存统计（明天讲）

syncblk 输出会显示哪个线程持有哪个锁——再 ~*s clrstack 看那个线程在干啥，互锁死锁一眼看出。

4. 真实战例（4 个经典 race condition）

Race 1：ConcurrentDictionary 用错

// ❌ 错：ContainsKey + 索引两步不原子，中间可能被插
if (!_dict.ContainsKey(k)) _dict[k] = v;

// ✅ 对：原子操作
_dict.TryAdd(k, v);
_dict.GetOrAdd(k, _ => v);

Race 2：List 跨线程读写

// ❌ 错
if (_list.Count > 0) return _list[0];   // 中间另一线程 RemoveAt(0) → IndexOutOfRange

// ✅ 对
lock (_list) { if (_list.Count > 0) return _list[0]; }
// 或用 ConcurrentQueue<T>

Race 3：死锁（两个锁顺序不一致）

// ❌ 线程 1
lock (A) { lock (B) { /* ... */ } }
// ❌ 线程 2
lock (B) { lock (A) { /* ... */ } }
// → 偶发互等

// ✅ 统一锁顺序（按字段名字母序）
lock (A) { lock (B) { /* ... */ } }   // 所有地方都 A→B

Race 4：async void 异常吞 事件处理器 async void 内抛异常 → 进程崩溃，没 try-catch 找半天。修：见上文 SafeCallAsync 模式，或用 Channel<T> 把事件转成"队列消费"。

⚠️ 重点 & 易踩坑

项 说明
⭐ 永远打 ex.ToString() 不打 ex.Message——丢失 InnerException 链是排错大忌
⭐ 第一时机用 Exception Settings 异常被吞找源头，这是唯一手段
🔥 async void 必加 try-catch 事件处理器是 async void 高发区
🔥 跨线程访问 UI 控件 直接 .Text = ... 抛 InvalidOperationException；用 Dispatcher.Invoke / Control.Invoke
⭐ lock(this) / lock(typeof(X)) 公共对象上锁会被外部 lock 死锁；用 private readonly object _lock = new()
⭐ await 前后可能不同线程 await 后续可能切线程，Thread.CurrentThread 变了，[ThreadStatic] 变量丢失

🧪 三档练习

🟢 基础题：写一个 async void 事件处理器，内部抛 InvalidOperationException。先用 Exception Settings 捕获它第一时机；再改成 SafeCallAsync 包装模式正确处理。

🟡 进阶题：起两个 Task，A 锁 object1 后等 object2，B 反过来。用 Parallel Stacks 窗口截图显示互锁，再用 dotnet dump collect + syncblk 命令验证你的判断。

🔴 挑战题：写一个并发场景，ConcurrentDictionary<int, List<int>> 多线程往 List 里 Add。代码"看起来对"（用了 ConcurrentDictionary），但 List 本身不是线程安全的。复现一次崩溃，改成 ConcurrentDictionary<int, ConcurrentBag<int>> 或加锁修复，并解释为什么。

💡 工控导师说（真实战例）

某次现场上位机每周偶发崩一次，没任何规律。开发同事抓不到 dump，因为不知道啥时候崩。我让他装个 Windows 任务计划 + Procdump：procdump -ma -e -w DaqMonitor.UI.exe C:\dumps\ —— 程序一崩，自动抓完整 dump。 一周后抓到 dump，dotnet dump analyze 打开 → syncblk + ~*s clrstack → 发现是 OPC UA 订阅回调线程和 UI 线程互锁：UI 线程同步等 OPC 完工（.Result），OPC 回调在 UI Dispatcher 上等执行——经典 async 死锁。改 .Result 为 await，再没崩过。 铁律：偶发崩必须有 dump 机制。生产环境没 dump 你就是在算命。

Day 3 — 内存泄漏排查（4 种典型）🔴

一句话讲清楚

.NET 有 GC 不代表不会泄漏——事件订阅忘退订 / static 集合无限增长 / 闭包捕获 this / GDI 句柄没 Dispose，这四类典型泄漏能让你 7×24 跑的程序从 100MB 涨到 1GB，最后 OOM 崩溃。Chrome DevTools 的 Memory 三件套（Heap snapshot / Allocation timeline / Detached DOM）在 C# 这边对应 dotnet gcdump + dotnet counters + dotnet dump。

前端类比秒懂

C# 内存排查 Chrome DevTools
dotnet gcdump（堆快照） Memory → Heap snapshot
dotnet counters 实时监控 Memory → Allocation timeline
dotnet dump analyze + gcroot Memory → Retainers（dominator 树）
dotMemory（JetBrains） Memory 面板完整版
weak event / WeakReference WeakMap / WeakRef
GDI 句柄（Bitmap 等） Detached DOM 节点
IDisposable 清理 callback

分点精讲

1. 4 种典型泄漏

泄漏 1：事件订阅忘退订（⭐ 最常见）

// ❌ 错
public MainWindow()
{
    _plc.ValueChanged += OnValueChanged;   // 订阅
}
// 窗体关闭时没退订 → _plc 持有窗体引用 → 窗体永远 GC 不掉
// 每开一次窗体就泄漏一个

// ✅ 对
protected override void OnClosed(EventArgs e)
{
    _plc.ValueChanged -= OnValueChanged;   // 显式退订
    base.OnClosed(e);
}

详见 [M3 PLC 修正版] 的"事件订阅规范"。事件源长存活、订阅者短存活的场景必加 -=。

泄漏 2：static 集合无限增长

// ❌ 错：缓存没限制
private static readonly List<SensorPoint> _recent = new();
void OnNewPoint(SensorPoint p) => _recent.Add(p);   // 永远只增不减 → OOM

// ✅ 对：上限 / 过期
private static readonly Queue<SensorPoint> _recent = new();
void OnNewPoint(SensorPoint p)
{
    _recent.Enqueue(p);
    while (_recent.Count > 1000) _recent.Dequeue();   // 环形缓冲
}

泄漏 3：闭包 / 异步 lambda 捕获 this

// ❌ 错：lambda 捕获 this，长存活对象持有它
_scheduler.Schedule(async () =>
{
    await Task.Delay(TimeSpan.FromHours(1));
    this.TextBox.Text = "done";   // 1 小时后 this 还活着，本该释放
});

// ✅ 对：用弱引用 / 显式释放 / 缩短闭包生命周期

泄漏 4：GDI 句柄（Bitmap / Pen / Brush / Font 没 Dispose）

// ❌ 错
void OnRender(PaintEventArgs e)
{
    var bmp = new Bitmap(width, height);   // 没 using
    var pen = new Pen(Color.Red);
    e.Graphics.DrawImage(bmp, 0, 0);
}   // bmp 和 pen 直到 GC 才释放 GDI 句柄

// ✅ 对：using 包裹
using var bmp = new Bitmap(width, height);
using var pen = new Pen(Color.Red);
e.Graphics.DrawImage(bmp, 0, 0);

现象：Task Manager → 查看 → 选择列 → 勾 "GDI Objects"，跑到 10000 就崩。

3. 真实战例（必讲）

场景：DAQMonitor 跑 3 天后内存 1GB（正常 100MB）。 步骤： 1. dotnet counters monitor → 看到 gen-2-heap-size 持续涨 → 确认是泄漏不是高峰。 2. dotnet gcdump -p <pid> → 用 PerfView 打开，按类型排序 → SensorPoint 实例数 5000 万，正常应该 0（消费完就该 GC）。 3. dotnet dump collect + dumpheap -type SensorPoint → 拿到一个地址。 4. gcroot <address> → 输出 DOMAIN(LONG)... → List<SensorPoint> _recentInMemoryCache → SensorPoint[] ... → 根是 _recentInMemoryCache 静态 List。 5. 看代码：_recentInMemoryCache.Add(p) 永远不减 → 改 Queue<SensorPoint>(1000) 环形缓冲 → 内存稳定 100MB。

⚠️ 重点 & 易踩坑

项 说明
⭐ 事件订阅必退订 长存活源 + 短存活订阅者必 -=；或用 WeakEventManager
⭐ static 集合必加上限 List / Dictionary 用做缓存必加容量限制或 LRU
🔥 lambda 捕获 this 长存活调度器（Quartz / Timer）订阅 lambda 持有 this
🔥 Bitmap / Pen / Brush / Font 必须 using / Dispose，靠 GC 不可靠
🔥 WPF Binding to non-INPC 绑定到普通属性 → 强引用永不释放（少见但痛）
⭐ GC.Collect 不解决 不是 GC 不工作，是对象被引用，要先找 root
⭐ WeakReference 不是万能 弱引用本身有开销，且对象会被随时回收不可控
⭐ Timer 回调闭包 new Timer(_ => this.X()) 持有 this 直到 Timer Dispose

🧪 三档练习

1. 性能分析三件套

① VS Performance Profiler（最易上手） Debug → Performance Profiler（Alt+F2）。勾选要分析的： - CPU Usage：哪些方法烧 CPU 多（火焰图）。 - Memory Usage：哪些对象占内存多（接 Day 3）。 - GPU Usage：WPF 渲染 / DirectX 烧显卡。 - Concurrency Visualizer：线程时序图（看阻塞 / 等待）。 - Event Tracing for Windows (ETW)：底层事件追踪。

用法：Start → 操作 UI（复现卡顿）→ Stop → 看火焰图找热点。新人最爱用 Stopwatch 测，效率是 Profiler 的 1/10。

② dotnet-trace 抓火焰图（生产环境零侵入）

# 用 speedscope.app 打开（浏览器拖进去就行）
# 看 OnRender 占 60% → 优化方向明确

优势：生产环境不开 VS 也能抓。文件小（几 MB），可邮件给同事分析。

2. 性能优化实战例

例 1：启动慢 5 秒 - VS Profiler → 发现 Bootstrapper.ConfigureServices 同步建 SQLite 库 + 加载 1 万行配置。 - 改：建库改异步、配置改 lazy 加载 → 启动 1 秒。

3. 协议抓包（工业现场必备）

① 串口抓包：AccessPort / 串口网络调试助手 / Eltima Serial Port Monitor。 - 监听 COM3 收发的原始字节，hex 显示。 - 看你发的帧对不对、设备回的对不对、回得及时不。

② Modbus 抓包：Modbus Poll（Master）+ Modbus Slave（Slave）模拟器。 - 用 Modbus Poll 直连设备，验证你代码发的帧和它发的帧字节级一致。 - 排"PLC 给值对，我代码读错了"问题。

⑤ OPC UA 抓包：OpcUaClient（统一架构） / Opc.Ua.Client（开源）。 - 直接连 Server 看节点列表，验证你代码订阅的 NodeId 对不对。

💡 工控导师说（真实战例）

某次现场客户反馈"读取 PLC 偶发超时，几小时一次"。本地复现不出，去了现场。 装 Wireshark 抓 502 端口，几小时抓到一次：设备在收到请求 1.2 秒后才回，而我们的 timeout 是 1 秒——所以触发了超时重试。看 PLC 工程师，他说 PLC 那个扫描周期里在跑"长任务"会偶发慢。 解决：把 timeout 从 1 秒提到 3 秒 + 重试一次（Polly），偶发超时消失。抓包证明了不是代码错，是设备慢——这是关键证据。 铁律：现场所有"偶发问题"，第一步必抓包。日志说不清的，字节能说清。

🎓 职业建议

面试问"你怎么优化性能"—— - 15K 答："VS Profiler / dotnet-trace 找热点，BenchmarkDotNet 量化优化效果，生产用 dotnet-counters 监控 GC 压力。串口 / Modbus 问题先抓包看字节，分清代码错还是设备错。" - 13K 答："加 StopWatch 看哪行慢。" → 13K。

性能和抓包是 15K 工程师的"双修课"，二者都要会。

Day 5 — 工业现场物理工具 + Serilog 关联追踪 🔴

一句话讲清楚

不是所有 bug 都在软件里——电压不稳 / 线缆虚接 / RS485 终端电阻没接 都会让你的"完美代码"出问题。所以 13K 工程师必备：① 物理工具（万用表 / 示波器 / 逻辑分析仪）；② 结构化日志 + TraceId，把"现场偶发"变"日志可查"。

前端类比秒懂

工业现场工具 / Serilog 前端类比
万用表（测电压电流通断） DevTools 的 Network → Status
示波器（看波形） Network → Timing（瀑布图）
逻辑分析仪（解协议） Network → Bytes
网络测线仪 ping + traceroute
Serilog 结构化日志 Sentry / Datadog Logs
LogContext.PushProperty("TraceId") X-Request-Id / correlationId

分点精讲

1. 物理工具（13K 必问）

① 万用表（最基础） - 测电压：PLC 模拟量输入卡是不是给到 24V？传感器供电是否正常？ - 测电流：4-20mA 回路是工业标准，回路里串万用表（mA 档）测实际电流值，反推工程量 (电流 - 4) / 16 * 量程。 - 测通断：线缆虚接？蜂鸣档一搭就知道。 - 铁律：现场所有"通信不通"，先量电压。RS485 A/B 之间应该有 0.5-1V 压差。

② 示波器（看信号质量） - 看 RS485 差分信号波形（A-B）：电平、上升沿、噪声。 - 看模拟量噪声：传感器信号是否被电磁干扰。 - 看继电器触点抖动。 - 入门款：Rigol DS1054Z（约 2000 元）足够。

③ 逻辑分析仪（解协议） - 便宜版 Saleae 8 通道（约 100-500 元）足够用。 - 抓 I2C / SPI / UART / CAN / 1-Wire 原始波形，自动解码。 - 排"我发的字节对，但设备收错了"问题——直接在物理层看。

④ 网络测线仪 - RJ45 8 根线通断测试，1 秒确认网线是不是做错线序。 - 现场调试第一件事。

⑤ USB 转串口 / 网口 / CAN - 笔记本通常没有这些接口，调试必备。

2. Serilog 结构化日志 + TraceId（关联追踪）

为什么需要 TraceId？ 工业现场一条数据流要经过：UI → 采集层 → PLC 驱动 → 物理层 → PLC → 反向回来。出问题时，10 个点位并发读取，你不知道哪条日志对应哪个点位。

解决方案：每次请求开始时分配一个唯一 TraceId，通过 LogContext.PushProperty 推入日志上下文，整条调用链的所有日志自动带上这个字段。事后查询："TraceId=xxx" 一搜就能看到完整链路。

// 入口处分配 TraceId（IDevice 是同步门面，这里就同步写）
public SensorPoint ReadPoint(int pointId)
{
    using (LogContext.PushProperty("TraceId", Guid.NewGuid().ToString("N").Substring(0, 8)))
    using (LogContext.PushProperty("PointId", pointId))
    {
        _log.Information("开始读取");
        try
        {
            var raw = _plc.Read(pointId);
            _log.Information("PLC 返回 Raw={Raw}", raw);
            var value = _scaler.Scale(raw);
            _log.Information("工程量={Value}", value);
            return new SensorPoint { Id = pointId, Value = value, Timestamp = DateTime.UtcNow };
        }
        catch (Exception ex)
        {
            _log.Error(ex, "读取失败");
            throw;
        }
    }
}

Serilog 完整配置：

// Bootstrap 一次性配置
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    .Enrich.FromLogContext()                  // 自动加 TraceId / PointId 等上下文属性
    .Enrich.WithMachineName()                 // 区分多台上位机
    .Enrich.WithEnvironmentUserName()
    .Enrich.WithProperty("App", "DaqMonitor")
    .WriteTo.Console(formatter: new CompactJsonFormatter())    // JSON 结构化，便于 ES / Loki 索引
    .WriteTo.File("logs/daq-.log",
        rollingInterval: RollingInterval.Day,
        retainedFileCountLimit: 7,            // 7 天滚动
        formatter: new CompactJsonFormatter())
    .WriteTo.SQLite("logs/daq.db")            // 落库便于查询
    .WriteTo.Seq("http://localhost:5341")     // 可选：Seq 可视化日志
    .CreateLogger();

关键：Console / File / SQLite 都用 CompactJsonFormatter——以后想导到 ELK / Loki 不用改代码。打日志别用字符串插值 $"PointId={id}"，用模板 "PointId={PointId}" 让 Serilog 结构化（保留字段名）。

3. 排查 SOP（标准流程）

第 1 步：复现 - 找到稳定的复现路径，不能复现的 bug 等于猜。 - 现场偶发：装 Procdump / dotnet-dump 监控（崩溃自动抓）。

第 2 步：抓日志 - TraceId 反查整条调用链：grep "TraceId=ab12cd34" logs/*.log - 看 5 秒前后上下文，往往能看到"前 1 秒网络断了"、"前 3 秒 CPU 飙到 100%"。

第 3 步：抓 dump / trace - 内存问题 → dotnet dump collect + dumpheap -stat - 性能问题 → dotnet trace collect 火焰图 - 崩溃问题 → Procdump 自动抓 first-chance + crash dump

第 4 步：二分法注释代码 - 找不到具体在哪？注释一半代码看 bug 还在不。 - 不断二分，半小时定位到一行。

第 5 步：写最小复现单元测试 - 隔离环境变量，最小依赖（不用真 PLC，用 Mock）。 - 既是验证修复，也是回归测试。

⚠️ 重点 & 易踩坑

项 说明
⭐ 现场先量电压 不通电 / 电压不稳是工业现场 #1 故障源
⭐ RS485 终端电阻 长线缆两端必须接 120Ω 终端电阻，否则信号反射通信乱
⭐ 共地（GND） RS485 即便差分也要共地，否则烧接口
🔥 日志用模板不用插值 _log.Info("X={X}", x) 而非 $"X={x}"，才能结构化
⭐ TraceId 要短 8 位足够，避免日志变长
⭐ 敏感字段打码 密码 / Token / 工艺配方核心字段打码
⭐ 日志级别合理 Error = 系统挂了 / Warn = 异常但能跑 / Info = 关键业务 / Debug = 调试细节
⭐ 异步日志 sinks SQLite 等慢 sink 要异步，否则拖垮采集
