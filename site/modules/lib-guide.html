二、调库之前先想清楚:库在替你干什么

你手搓过 R3/R4,这是你比"只会调库的人"强的地方——每个库调用背后都是你写过的代码:

你手写过(R3/R4) 调库后对应物
Crc16.Modbus(15 行移位异或) 库内部算,不可见
BuildReadHoldingRequest 组 8 字节帧 client.ReadHoldingRegisters(...) 一个调用
ParseReadRegisters 拆响应 同上,直接给你 short[]/Span<short>
IsExceptionResponse 异常码分流 抛 ModbusException(FluentModbus)
串口参数 + 半双工等响应 库 Transport 层管超时/重试
PollOnce 轮询循环 库不管,还是你自己写
断线重连/心跳(R4 TcpDevice) 库不管,还是你自己写
粘包半包蓄水池 TCP 库内部处理;串口库按帧处理

关键结论:调库省的是"字节层"(组帧/CRC/解析),省不掉的是"业务层"(轮询节奏、断线重连、数据进管道、报警)。 R5 的管道、R4 的重连,不管调不调库都得自己写——你已经写过一遍了。

三、FluentModbus(Modbus,新项目首选)

装包

dotnet add package FluentModbus
dotnet add package System.IO.Ports    # 串口 RTU 才需要(R4 装过同一个包)

TCP 主站(设备是 Modbus TCP Server,最常见)

using System.Net;
using FluentModbus;

using var client = new ModbusTcpClient();
client.Connect(new IPEndPoint(IPAddress.Parse("192.168.0.10"), 502)); // 设备 IP + 默认 502

var regs = client.ReadHoldingRegisters<short>(1, 0, 2);   // (从站号, 起始地址, 数量)→ Span<short>
client.WriteSingleRegister(1, 4, (ushort)1234);            // 写单寄存器(功能码 06)
client.WriteMultipleRegisters<short>(1, 10,               // 批量写(功能码 10)
    new short[] { 100, 200, 300 });
  • 地址直接写协议地址(0 起)——手册的 40001 照样要你自己减一,库不管这个(E04 的坑不因调库消失)
  • ReadHoldingRegisters<T> 返回 Span<T>(ref struct):不能存字段、不能跨 await,要留存先 .ToArray()
  • WriteSingleRegister 非泛型且有 short/ushort 两个重载——写 1234 字面量会二义性,显式 (ushort)1234

RTU 主站(串口,9600-8-N-1)

using System.IO.Ports;
using FluentModbus;

var port = new SerialPort("COM3", 9600, Parity.None, 8, StopBits.One);
port.ReadTimeout = 1000; port.WriteTimeout = 1000;
port.Open();                                               // 串口参数还是自己配(E03 不白学)

using var client = new ModbusRtuClient();
client.Initialize(new ModbusRtuSerialPort(port), ModbusEndianness.BigEndian); // 串口交给库
var regs = client.ReadHoldingRegisters<ushort>(1, 0, 2);   // 读 1 号从站,地址 0 起 2 个
client.WriteSingleRegister(1, 0, (ushort)42);              // 写单寄存器

TCP 从站(测试神器:没设备也能自测)

using var server = new ModbusTcpServer();
server.AddUnit(1);                                        // 先注册从站号,再访问缓冲(顺序反了抛 KeyNotFound)
server.Start(new IPEndPoint(IPAddress.Loopback, 15020));
server.GetHoldingRegisterBuffer<short>(1)[0] = 0x1234;    // 预置数据:地址 0 = 0x1234
// 主站 Connect 到 127.0.0.1:15020 即可读写 —— 全进程内,零硬件

✅ 沙盒实测(.NET 8 + FluentModbus 5.3.2,主从同进程):

[FluentModbus TCP 读] 地址0=0x1234, 地址1=0x5678
[FluentModbus TCP 写] 地址4 <- 1234, 读回=1234
[FluentModbus TCP 批量写] 地址10起3个, 读回=[100,200,300]

四、NModbus4(接手老项目必识)

dotnet add package NModbus4

using System.Net.Sockets;
using Modbus.Device;                    // ⚠ 命名空间是 Modbus.*,没有 NModbus 前缀

using var tcp = new TcpClient("192.168.0.10", 502);
var master = ModbusIpMaster.CreateIp(tcp);
master.Transport.Retries = 0;           // 默认重试 3 次,超时表现怪就先看这

ushort[] regs = master.ReadHoldingRegisters(slaveAddress: 1, startAddress: 0, numberOfPoints: 2);
master.WriteSingleRegister(slaveAddress: 1, registerAddress: 4, value: 1234);

坑(全部沙盒实踩):

  1. 包只发到 net40 程序集,net8 里还原报 NU1701 警告——能编译能跑,但新项目别选它
  2. 命名空间是老 NModbus 的 Modbus.Device / Modbus.IO
  3. 串口适配器 SerialPortAdapter 访问级别受限,.NET 8 上接串口 RTU 不顺——要串口直接上 FluentModbus
  4. 做从站模拟时 DataStore.HoldingRegisters[1] 才是地址 0(下标 0 是占位)
  5. 从站 Listen() 是阻塞方法,要 Task.Run(() => slave.Listen()) 包

✅ 沙盒实测(.NET 8 + NModbus4 2.1.0,主从同进程):

[NModbus4 TCP 读] 地址0=0x1234, 地址1=0x5678
[NModbus4 TCP 写] 地址4 <- 1234, 读回=1234

五、S7netplus(西门子 PLC)

dotnet add package S7netplus

using S7.Net;    // ⚠ 包名 S7netplus,命名空间是 S7.Net

using var plc = new Plc(CpuType.S71200, "192.168.0.1", 0, 1); // (CPU 型号, IP, 机架号, 槽位号)
plc.Open();

ushort dbw0 = (ushort)plc.Read("DB1.DBW0")!;         // 读 DB1 块第 0 个字;返回 object 自己转型
plc.Write("DB1.DBW2", (ushort)42);                   // 写 DB1 块第 2 个字
var bytes = plc.ReadBytes(DataType.DataBlock, 1, 0, 16); // 原始字节:DB1 从 0 起连续 16 字节
  • S7 地址直接写 "DB1.DBW0" 字符串(DB 块.字节),比 Modbus 寄存器模型直观——没有 40001 那套偏移
  • Read(string) 返回 object,类型自己负责转(0.20 版没有泛型 Read)
  • 与 R4 的关系:PlcDevice 的 simulate=true 模拟模式就是给它占的位——真实项目把这个类接上真调用
  • 编译验证于 S7netplus 0.20.0(运行需要真 PLC)

六、HslCommunication(日系/杂牌设备,国内中小公司常用)

  • 一个包覆盖三菱 MC、欧姆龙 Fins、基恩士、松下、罗克韦尔、西门子、Modbus 全家——国内公司用它极多,JD 里"熟悉 HSL"就是它
  • 商用需付费授权(个人学习免费)。进公司问一句"HSL 授权买了没"——这个问题本身就是加分项
  • 风格示意(Modbus TCP,⚠ 未沙盒验证,以官方 Demo 为准):
var client = new HslCommunication.ModBus.ModbusTcpNet("192.168.0.10", 502, 0x01);
await client.ConnectServer();

OperateResult<short> read = client.ReadInt16("100");   // 地址写十进制字符串
if (read.IsSuccess) Console.WriteLine(read.Content);

await client.WriteAsync("100", (short)42);

七、手搓 vs 调库:怎么选(面试怎么答)

场景 选择 原因
公司项目,交付要快 调库 生产力;成熟库的边界情况处理更全
协议冷门/厂商只给协议手册 手搓 没库可调——非标行业常态(两轴插补、私有 AA55 帧都属这类)
库出问题/现场疑难(偶发坏帧、丢数据) 手搓功底下到字节层 只会调库的人在这里就瘫了
学习期/面试期 手搓 讲得出 CRC、半包、字节序的人才值 13-15K

🎤 面试一句话:"项目里协议层我是手搓的,因为要吃透字节流;生产里我清楚主流是调库——Modbus 用 FluentModbus、西门子用 S7netplus、日系用 HSL。调库是为了效率,手搓是为了底盘——库出问题时我能下到字节层排查,这是我手搓过的原因。"

八、沙盒工程怎么搭的(可复现)

mkdir LibDemo && cd LibDemo
dotnet new console          # SDK 10 模板只给 net10.0,建完把 csproj 改回 net8.0
dotnet add package FluentModbus
dotnet add package NModbus4
dotnet add package S7netplus
dotnet add package System.IO.Ports
dotnet run

csproj 两个非默认项(和参考工程同款经验):

<LangVersion>latest</LangVersion>   <!-- FluentModbus 5.x 的 Span 返回值需要新语言版本 -->
<RollForward>Major</RollForward>    <!-- 本机只装了 .NET 10 运行时,net8.0 工程滚动向前跑 -->

验证结论:TCP 两库主从运行通过(输出见上),FluentModbus RTU/S7netplus 编译通过(运行需真串口/真 PLC)。
