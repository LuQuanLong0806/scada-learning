〇、先拆焦虑:你怕的"高并发"不是上位机考的

互联网后端(Node 世界) 上位机/工业(你要面试的)
压力来源 万级用户同时读写 1 台设备 100Hz × N 点位 ≈ 几百次写/秒
真命题 缓存穿透/分库分表/主从/熔断 高频写不丢不卡 + 历史表越来越大怎么办
面试考不考 后端岗考 基本不考(13-15K 上位机 JD 没人问读写分离)
标准答案 一整套中间件 你项目里就有:Channel 串行写泵 + 攒批 + 索引 + 分表归档

🎤 你的"高并发"面试话术(背下来,这就是工业版高并发答案):

"我的项目采集频率 100Hz 多点位,直接逐条写库会拖垮采集线程还触发 SQLite 单写者锁。我的方案是三层:①EF Core 不直接写,写请求进 Channel 队列(SingleReader 串行化,天然满足单写者);②攒批:攒满 N 条或 200ms 整批落库,把每秒几百次写压缩成每秒 5 次批量写;③查询路径建 (point_id, time) 复合索引,历史查询毫秒级。真要上海量,再换 SQL Server + Dapper 批量插入或 SqlBulkCopy。"

——没有高并发经历没关系,你有一套完整的工业版高频写方案,这是等效资历。

二、SQL 手写 12 题(🔴 必会,2 小时;表就是你项目里的表)

练习表 = 你项目的真实表,打开 %LocalAppData%\DaqMonitor\daq.db(VSCode SQLite 插件)边写边验: sensor_record(id, point_id, value, time) + 假想配置表 point_def(point_id, name, unit) 方言:答案给 SQLite,括号注 SQL Server 差异。先自己写,再看答案。

① 查点位 1 今天的全部记录

SELECT * FROM sensor_record
WHERE point_id = 1 AND time >= date('now','start of day');
-- SQL Server: WHERE point_id=1 AND time >= CAST(GETDATE() AS DATE)

② 点位 1 今天的最大/最小/平均

SELECT MAX(value), MIN(value), AVG(value) FROM sensor_record
WHERE point_id = 1 AND time >= date('now','start of day');

③ 每个点位今天的平均值(GROUP BY 必考)

SELECT point_id, AVG(value) FROM sensor_record
WHERE time >= date('now','start of day')
GROUP BY point_id;

④ 每小时平均温度(时间截断聚合——班报/日报的核心 SQL,面试最爱)

SELECT strftime('%Y-%m-%d %H:00', time) AS 小时, AVG(value)
FROM sensor_record WHERE point_id = 1
GROUP BY strftime('%Y-%m-%d %H:00', time);
-- SQL Server: GROUP BY DATEADD(HOUR, DATEDIFF(HOUR,0,time), 0) 或 FORMAT(time,'yyyy-MM-dd HH:00')

⑤ 最新的 100 条

SELECT * FROM sensor_record ORDER BY time DESC LIMIT 100;
-- SQL Server: SELECT TOP 100 ... ORDER BY time DESC

⑥ 今天值超过 100 的次数

SELECT COUNT(*) FROM sensor_record
WHERE value > 100 AND time >= date('now','start of day');

⑦ JOIN:查出"温度传感器"这个点位的名字+单位+最新值(配置表联历史表)

SELECT d.name, d.unit, r.value, r.time
FROM sensor_record r JOIN point_def d ON r.point_id = d.point_id
WHERE d.name = '温度传感器'
ORDER BY r.time DESC LIMIT 1;

⑧ 每个点位今天的报警次数(条件计数 SUM CASE——比子查询优雅,说出来加分)

SELECT point_id,
       SUM(CASE WHEN value > 100 THEN 1 ELSE 0 END) AS 报警次数
FROM sensor_record
WHERE time >= date('now','start of day')
GROUP BY point_id;

⑨ 删除 30 天前的旧数据(归档场景,工业真实需求)

DELETE FROM sensor_record WHERE time < date('now','-30 day');
-- 面试追问"亿级表这么删会锁死怎么办" → 答:分批删(LIMIT 循环)或按月分表直接 DROP 整月

⑩ 分页:第 3 页,每页 50 条

SELECT * FROM sensor_record ORDER BY time DESC LIMIT 50 OFFSET 100;
-- SQL Server: OFFSET 100 ROWS FETCH NEXT 50 ROWS ONLY(2012+)

⑪ 按天统计数据量(工业真实用途:对账——每天应采 N 条,少了对不上就是丢点)

SELECT date(time) AS 天, COUNT(*) FROM sensor_record
GROUP BY date(time) ORDER BY 天 DESC;

⑫ 概念题:(point_id, time) 复合索引,下面哪条查询用得上?

A. WHERE point_id=1 AND time>今天     → ✅ 完美命中(最左前缀 point_id + time 范围)
B. WHERE time>今天                    → ❌ 用不上(跳过最左列 point_id,索引白建;单建 time 索引才救它)
C. WHERE point_id=1                   → ✅ 部分命中(最左前缀)

最左前缀法则:复合索引像电话簿(姓,名)——知道"姓张"能翻目录,只知道"名伟"只能全本扫。这就是你项目建 (point_id,time) 而不是 (time,point_id) 的原因——最高频查询是"某点位某时段"。

三、大数据量优化:会说版话术(JD"大数据量存储优化经验"对应题)

面试官问"跑了一年后,历史表几亿行,查询变慢怎么办?"——四板斧按顺序答:

  1. 索引先说:确认查询路径有覆盖索引(你的 (point_id,time)),先看是不是索引缺了而不是数据多了;
  2. 按月分表:sensor_record_202608 / sensor_record_202609…查询跨表 UNION,删除=直接 DROP 整张月表(比 DELETE 快一万倍);
  3. 冷热分离:热数据(近 3 个月)留主库,冷数据归档到归档库/文件(导 CSV/Parquet),界面查"历史"默认只查热区;
  4. 写入侧减量:不是每个原始点都要存——只存变化点和聚合值(每分钟存 min/avg/max 三个值,存储降 99%),这叫死区/压缩记录,组态软件(SCADA)的标配功能。

能把 2/3/4 讲出来,你就覆盖了 JD 那句"大数据量存储优化经验"。

四、事务/连接池:Node 背景一秒映射表

你会的(Node) C#/.NET 对应 面试一句话

pg pool / 连接复用 ADO.NET 连接池(默认开) "DbContext 短命不是浪费——底层连接池在复用,开/关连接是逻辑的不是物理的"
prisma migrate EF Migrations(版本化改表) "开发 EnsureCreated 快速起,生产 Migrations 管演进"
Knex/Sequelize 查询构建器 LINQ(被 EF 翻译成 SQL) "LINQ 是强类型的 SQL 构建器,翻译发生在数据库端"

五、连环追问预埋(5 连,每题 15 秒)

  1. "高频采集怎么入库不丢不卡?" → 第〇节话术(队列+攒批+索引)
  2. "一年后表 10 亿行?" → 第三节四板斧
  3. "为什么开发用 SQLite、上线换什么?" → "SQLite 单文件零部署适合单机版客户;网络版/多客户端换 SQL Server——EF 面向提供程序,换连接串业务零改,我项目实测过(Bootstrapper 一行)"
  4. "EF 和 Dapper 怎么选?" → "业务 CRUD 用 EF(开发效率+迁移),高频写/复杂报表 SQL 用 Dapper(可控+快),混合用不冲突"
  5. "两条写入必须同时成功?" → "包事务:Begin→两次写→Commit,任何一步失败整体回滚;EF 里多个 Add 一次 SaveChanges 天然如此"
