M1 — 串口通信（SerialPort）

优先级定位：🔴 必学 · 串口 RS232/485（JD 主干必会） 技术来源：🟩 .NET 类库 System.IO.Ports（.NET 8 需 dotnet add package System.IO.Ports；它是微软官方 BCL 扩展，不是第三方，装了就行、随 .NET 版本）。 给简历加的能力：真实 / 虚拟串口设备接入 —— 上位机对接下位机、仪表、传感器的最普遍方式。 前置：M0（类 / 事件 / 并发）。M1 是第一次把"后台收数 → 事件 → UI"串成真实链路。

模块目标

写出一个串口采集器：配置波特率 → 打开端口 → 接收字节流 → 解析成业务数据 → 通过 DataReceived 事件抛给 UI → 显示在 DAQ Monitor。

Day 1 — 串口基础 + 收发第一个字节

一句话讲清楚

串口 = 一条"按字节排队"的双向数据线。上位机和下位机约定好"语速"(波特率)和"帧格式"(数据位 / 停止位 / 校验)，然后一个发字节、一个收字节。

前端类比秒懂

串口概念 前端类比 说明
SerialPort WebSocket / Node serialport 建立连接通道
波特率 9600 / 115200 带宽 / 速率 双方必须一致
DataReceived 事件 onmessage 收到数据回调
字节流 byte[] ArrayBuffer 裸二进制，要自己解析
虚拟串口 localhost 回环 没硬件也能练

分点精讲

① 装包 + 建立端口（🟩）

// .NET 8 需先装官方包（仍是微软出品，不是第三方）
// dotnet add package System.IO.Ports
using System.IO.Ports;

var port = new SerialPort("COM3", 9600, Parity.None, 8, StopBits.One);
port.Open();
port.WriteLine("AT\r\n");                 // 发字符串
int n = port.BytesToRead;
byte[] buf = new byte[n];
port.Read(buf, 0, n);                    // 收字节
port.Close();

② 异步收数（事件驱动）（🟩 + 🟦）

port.DataReceived += (s, e) =>
{
    var sp = (SerialPort)s!;
    int n = sp.BytesToRead;
    byte[] data = new byte[n];
    sp.Read(data, 0, n);
    Console.WriteLine($"收到 {n} 字节");   // ⚠️ 这个回调在【后台线程】！
};

⚠️ 串口 DataReceived 是后台线程触发的（呼应 M0 Day 7）。要在 WPF 改界面必须用 Application.Current.Dispatcher.Invoke(...)。

③ 虚拟串口练手（无硬件方案） - Windows 装 com0com 或 VSPD，虚拟出 COM3<->COM4 一对；DAQ Monitor 开 COM3，另写个小发送器开 COM4 发数据，就能闭环测试，零硬件成本。

⚠️ 重点 & 易踩坑

项 说明
⭐ 波特率双方一致 下位机 9600、上位机 115200，收的全是乱码
⭐ DataReceived 是后台线程 跨线程改 UI 必崩，用 Dispatcher.Invoke
🔥 字节流要自己分包 串口不保证"一次发一次收"，可能半包 / 粘包，要按协议帧(头+长度)拼
🔥 中文乱码 下位机常用 GBK，上位机默认 UTF-8，要 port.Encoding = Encoding.GetEncoding("GBK")
🔥 忘记 Close() 端口被占用，下次 Open() 抛"拒绝访问"

✏️ 练习

开一个 SerialPort，订阅 DataReceived，把收到的字节数与十六进制打印出来；用虚拟串口工具从对端发一串数据验证。

✅ 答案

var port = new SerialPort("COM3", 9600);
port.DataReceived += (s, e) =>
{
    var sp = (SerialPort)s!;
    int n = sp.BytesToRead;
    byte[] buf = new byte[n];
    sp.Read(buf, 0, n);
    Console.WriteLine($"收到 {n} 字节：{BitConverter.ToString(buf)}");
};
port.Open();
Console.WriteLine("按任意键退出"); Console.ReadKey(); port.Close();

🔗 本项目已含参考实现（可直接读，不必从零）：DaqMonitor.Core/Devices/ 下已有 ISerialChannel/RealSerialChannel/LoopbackSerialChannel/SerialDevice（含 FrameParser.Build 双向建帧 + CRC 校验），并配 5 个单测全绿（单帧/粘包/半包/坏CRC/管道集成）。建议：先读这份实现理清思路 → 自己照着重写一遍加深记忆 → 跑 dotnet test 看那 5 个绿。这就是"边做边学"：你手里的工程已经是能跑的真实代码。

Day 2 — 协议帧解析（把字节流变成业务数据）

一句话讲清楚

裸字节没意义，必须按"协议帧"切包：每个帧有【帧头 + 长度 + 数据 + 校验】，像处理 TCP 粘包一样拼包、校验、提取。

前端类比秒懂

协议解析 前端类比
帧头 0xAA 0x55 自定义二进制协议的分隔符
长度字段 Content-Length / WebSocket 帧头
CRC16 校验 数据完整性校验（类比哈希）

分点精讲

① 拼包缓冲（解决半包 / 粘包）（🟦）

private readonly List<byte> _buffer = new();
private void OnBytes(byte[] chunk)
{
    _buffer.AddRange(chunk);
    while (TryTakeFrame(out var frame))   // 循环拆出所有完整帧
        HandleFrame(frame);
}

② CRC16 校验（🟦，Modbus 也会用，先打好基础）

public static class Crc16
{
    public static ushort Modbus(byte[] data)
    {
        ushort crc = 0xFFFF;
        foreach (var b in data)
        {
            crc ^= b;
            for (int i = 0; i < 8; i++)
                crc = (crc & 1) != 0 ? (ushort)((crc >> 1) ^ 0xA001) : (ushort)(crc >> 1);
        }
        return crc;
    }
}

③ 完整帧示例：AA 55 | Len | Payload... | CRC_L CRC_H

🔬 掰开揉碎：CRC16 到底在算什么（新手最卡的一关）

代码只有 8 行，但「为什么是 0xA001」「为什么初始 0xFFFF」「右移/异或在干啥」——不讲清楚你永远只会抄。 - 它算的是「数据指纹」：发送方把整帧(除 CRC 本身)算出一个 16 位校验值附在末尾；接收方用同样算法重算一遍，比对一致才说明传输没出错（类比：你给文件算个 MD5，对方再算一次对不对得上）。 - 初始值 0xFFFF：所有位先置 1 再开始异或，是为了让「全 0 数据」也能产生非零校验（否则 0 数据校验也是 0，分不清是没传还是传错了）。 - 右移 + 异或 0xA001（每一步在干啥）： 把当前字节和 crc 低 8 位异或 → 看 crc 最低位是不是 1： 是 1 → 右移一位 再 异或 0xA001 （0xA001 是多项式 0x8005 的「按位反转」形式，Modbus 用反转写法） 是 0 → 只右移一位 重复 8 次 = 处理完 1 个字节，循环每个字节

直觉理解：每右移一次，就把数据「喂」进校验寄存器一位；碰到 1 就「搅拌」一下多项式，保证任何 1 个 bit 翻转都会导致最终结果不同。 - 线序坑（本项目测试踩过）：算出的寄存器值是 0x0A84，但 Modbus 先传低字节84、再传高字节0A，所以线上字节顺序是 84 0A，人们常写成「0x840A」。寄存器真值是 0x0A84，本项目 Crc16.Modbus 返回的就是这个（测试断言 0x0A84，不是 0x840A）。 - 查表法为什么快：上面是「计算法」每字节循环 8 次；工业用「256 项预计算表」，每字节直接查表异或，快一个数量级。本项目 FrameParser 用计算法够用，真高频场景再换表。

🧪 手算验证例（自己算一遍才算会，面试硬要求）

用本模块的 Crc16.Modbus 跑一遍，确认输出和手搓帧对得上。

// 算 Modbus 读取请求 01 03 00 00 00 02 的 CRC
ushort crc = Crc16.Modbus(new byte[] { 0x01, 0x03, 0x00, 0x00, 0x00, 0x02 });
byte lo = (byte)(crc & 0xFF);   // 低字节 → C4
byte hi = (byte)(crc >> 8);     // 高字节 → 0B
Console.WriteLine($"{lo:X2} {hi:X2}");   // 运行结果：C4 0B

运行结果：C4 0B —— 和 M2 手搓请求帧补齐后的 01 03 00 00 00 02 C4 0B 一致 ✓。

⚠️ 连「标准答案」都可能错：某份流传的 Modbus 讲义写「01 06 00 01 00 64 的 CRC 是 19 98」——实测是 D9 E1（用上面同样的函数一算便知）。所以 CRC 必须自己会手算/会跑代码验证，不能抄别人的结论。

✏️ CRC 三档练习

  • 🟢 基础题：用 Crc16.Modbus 算 01 06 00 01 00 64（写寄存器 40002 = 100）的 CRC，打印低/高字节。 ✅ 答案：D9 E1（不是网上有些资料写的 19 98）。
  • 🟡 进阶题：写一个 VerifyCrc(byte[] frame)：拆出末尾 2 字节与 Crc16.Modbus(数据部分) 比对，返回 bool。
  • 🔴 挑战题：把 Crc16.Modbus 改成查表法（预生成 256 项表），和原实现跑同一组输入，断言结果一致。

🔬 掰开揉碎：为什么会有「半包 / 粘包」（现场最难查的 bug 源头）

串口是字节流，不保证「你发一次、我收一次」： - 半包：下位机一次发 20 字节，你 DataReceived 可能先收到 5 字节、再 15 字节（系统缓冲没攒够就通知你了）。 - 粘包：下位机连发两帧，你一次收到 40 字节（两帧粘一起）。 - 后果：直接按「收到=一帧」解析 = 偶发乱码/丢数据，现场几周才复现一次，极难查。 - 正解（本项目 FrameParser 的做法）：维护一个 _buffer，来啥都 AddRange 进去，然后循环尝试拆帧（TryTakeFrame 找帧头→读长度→够长才取出），拆不出就留着等下一波；注意：永远拆不出完整帧时（比如收到垃圾头）要清空缓冲，否则缓冲无限增长 = 内存泄漏。

🔬 掰开揉碎：SerialPort 真实项目里的「坑」（光会 Open/Read 不够）

  • DataReceived 在某些机器/某些 USB 转串口上不触发：这是 .NET SerialPort 的已知老毛病（基于 Win32 事件，不稳定）。企业级写法是用 BaseStream.ReadAsync 自己开一个读循环，不依赖 DataReceived： csharp // 现代/稳健写法：不依赖 DataReceived 事件 var buf = new byte[1024]; while (!ct.IsCancellationRequested) { int n = await port.BaseStream.ReadAsync(buf, 0, buf.Length, ct); // 阻塞等数据，异步不卡 UI OnBytes(buf.AsMemory(0, n)); // 喂给帧解析器 }
  • 硬件流控 DTR/RTS：有些下位机要求上位机拉高 DtrEnable/RtsEnable 才肯通信，连不上时检查这个。
  • 跨线程 Close() 崩溃：DataReceived 在后台线程，若在 UI 线程直接 port.Close() 可能和后台读冲突。统一用 CancellationToken 先停止读循环、再 Close()。
  • BytesToRead 一次性读不完：循环读直到 BytesToRead == 0，别只 Read 一次。

⚠️ 重点 & 易踩坑

项 说明
⭐ 一定要处理半包 / 粘包 不处理 = 偶尔丢数据，现场最难查的 bug
⭐ CRC 用查表法更快 上面是计算法，工业可用查表优化
🔥 大小端 下位机可能是小端，读 int 用 BinaryPrimitives.ReadInt32LittleEndian
🔥 缓冲无限增长 永远拆不出完整帧时要清空缓冲，防内存泄漏

✏️ 练习

实现 TryTakeFrame：从 _buffer 找 AA 55 开头、按第 3 字节长度取出完整帧并移除缓冲；校验 CRC。

✅ 答案（骨架）

private bool TryTakeFrame(out byte[] frame)
{
    frame = Array.Empty<byte>();
    int idx = _buffer.IndexOf(0xAA);
    if (idx < 0 || _buffer.Count < idx + 3) return false;
    if (_buffer[idx + 1] != 0x55) { _buffer.RemoveAt(idx); return false; }
    int len = _buffer[idx + 2];
    int total = 3 + len + 2;                 // 头+长+载荷+CRC
    if (_buffer.Count < idx + total) return false;
    frame = _buffer.GetRange(idx, total).ToArray();
    _buffer.RemoveRange(0, idx + total);
    return true;
}
