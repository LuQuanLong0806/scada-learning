Day 1 — BenchmarkDotNet 量化性能 🟡

一句话讲清楚

BenchmarkDotNet 是 .NET 官方压测工具，告诉你"哪个写法快多少 μs、分配了多少字节"——前端类比：Jsben.ch / Vitest bench 但更专业：自动预热、跑多轮、统计 Mean/Median/StdDev、还能反汇编看 JIT 出的机器码。

前端类比秒懂

BenchmarkDotNet 前端类比
[Benchmark] 方法 benchmark.js 的 suite.add('name', fn) / vitest.bench
[Params(8,64,256)] 多档输入 bench 不同 size 的输入数组
Mean / Median / StdDev Chrome Performance 的多轮采样统计
[MemoryDiagnoser]（Allocated 列） Chrome DevTools Memory heap snapshot 对比
[DisassemblerDiagnoser] 看 JIT 编译出的汇编（更底层 than Source Map）
Baseline 比例（Ratio 列） "比基线快 3 倍"的相对值

分点精讲

① 装 BenchmarkDotNet + 第一个压测项目（🟧） 新建一个独立的 Console 项目（别和主工程混在一起，压测项目 Release 跑、主工程 Debug 跑）：

dotnet new console -o src/DaqMonitor.Bench
cd src/DaqMonitor.Bench
dotnet add package BenchmarkDotNet
dotnet add reference ../DaqMonitor.Core   # 引用被压测工程

入口三行（注意要 BenchmarkRunner.Run，不是直接调方法）：

// Program.cs
BenchmarkRunner.Run<CrcBench>();   // 跑完自动在 Results/ 生成 Markdown 报告

② 真实场景：CRC16 两套实现 PK（按位 vs 查表）（🟧🟦） Modbus CRC16 有两种经典实现——按位（M2 写过）和查表法。哪个快？嘴说不算，bench 一下：

using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]                          // 显示 Allocated 字节/Op
public class CrcBench
{
    private byte[] _data = null!;

    [Params(8, 64, 256, 1024)]             // 多档输入：短帧/中帧/长帧
    public int Size { get; set; }

    [GlobalSetup]
    public void Setup() => _data = new byte[Size];

    [Benchmark(Baseline = true)]           // 基线：M2 的按位实现
    public ushort ModbusCrc16_ByBit()
    {
        ushort crc = 0xFFFF;
        foreach (var b in _data)
        {
            crc ^= b;
            for (int i = 0; i < 8; i++)
                crc = (crc & 1) != 0 ? (ushort)((crc >> 1) ^ 0xA001)
                                     : (ushort)(crc >> 1);
        }
        return crc;
    }

    private static readonly ushort[] _crcTable = BuildTable();
    [Benchmark]
    public ushort ModbusCrc16_Table()      // 查表法：空间换时间
    {
        ushort crc = 0xFFFF;
        foreach (var b in _data)
            crc = (ushort)((crc >> 8) ^ _crcTable[(crc ^ b) & 0xFF]);
        return crc;
    }

    private static ushort[] BuildTable()
    {
        var t = new ushort[256];
        for (int i = 0; i < 256; i++)
        {
            ushort crc = (ushort)i;
            for (int k = 0; k < 8; k++)
                crc = (crc & 1) != 0 ? (ushort)((crc >> 1) ^ 0xA001)
                                     : (ushort)(crc >> 1);
            t[i] = crc;
        }
        return t;
    }
}

逐行白话： - [Params(8,64,256,1024)]：跑 4 档——Modbus 一帧典型 8 字节、长一点 64、大块批量 256/1024。这样能看到"小包谁快、大包谁快"。 - [GlobalSetup]：每档参数切之前跑一次，准备数据，不算进测量。 - [Benchmark(Baseline = true)]：标基线，输出里 Ratio 列会显示别的实现相对它几倍。 - [MemoryDiagnoser]：开内存诊断，输出多一列 Allocated Bytes/Op——按位法 0 字节（栈上算），查表法也是 0（表是 static 一次建好）。

跑一下（必须 Release，Debug 会乱算）：

cd src/DaqMonitor.Bench
dotnet run -c Release

典型输出（节选）：

| Method               | Size | Mean      | Ratio | Allocated |
|--------------------- |----- |----------:|------:|----------:|
| ModbusCrc16_ByBit    | 8    |  45.6 ns  |  1.00 |         - |
| ModbusCrc16_Table    | 8    |  18.2 ns  |  0.40 |         - |
| ModbusCrc16_ByBit    | 1024 | 5,180 ns  |  1.00 |         - |
| ModbusCrc16_Table    | 1024 | 2,050 ns  |  0.40 |         - |

怎么读：查表法比按位快 2.5 倍（Ratio 0.40），而且大小包都稳——这就是 1000Hz 采集该选的实现。

③ MemoryDiagnoser 看分配：struct vs class、Span vs byte[]、Channel vs ConcurrentQueue（🟦） 这三个对比是面试高频，bench 一次你终身记得：

[MemoryDiagnoser]
public class AllocBench
{
    [Benchmark(Baseline = true)]
    public SensorPoint_Class ReturnClass() => new() { Id = 1, Value = 42.0 };

    [Benchmark]
    public SensorPoint_Struct ReturnStruct() => new() { Id = 1, Value = 42.0 };

    // Span<T> 切片 vs byte[] + MemoryStream
    [Benchmark]
    public int SpanSlice()
    {
        var buf = new byte[1024];
        var slice = buf.AsSpan(64, 128);    // 0 字节分配
        return slice.Length;
    }

    [Benchmark]
    public int MemoryStreamCopy()
    {
        var buf = new byte[1024];
        using var ms = new MemoryStream(buf, 64, 128);   // 多一个对象
        return (int)ms.Length;
    }
}

输出会告诉你：struct 走栈、Allocated = -；class 上堆、Allocated = 24 B（每 Op 多 24 字节）。1000Hz 下你一秒就多 24KB 垃圾，GC 立刻被催。这就是为什么 M5/M9 推 readonly struct SensorPoint。

⚠️ 重点 & 易踩坑

项 说明
⭐ 必须 Release 跑 Debug 编译没优化，结果差 10 倍都是常事；CI 里加 -c Release
⭐ 自动预热不要手动循环 别自己写 for i=0..1e6 跑计时——JIT 第一遍冷、第二遍热，BND 自动预热
🔥 Dead code elimination 单纯 var x = Compute() 不用 x，JIT 会把整段删掉→测出"0ns"，要用 _ = Compute() 或 [Benchmark] 返回值
🔥 异常路径贵 100x try/catch 包热路径、且不抛还好；一旦抛异常，单 Op 多 1μs 起
🔥 GC 噪声会让 StdDev 飙 单次跑波动大，看 Median 比 Mean 稳；StdDev 大于 Mean 的 10% 说明干扰大，关其他进程重跑
🔥 JIT 分层编译 加 [MethodImpl(MethodImplOptions.NoOptimization)] 会反优化；别在 bench 方法上加奇怪 Attribute

Day 2 — 实时监控 + 内存泄漏排查 🔴

一句话讲清楚

dotnet counters 是命令行实时仪表盘（GC/堆/线程/自定义业务指标），dotnet trace 抓火焰图，dotMemory 抓堆快照找"只增不减"的泄漏——前端类比：Chrome Task Manager + Performance 火焰图 + Memory Profiler，全套搬到 .NET。

前端类比秒懂

.NET 工具 前端类比 用途
dotnet counters monitor Chrome Task Manager 实时看 CPU/GC 堆/线程数
dotnet trace Performance 火焰图 CPU 采样找热点
dotnet dump + SOS Heap snapshot CLI 抓堆、找对象引用链
JetBrains dotMemory Memory Profiler（GUI） 双快照对比找泄漏
PerfView 高级 Lighthouse 免费但学习曲线陡
自定义 EventCounter performance.mark() 上报业务指标 上报队列长度、批次大小

分点精讲

① dotnet counters 实时看 GC / 堆 / 线程（🟧 全平台命令行） 先全局装一次：

dotnet tool install -g dotnet-counters
dotnet tool install -g dotnet-trace       # 顺便装上
dotnet tool install -g dotnet-dump        # 顺便装上

启动你的 DAQ Monitor，另开终端：

# 找到你的进程
dotnet counters ps

# 实时监控（-n 是进程名，--counters 指定要看的指标类别）
dotnet counters monitor -n DaqMonitor.UI --counters System.Runtime

屏幕会实时滚动（每秒刷新）：

System.Runtime
    CPU Usage (%)                                 12
    Working Set (MB)                             184
    GC Heap Size (MB)                              42.3
    Gen 0 GC / 1 sec                               3.2     ← 关注！每秒 3 次 Gen0
    Gen 1 GC / 1 sec                               0.1
    Gen 2 GC / 1 sec                               0       ← Gen2 必须接近 0
    Time in GC (%)                                 4.8
    ThreadPool Thread Count                       12
    Monitor Lock Contention / sec                  2.1     ← 锁竞争高？警惕

怎么看： - GC Heap Size 一直涨不回落 → 内存泄漏（看 Day 2 后半段）。 - Gen 2 GC / 1 sec > 0 → 大对象频繁进老年代，最致命——多半是 new byte[大] 没复用。 - Monitor Lock Contention 高 → 多线程在抢同一个 lock，M0 并发那块要回顾。 - Time in GC (%) > 10% → GC 占用过多 CPU，分配太频繁，回去加 struct / 池化。

② 自定义 EventCounter：上报业务指标（队列长度、批次大小）（🟦） 系统指标不够用——你想知道"采集管道里堆了多少点""每批多大"。这就要 EventCounter：

// src/DaqMonitor.Core/Metrics/PipelineMetrics.cs
using System.Diagnostics.Tracing;

[EventSource(Name = "DaqMonitor-Pipeline")]
public sealed class PipelineMetrics : EventSource
{
    private readonly EventCounter _queueLength;
    private readonly PollingCounter? _batchSizeAvg;     // 平均批量

    public static readonly PipelineMetrics Instance = new();

    public PipelineMetrics()
    {
        _queueLength = new EventCounter("QueueLength", this)
        {
            DisplayName = "管道队列长度",
            DisplayUnits = "个"
        };
    }

    [Event(1)]
    public void RecordQueueLength(int len) => _queueLength.WriteMetric(len);

    public void ReportBatch(int size)
    {
        _queueLength.WriteMetric(size);   // 每次 Flush 后报当前批量
    }
}

管道里调用（呼应 M9 Day 3）：

private void Flush()
{
    List<SensorPoint>? batch = null;
    lock (_gate) { /* ... */ }
    if (batch is not null)
    {
        PipelineMetrics.Instance.ReportBatch(batch.Count);   // 上报业务指标
        BatchReady?.Invoke(this, batch);
    }
}

监控它：

dotnet counters monitor -n DaqMonitor.UI --counters DaqMonitor-Pipeline

前端类比：这就是 performance.mark('flush') + measure，但能从命令行/容器里实时看，不依赖 UI。

③ dotMemory 抓双快照对比，找"只增不减"的对象（🟧 GUI） 工业程序跑 7 天内存涨到 OOM，99% 是泄漏。排查流程： 1. 启动程序，连上设备，等初始化结束（5 分钟，让"一次性分配"过去）。 2. dotMemory Attach 到进程，抓快照 1（baseline）。 3. 让程序跑它的典型工作负载 30 分钟（采集 + 报警 + 上云）。 4. 抓快照 2。 5. 选 "Compare Snapshots" → 看 Surviving Objects（快照 2 比 1 多出来的）。

典型报告会告诉你： - EventHandler 多了 5000 个 → 事件忘退订（最常见）。 - List<SensorPoint> 持续涨 → static 容器没清理。 - Timer 多了 200 个 → 每次重连 new Timer 没释放旧的。

④ 4 种典型内存泄漏（必背）

泄漏 1：事件订阅忘退订（呼应 M3）

// ❌ 错的：每次重连都 +=，旧 handler 持有旧 device 引用
public void Reconnect()
{
    _device.DataReceived += OnData;     // 第 10 次重连 = 10 个 handler 持有 10 个旧 device
}

// ✅ 对的：先退订再订阅
public void Reconnect()
{
    if (_device is not null) _device.DataReceived -= OnData;
    _device = new ModbusDevice();
    _device.DataReceived += OnData;
}

泄漏 2：static 字段持 List 无限增长

// ❌ 错的：永远只 Add，从不 Trim
public static class GlobalBuffer
{
    public static List<SensorPoint> All = new();   // 跑 7 天涨到 GB 级
}

// ✅ 对的：限长 + 旧数据落盘后清掉
public static class GlobalBuffer
{
    private static readonly LinkedList<SensorPoint> _buf = new();
    public static void Add(SensorPoint p)
    {
        _buf.AddLast(p);
        while (_buf.Count > 10_000) _buf.RemoveFirst();   // 滑动窗口
    }
}

泄漏 3：字典 key 元数据（Tuple / string）没释放

// ❌ 错的：key 用 $"{deviceId}-{DateTime.Now.Ticks}"，每次都不一样，字典只增不减
_cache[$"{id}-{DateTime.Now.Ticks}"] = value;

// ✅ 对的：用 MemoryCache 设过期，或自己定时清理
_cache.Set(id, value, TimeSpan.FromMinutes(5));

泄漏 4：Timer 回调闭包持有引用

// ❌ 错的：闭包持有 this，Timer 不停 → this 永不释放
public class BadWorker
{
    public void Start()
    {
        var timer = new Timer(_ => DoWork(), null, 1000, 1000);
        // 没 Dispose timer，它持有 this 引用
    }
}

// ✅ 对的：实现 IDisposable，Dispose 时关 Timer
public sealed class GoodWorker : IDisposable
{
    private readonly Timer _timer;
    public GoodWorker() => _timer = new Timer(_ => DoWork(), null, 1000, 1000);
    public void Dispose() => _timer.Dispose();
}

⚠️ 重点 & 易踩坑

项 说明
⭐ Finalizer 隐藏引用 C# 析构函数 ~Class() 会让对象多活一代，频繁写 finalizer 会卡 GC 线程
🔥 异步 lambda 捕获 device.Connect += async () => await X() 闭包持有引用，事件不退订永远活着
🔥 WeakReference 不是免死金牌 用错（如订阅 WeakEvent 系统却持有强引用）照样泄漏
🔥 static 容器是泄漏大户 任何 static List/Dict 都要限长或定期清，否则撑到 OOM
🔥 Timer 不 Dispose new Timer(callback, ...) 不 Dispose 就一直持引用；IDisposable 模式别省
⭐ dotMemory 看 Retention Path 不只看"对象多"，要看"谁持有它"——Retention Path 是定位泄漏的关键

🧪 三档练习

🟢 基础题：启动 DAQ Monitor，dotnet counters monitor 观察 GC Heap Size 跑 5 分钟的曲线，截图。要求 Gen 2 GC 一直是 0。

🟡 进阶题：给 AcquisitionPipeline 加 PipelineMetrics（队列长度 EventCounter），从 dotnet counters monitor 实时看到队列长度变化。

🔴 挑战题：故意制造一个泄漏版本（在 MainViewModel 里订阅一个 static event 不退订），用 dotMemory 抓两个快照对比，定位到具体是哪个对象、哪条 Retention Path。然后改成正确写法，再抓一次快照验证泄漏消失。

✅ 答案（基础题） 正常曲线：GC Heap Size 在某个范围波动（20-50MB），不单调上升。Gen 2 GC 始终 0。如果一直涨——就是泄漏，回 Day 2 ④ 四个模板对一遍。

💡 工控导师说：我审过一段代码——程序跑 3 天内存涨到 2GB，工厂被迫每周重启一次。后来用 dotMemory 抓两个快照一对比，是 static event 每次重连都订阅一次没退订。改一行 -= 修好，省下每次重启的 30 分钟停机。这就是性能工程的真金白银。

🎓 职业建议："你怎么排查内存泄漏？"是中高级岗面试必问。答"用 dotMemory 抓两个快照，看 Surviving Objects + Retention Path；常见 4 类：事件忘退订、static 容器、字典 key 没清、Timer 不 Dispose"——这一套术语一出口，面试官直接把你归到"真上过生产"的档。

Day 3 — 长跑稳定性策略（限流 / 降级 / 熔断 / 自愈）🔴

一句话讲清楚

工业系统跑 7×24 不崩 = 限流（防压垮）+ 降级（备路兜底）+ 熔断（防雪崩）+ 心跳（主动探活）+ 自愈（自动重连）+ 监控（事后追溯）——前端类比：Service Worker 离线缓存 / PWA 降级页面 / 请求限流 / Sentry 上报。

前端类比秒懂

上位机长跑策略 前端类比
Channel 有界 + DropOldest axios 拦截器丢弃过期请求
DB 挂 → 内存兜底 Service Worker 缓存兜底

分点精讲

① 限流：Channel 有界 + DropOldest（采集永远不停）（🟦，呼应 M0/M9） 无界 Channel 是"只要生产够快，内存管够"——一旦消费端卡顿（DB 慢查询），内存爆。生产级必须有界：

var channel = Channel.CreateBounded<SensorPoint>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.DropOldest,   // 队列满丢最旧，采集不停
    SingleReader = false,
    SingleWriter = false
});

// 写入端（采集线程）
public void OnDataReceived(SensorPoint p)
{
    // TryWrite 不阻塞：满就丢，采集线程绝不卡
    if (!channel.Writer.TryWrite(p))
        Interlocked.Increment(ref _droppedCount);   // 记丢了多少，监控用
}

为什么 DropOldest 不是 Wait：工业现场"实时值"最重要——宁可丢老的，也不能让采集线程被卡住漏掉新值。这和后端 Web 不同（后端是 Wait 排队），采集系统永远要先保新数据。

② 降级：DB 挂了走内存兜底，设备掉线用模拟值占位（🟦）

// 持久化降级：DB 异常 → 内存队列暂存 + 后台重试
public async Task SaveAsync(IEnumerable<SensorPoint> batch)
{
    try
    {
        await using var db = _dbFactory.CreateDbContext();
        db.Points.AddRange(batch.Select(p => p.ToEntity()));
        await db.SaveChangesAsync();
    }
    catch (Exception ex)        // DB 挂了
    {
        _log.Warning(ex, "DB 不可用，转入内存兜底 {Count} 条", batch.Count());
        _inMemoryFallback.AddRange(batch);    // 暂存
        _dbAvailable = false;                  // 触发后台重试
    }
}

// 后台任务：每 30s 试着重连 DB
private async Task DbReconcileLoopAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        await Task.Delay(30_000, ct);
        if (!_dbAvailable && _inMemoryFallback.Count > 0)
        {
            try
            {
                await using var db = _dbFactory.CreateDbContext();
                db.Points.AddRange(_inMemoryFallback.Select(p => p.ToEntity()));
                await db.SaveChangesAsync();
                _inMemoryFallback.Clear();
                _dbAvailable = true;
                _log.Information("DB 恢复，已重放 {Count} 条", _inMemoryFallback.Count);
            }
            catch { /* 还没好，下次再试 */ }
        }
    }
}

③ 熔断：连续失败 5 次 → 停 30s 重连（防雪崩）（🟦） 为什么需要熔断：设备挂了你每秒重试 1000 次，把现场总线打死、把 CPU 跑满。熔断 = 失败到一定阈值就主动"歇一会"：

public sealed class CircuitBreaker
{
    private int _failures;
    private DateTime _openUntil = DateTime.MinValue;
    private readonly int _threshold;          // 失败阈值
    private readonly TimeSpan _openDuration;  // 熔断时长

    public CircuitBreaker(int threshold = 5, TimeSpan? openDuration = null)
    {
        _threshold = threshold;
        _openDuration = openDuration ?? TimeSpan.FromSeconds(30);
    }

    public bool IsClosed => DateTime.UtcNow >= _openUntil;   // 闭=可调用

    public void RecordSuccess()
    {
        Interlocked.Exchange(ref _failures, 0);
        _openUntil = DateTime.MinValue;
    }

    public void RecordFailure()
    {
        if (Interlocked.Increment(ref _failures) >= _threshold)
        {
            _openUntil = DateTime.UtcNow + _openDuration;
            // 触发回调：广播设备离线、记日志
        }
    }
}

// 使用：在 Retry 外面再包一层熔断
if (_breaker.IsClosed)
{
    try { await _device.ReadAsync(); _breaker.RecordSuccess(); }
    catch { _breaker.RecordFailure(); /* 连续 5 次后停 30s */ }
}
else
{
    _log.Warning("熔断中，跳过读取，{Sec} 秒后重试",
        (_openUntil - DateTime.UtcNow).TotalSeconds);
}

④ 心跳：每 5s 发 0x00，3 次无响应判离线（🟦，M9 Day 4⑤ 已落地） M9 的 DeviceHealthMonitor 已经完整实现——主动探活，别信 IsConnected。这里复习关键参数：

参数 推荐值 说明
心跳间隔 3~10s 太短压设备，太长发现掉线慢
判离线阈值 连续 2~3 次 防 1 次抖动误判
重连退避 1s→2s→4s...→封顶 30s 指数退避别死循环

⑤ 自愈：设备掉线 → 自动重连，Redis 挂 → 走内存（🟦） 自愈 = 系统检测到故障后自动恢复到可用状态，不需要人工重启。组合上面 ① ~ ④：

心跳探活 → 检测掉线 → 熔断打开（停 30s）→ 退避重连 → 成功后熔断关闭 → 恢复采集
                          ↓（DB/Redis 挂）
                     降级走内存/模拟值

关键：故障期间 UI 仍然能显示"上次值 + 离线标记"，而不是白屏崩溃。这就是 7×24 的真正含义——永远不挂，最多降级。

⚠️ 重点 & 易踩坑

项 说明
⭐ 限流先于优化 别等性能不够才限流——先限流保命，再优化提性能
⭐ 降级要可见 UI 上明示"DB 异常 / 数据缓存中"，别让操作员以为系统正常
🔥 熔断阈值要合理 太敏感（失败 1 次就熔断）= 频繁中断；太迟钝 = 不熔断等于没装
🔥 重连退避必须封顶 Math.Min(delay, 30s)——不然指数涨到几分钟，现场等不起
🔥 日志文件别无限增长 retainedFileCountLimit + fileSizeLimitBytes 必须设，否则一周塞满磁盘
⭐ 故障期间采集不停 数据可以丢（DropOldest），但采集线程绝不能因为下游故障而停摆

🧪 三档练习

🟢 基础题：把 M9 的 AcquisitionPipeline 从 Channel.CreateUnbounded 改成 Channel.CreateBounded(1000, DropOldest)，并加一个 _droppedCount 计数器，每次丢弃 +1。

private readonly Channel<SensorPoint> _channel =
    Channel.CreateBounded<SensorPoint>(new BoundedChannelOptions(1000)
    {
        FullMode = BoundedChannelFullMode.DropOldest
    });
private int _droppedCount;

public void Enqueue(SensorPoint p)
{
    if (!_channel.Writer.TryWrite(p))
        Interlocked.Increment(ref _droppedCount);
}
public int DroppedCount => _droppedCount;   // 通过 PipelineMetrics 上报
