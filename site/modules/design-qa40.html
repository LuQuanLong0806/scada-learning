项目设计决策问答 40 问(面试官的"为什么"题库)

来源:DaqMonitor(R1-R8)+ MotionControl(MC1-MC6)全部「🏗️ 为什么这样设计」决策块的集中背诵版。 为什么有这一篇:面试官区分"敲过项目的人"和"设计过项目的人",靠的就是追问"为什么这样设计、不用别的方案"。这 40 问每问都是"备选方案 → 为什么选它 → 不这样会怎样"的完整决策链。 用法:每做完一篇实践,回头过对应分区;面试前一天全量过一遍,每问脱稿说满 1 分钟。配套:语言八股见《面试问答_逐字稿_30题》,项目叙事见每篇末尾「🎤 面试怎么讲」。

一、架构与分层(8 问)

Q1 · 为什么 Core/UI/Tests 三层,依赖只从外向内?

  • 决策:编译方向=依赖方向——UI、Tests 引用 Core,Core 谁也不引用。
  • 备选:单项目全塞一起(建得快,但换皮/无界面测试都要大改,测试得加载 XAML)。
  • 🎤:"我分层的原则是编译方向=依赖方向:UI 引用 Core、Core 谁也不引用。Core 可以被 WPF、WinForms 或无界面服务任意复用,测试也只测 Core 不碰 UI。"
  • 详解:R1

Q2 · 为什么目标框架 net8.0 + RollForward,而不是本机最新的 net10?

  • 决策:LTS 对齐企业部署;RollForward.Major 允许"用 8 编译、用 10 运行"。
  • 备选:net10.0 零配置(STS 18 个月 EOL;客户工控机多装 LTS 运行时)。
  • 🎤:"目标框架选 LTS 的 net8.0 对齐企业部署习惯,本机高版本运行时靠 RollForward 向前兼容——目标旧、运行新可以,反过来必炸。"
  • 详解:R1

Q3 · SensorPoint 为什么是 struct、字段为什么直接公开?

  • 决策:采样点"小、短命、海量"——栈分配零 GC;值拷贝=天然快照;纯数据载体不需要属性封装。
  • 备选:class(引用语义好改,但 100Hz 堆分配让 Gen0 GC 每分钟上千次;到处判 null)。
  • 代价要认:List 索引器返回副本必须整取整存;字段忘赋是默认值(Timestamp 0001 年)——项目里显式抄时间戳就是对策。
  • 🎤:"SensorPoint 是 4 字段 struct:高频采集避免 Gen0 抖动、值语义是快照;struct 的坑我踩过也管住了——索引器副本、默认值,代码里都有对应处理。"
  • 详解:R1

Q4 · 设备状态为什么三态枚举而不是 bool IsOnline?

  • 决策:Offline/Connecting/Online 三态是状态机最小完备集,握手中间态必须让用户看见。
  • 备选:bool(把"正在连"显示成"离线",操作员连点重连→双开连接任务抢串口)。
  • 🎤:"设备状态我做三态不是 bool:握手是用户必须看得见的中间态,UI 状态灯的黄灯闪烁就是它驱动的;bool 会诱导操作员重复点连接。"
  • 详解:R1

Q5 · 设备接口为什么是同步门面,不做成全 async?

  • 决策:设备指令低频毫秒级,async 的传染成本(ViewModel/测试/回调全要 async,一处 .Result 就死锁)远大于收益;真正不能卡的采集循环在 Task.Run 后台线程,和接口签名无关。
  • 🎤:"设备接口我刻意做成同步门面:设备指令低频且毫秒级,async 传染成本远大于收益;UI 不卡靠的是采集在后台线程,不是接口 async。异步用在刀刃上,不是 everywhere。"
  • 详解:R2

Q6 · 设备给上层为什么用事件推送,而不是轮询 Read()?

  • 决策:采集是持续数据流,推送让频率由设备定、多订阅方(管道+UI+诊断)零成本。
  • 备选:轮询(周期配低丢数据、配高浪费;各消费方自己起定时器、时间戳各盖各的)。
  • 🎤:"设备到上层我用事件不用轮询:推送让频率由设备定、多订阅方零成本;轮询无论周期设多少,不是丢数据就是浪费,还破坏单一时间源。"
  • 详解:R2

Q7 · 为什么第二个类是"模拟设备",而不是直接写真串口?

  • 决策:行业现实是开发期经常没有真设备——模拟与真实共用 IDevice,全链路先行,真机到了只换 new 的那一行;单元测试和 CI 也不依赖硬件。
  • 🎤:"我先写模拟设备再接真机——设备开发期经常不在手上,共用接口让全链路先跑通,真机到了只换一行;测试也因此不依赖硬件。"
  • 详解:R2 / R4

Q8 · 协议解析为什么独立成纯函数层,不写进设备类?

  • 决策:IDevice 拆"谁提供数据",协议层拆"字节怎么变数值"——两个变化方向;纯逻辑零 IO,半包/粘包/坏帧/字节序全部不插硬件就能穷举测试。
  • 🎤:"协议解析独立成纯函数层:字节进数值出、零 IO 依赖,拆包的坑全部纯单测覆盖;换传输方式解析层原样复用。"
  • 详解:R3

二、通信与协议(6 问)

Q9 · CRC 为什么自己写 15 行不用库?为什么 CRC 不是累加校验和?

  • 决策:Modbus CRC16 规范定死(0xA001/初值 FFFF/低字节在前),手写参数可控+已知向量验证;CRC 抓得住字节换序,累加和抓不住。
  • 🎤:"帧校验用 CRC16 不是累加和:累加和检测不到换序,CRC 指纹特性保证任意 1 位翻转必被抓住;15 行手写配规范样例向量,比引库再对参数更可控。"
  • 详解:R3

Q10 · 拆帧为什么是流式蓄水池(Feed + TryTakeFrame),不是一次性 Parse?

  • 决策:串口/TCP 给的是字节流不保证帧边界——Feed 攒缓冲、TryTakeFrame 循环切,半包等下批、粘包多切几条。
  • 备选:一次性 Parse(测试里整帧喂入全绿,现场随机丢数据——最难排查的 bug)。
  • 🎤:"拆帧我做成流式:传输层不保证帧边界,先攒后切,半包等下批粘包多切;一次性 Parse 只在测试里成立,现场必丢数据。"
  • 详解:R3

Q11 · 串口帧用 AA55 帧头+CRC,TCP 帧为什么改成长度前缀?

  • 决策:帧格式跟传输介质走——串口有干扰用魔数帧头硬同步;TCP 可靠有序,长度前缀一次定位、载荷里出现什么字节都不怕。解析器还做成无状态纯函数,一个类服务多个连接。
  • 🎤:"帧格式跟介质走:串口不可靠用帧头加 CRC 硬同步;TCP 可靠有序用长度前缀一次定位。解析器无状态、缓冲归调用方,多连接复用同一个类。"
  • 详解:R3

Q12 · 设备为什么不直接用 SerialPort,中间隔一层 ISerialChannel?

  • 决策:SerialDevice 管协议不该关心字节从哪来;LoopbackSerialChannel 让"请求-响应"全时序(延迟/坏帧/超时)零硬件穷举测试。
  • 备选:直接 new SerialPort(测试要装虚拟串口对,CI 跑不了)。
  • 🎤:"协议和链路我分开抽:设备只认 ISerialChannel,生产真串口、测试内存回环——串口全时序不插硬件就能测,这是 axios 换 msw 的同一个思路。"
  • 详解:R4

Q13 · Modbus 为什么手搓 RTU 帧,不用 NModbus 库?

  • 决策:只用 03/06/16 三个功能码,百行代码换全链路白盒——现场抓包能逐字节解释;判定依据是"用的深度"不是"手搓瘾",要全功能码就立刻换库。
  • 🎤:"Modbus 我手搓没用库:只用三个功能码,百行换全链路白盒,异常码、字节序都能逐字节调试;什么时候该换库我也清楚——用得深了控制力的收益就不抵维护成本了。"
  • 详解:R4

Q14 · 断线重连为什么指数退避?心跳为什么必须自己发?

  • 决策:固定间隔=故障期匀速敲门,恢复瞬间惊群;退避让重试密度递减。TCP 是惰性协议,对端断电不通知——半开连接只能靠 10s 心跳+30s 超时判死。
  • 🎤:"重连用指数退避防惊群;心跳必须应用层自发——对端断电 TCP 不通知你,半开连接靠心跳超时才能及时判死,WebSocket 的 ping/pong 是同一个解。"
  • 详解:R4

三、异步与并发(4 问)

Q15 · 缓冲为什么用 Channel,不用 ConcurrentQueue 或 ObservableCollection?

  • 决策:Channel 是官方生产者-消费者原语:线程安全之外还有异步挂起唤醒(没数据不占线程)、Complete 完成语义、取消配合;ObservableCollection 跨线程 Add 直接异常。
  • 🎤:"管道缓冲用 Channel:await foreach 没数据时异步挂起零线程开销,还有完成/取消语义;ConcurrentQueue 要自己管轮询节拍,ObservableCollection 跨线程直接崩。"
  • 详解:R5

Q16 · 采集管道为什么"构造即启动",不给 Start/Stop?

  • 决策:管道是常驻基础设施,生命周期=容器生命周期——引用在手必在消费,把"忘启动"这类静默错误从结构上消灭;按需启停在设备层做。
  • 备选:显式 Start(忘了调,系统"看起来正常"但曲线永远空白——无报错不工作的 bug 比崩溃难查一个量级)。
  • 🎤:"管道做成构造即启动、Dispose 即停:常驻服务的启动不该依赖每个调用点记得调;真正按需的启停在设备层,每层管自己的生命周期。"
  • 详解:R5

Q17 · 事件回调里为什么只做 TryWrite 一件事?

  • 决策:1000 事件/秒时回调越短,设备线程越不被拖住——重活(刷 UI/落库)全部留给后台批量消费。
  • 🎤:"事件回调只做入队一件事:设备线程的回调每多干一毫秒,采集就慢一毫秒,重活全部推给管道批量消费。"
  • 详解:R5

Q18 · 锁内为什么只干纳秒级的事(自增/换包),重活全部锁外?

  • 决策:锁内干得越少竞争越少——R5"锁内换包、锁外触发 BatchReady"、R7"锁内自增计数、锁外 Append 日志"同一条纪律。
  • 🎤:"锁里只做不可再分的最小动作:换列表引用、自增整数,然后放锁再干可能慢的活——锁的持有时间决定竞争强度。"
  • 详解:R5 / R7

四、报警规则(2 问)

Q19 · 报警规则为什么是数据字段,不是 Func 谓词?

  • 决策:阈值是现场调出来的配置——要能 UI 编辑、JSON 序列化存盘;谓词改一次阈值就改代码发版。配置数据化是工程软件和 demo 的分水岭。
  • 🎤:"报警规则我做成纯数据字段:阈值是现场调的配置,要能编辑要能存盘;谓词函数把配置变成了代码。"
  • 详解:R5

Q20 · 报警判断为什么必须回滞+边沿,不能纯阈值?

  • 决策:阈值附近信号必抖(100 上下飘 0.5 → 1 秒报 50 条刷屏);回滞把恢复门槛拉到 Threshold−Hysteresis 吸收抖动,边沿只在"正常→报警"跃迁时报一次——工业报警标配防抖。
  • 🎤:"报警加回滞和边沿:阈值附近信号必抖,纯阈值一秒几十条把真报警淹没;回滞吸收带内抖动、边沿只在跃迁时报,这是温控器、烟感通用的工业做法。"
  • 详解:R5

五、持久化(3 问)

Q21 · 为什么要"双写"(内存+数据库),不直接读写库?

  • 决策:实时表(微秒)和历史查询(毫秒)延迟要求差三个数量级——内存字典伺候实时+报警,Channel 写泵串行落 SQLite;崩机只丢队列尾巴几条,风险有界。
  • 🎤:"存储双写:内存层伺候实时和报警,写泵串行落库伺候历史——两条链路延迟要求差三个数量级,拆开各自满足;SQLite 单写者也靠串行写泵天然化解。"
  • 详解:R6

Q22 · DbContext 为什么用 IDbContextFactory 现造现弃,不做单例?

  • 决策:DbContext 非线程安全——写泵和历史查询是两个并发场景;短命上下文线程安全、变更跟踪即用即弃。单例会随机抛 second operation 异常(不定时崩,最难查)。
  • 🎤:"DbContext 用 factory 按需创建用完即弃:写泵和查询并发,而它非线程安全;短命上下文还不积累跟踪缓存,这是正确性设计不是性能优化。"
  • 详解:R6

Q23 · 为什么选 SQLite,不是 SQL Server 或时序库?

  • 决策:上位机交付形态是"拷文件夹到断网工控机就能跑"——嵌入式零部署、备份=拷文件;单写者限制已被串行写泵化解,单机采集量远未到天花板。
  • 🎤:"落库选 SQLite:断网车间现场没有 DBA,零部署压倒一切;要多机共享时,EF Core 换个 provider 就迁 PostgreSQL。"
  • 详解:R6

六、容错与诊断(2 问)

Q24 · 重试为什么抽成公共类?为什么要加随机抖动?

  • 决策:横切关注点只留一份策略真相;指数退避防猛敲故障设备,抖动防多客户端同步重试形成雪崩(react-query、AWS SDK 同款)。
  • 🎤:"重试抽公共类:退避节奏全项目一份真相;指数退避加抖动是标配——固定退避下 100 个客户端会在同一毫秒集体涌回,把刚恢复的服务再打挂。"
  • 详解:R7

Q25 · 诊断日志为什么构造时抓 SynchronizationContext、写时 Post?

  • 决策:WPF 绑定集合只许 UI 线程改(真实修过的 bug:后台 Add 当场异常)——把线程规则关进类里,调用方无感;用 SynchronizationContext 不用 Dispatcher,因为 Core 层不许依赖 WPF 类型。
  • 🎤:"诊断服务构造时抓 UI 上下文快照,后台写日志类内部自动 Post 回 UI 线程——线程安全是类的责任不是每个调用者的责任;选 SynchronizationContext 是为了 Core 不反向依赖 WPF。"
  • 详解:R7

七、WPF 主界面(7 问)

Q26 · 整个界面为什么走 MVVM,不把事件写在 code-behind?

  • 决策:客户改界面极频繁——MVVM 把"长什么样"和"什么逻辑"切开;VM 无控件引用可以纯 new 就测;数据流统一"数据→VM→绑定→控件"。
  • 前端同源:React 的 render(state) 就是这个思想,WPF 2005 年就内建了。
  • 🎤:"界面走 MVVM:View 只绑定、逻辑全在 VM——可脱离 UI 单测、改界面不动逻辑;本质是声明式 UI,和 React 同一个思想。"
  • 详解:R8

Q27 · 命令为什么包 RelayCommand,不直接 Click 事件?

  • 决策:把"点击"变成 VM 属性——执行体和 CanExecute 都在 VM(可单测);CanExecute=false 按钮自动灰;一个命令多处绑定。
  • 🎤:"按钮用 Command 不用 Click:命令成为 VM 的属性,VM 不引用控件可以纯测,CanExecute 自动灰按钮——从事件回调换成可绑定可测试的意图声明。"
  • 详解:R8

Q28 · UI 表格为什么绑 PointView(class),不直接绑 SensorPoint(struct)?

  • 决策:WPF 刷新靠 PropertyChanged 事件,struct 值拷贝发不出通知——Core 为性能用 struct,UI 为通知用 class+OnChanged,两套形状各司其职,中间一道转换是 MVVM 标准件。
  • 🎤:"Core 和 UI 各有各的数据形状:SensorPoint struct 为零 GC,PointView class 每属性带通知——两层各要各的,转换不是冗余是分工。"
  • 详解:R8

Q29 · 仪表盘/状态灯为什么自绘控件,不用现成库?

  • 决策:工业客户有"照旧软件长"的像素级迁移要求——Control+Generic.xaml 把外观(模板)和逻辑(角度换算)分离,换皮不换逻辑;依赖属性让控件和 TextBlock 一样可绑定。
  • 🎤:"仪表自绘:继承 Control、外观全在 Generic.xaml、对外只暴露依赖属性——风格换模板就行,数值一动指针自己转;会依赖属性+模板才算摸到 WPF 核心机制。"
  • 详解:R8

Q30 · 实时曲线为什么自管 600 点滚动缓冲、对外只开 Push?

  • 决策:滚动缓冲(超限 RemoveAt(0))让内存有界、画面像心电图左移;这层逻辑放 VM 会沾图表库类型,放 XAML 写不了循环——控件自包含、可整体搬走。
  • 🎤:"曲线控件自管滚动缓冲、对外只开 Push 一个口:内存有界、控件可复用,VM 不沾图表库类型。"
  • 详解:R8

Q31 · 演示模式和真实数据通路为什么必须严格分家?

  • 决策:真实修过的 bug——AttachChart 顺手调了 StartDemo(),没启动采集曲线也跳随机数。纪律:演示和真实是两条线,接了真实通路必须关演示入口(单一显式开关)。
  • 前端同源:忘关 mock、上线还在吐假数据,同一个经典 bug。
  • 🎤:"这里修过一个真 bug:演示模式被顺手调用,曲线在吐随机数。从此定死规矩——演示通路和真实通路绝不并存,mock 必须有显式单一开关。"
  • 详解:R8

Q32 · 批量刷新为什么一次 Dispatcher.Invoke 包整批,不每条 Invoke 一次?

  • 决策:跨线程切换本身有开销——一批 500 点切一次线程,循环在 UI 线程内跑完;每条 Invoke 等于 500 次线程往返,批量优化的意义全没了。
  • 🎤:"批量更新一次 Dispatcher.Invoke 包整批:跨线程一次、批内循环——每条 Invoke 一次等于把批量优化又还给线程切换。"
  • 详解:R8

八、WinForms 与运控(8 问)

Q33 · 运动指令失败为什么走返回码,不走异常?

  • 决策:没使能、超限位、断线是业务常态不是异常路径——返回码让失败处理显式平铺;枚举负数值还和固高/雷赛真卡 SDK 对齐,换真卡上层不改。
  • 🎤:"运动指令用返回码:失败是业务常态,每个调用点 if 判断显式处理;枚举对齐真卡 SDK 的 int 返回,换真卡判断逻辑一行不改。"
  • 详解:MC1

Q34 · 模拟"运动"为什么用节拍循环,不 Sleep 到终点?

  • 决策:模拟的价值在于像真——节拍循环产生连续中间状态:UI 看得到数字一格格走、急停能中途冻结、测试能断言"停在半路"。Sleep 版全绿,换真机第一次急停就暴露没处理过中途状态。
  • 🎤:"模拟卡用节拍循环:真卡运动是连续过程,急停要能中途打断、测试要能断言中间状态——省事版模拟会把时序问题留到真机一次性爆出来。"
  • 详解:MC1

Q35 · 12 个测试为什么按"行为"组织,不按方法覆盖?

  • 决策:卡的正确性是一组业务规则(未连接必拒/急停必冻结/报警必锁轴)——一条规则一个测试,名字即验收标准;只调公共 API,实现重构行为在就全绿。
  • 🎤:"测试按行为组织:规则被破坏时测试名直接告诉你坏了什么;方法级覆盖会在重构后一片假绿——方法全在,行为没人验证。"
  • 详解:MC2

Q36 · 测试等待为什么轮询条件+超时,时间为什么 tickMs 快进?

  • 决策:等的是条件不是时间——条件成立立即返回(快)、超时兜底(永不卡死),堵死 flaky 两个方向;仿真节拍 10ms 快进,时序完整但套件秒级。
  • 🎤:"异步等待轮询条件加超时,不固定 Sleep——快机器不等冤枉时间、慢机器等到条件才走,这是 Jest waitFor 的同款;再加仿真快进,稳和快各由一个设计负责。"
  • 详解:MC2

Q37 · 两轴界面为什么用控件数组+循环,不复制粘贴两份?

  • 决策:轴是同构的——下标即轴号,一份逻辑跑两轴、按钮状态集中算,加轴=数组加一项;事件里 IndexOf(sender) 反查轴号,控件→数据映射只在一处。
  • 🎤:"两轴界面控件数组加循环:WinForms 没有组件化,控件数组就是那个年代的 v-for;复制粘贴版加第三轴要改 40 处控件名,漏一处就是真 bug。"
  • 详解:MC3

Q38 · UI 冒烟为什么要自动化(STA 线程+手动泵+异常回传)?

  • 决策:MC2 测卡的行为,窗体接线恰恰没人测——90 行测试换"每次提交自动把操作员全流程真点一遍";UI 线程异常必须显式回传测试线程,否则测试看不见异常照样假绿。
  • 🎤:"窗体做了冒烟自动化:STA 线程跑真窗体、DoEvents 驱动消息泵、全流程断言零异常——测的是接线不是逻辑;关键是异常回传,不然 UI 线程崩了测试还是绿的。"
  • 详解:MC4

Q39 · 两轴插补为什么做成卡的指令,不界面循环发单轴小步?

  • 决策:插补要求两轴严格同步——UI 消息泵一卡顿轨迹就歪;卡内一个循环同拍推进,同步由结构保证。对齐真卡:插补在硬件做(G01),上位机只发一条指令。
  • 🎤:"插补下推到卡:同步要求放在有时钟权威的一方——卡内一个循环两轴同拍推进;界面软件插补每拍都有微小错拍,画出来的直线全是锯齿。"
  • 详解:MC5

Q40 · 轨迹图为什么自绘 Panel,不用 Chart 控件?

  • 决策:要的是机床俯视坐标系——Y 向上、毫米等比(圆是圆)、十字定位线,这些是领域语义不是图表语义;4000 点 DrawLines 一帧+双缓冲,比图表库少背动画开销。类似前端:数据可视化用 ECharts,游戏小地图一定自己拿 canvas 画。
  • 🎤:"轨迹图自绘:机床坐标系的 Y 翻转就是一个减号、等比缩放一条公式,领域语义握在手里;Chart 库要先说服它反转 Y 轴,再加一个效果都要和库搏斗。"
  • 详解:MC6
