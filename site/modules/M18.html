M18 — 配方管理（工艺参数版本化）

优先级定位：🟡 加分项 · 配方管理（13-15K JD 偶尔点名，注塑机/包装线/食品配方场景刚需） 技术来源：🟦 System.Text.Json（参数 JSON 列）+ 🟧 Microsoft.EntityFrameworkCore.Sqlite（EF Core，沿用 M4）+ 🟧 ClosedXML（Excel 导入导出，沿用 M10） 给简历加的能力：让上位机支持「切换产品配方」——一键把工艺参数（温度设定 / 压力阈值 / 时间序列）从一组切换到另一组，并带版本化 + 审计。这是真实工厂里最常见的一个「软需求」，能讲出来就比只做采集的同行多一项能打的牌。 前置：M4（EF Core / DbContext / 迁移）、M9（DI / 单测 / 工程分层）、M10（ClosedXML 导出）。

⏱️ 阅读路径(按时间预算选入口) - 3 分钟:看「模块目标」— 知道配方 = 一组工艺参数的命名版本 - 30 分钟:加看 Day 1 配方 CRUD + JSON 序列化 - 3 小时:全文精读 + Day 2 版本化 + 回滚事务(写入+回读+失败回滚) + Day 3 Excel 导入导出 - 🎯 面试高频:JSON 列 vs 关联表权衡 / 配方切换事务思想 / 版本 diff 实现 / 审计谁改了啥 - 🔁 配套复习:代码肌肉 B23 Recipe 配方管理 · 间隔重复表

📚 前置语法(M18 用到的,陌生请查 C# 语法速查 — 前端视角) - class Recipe { public int Id { get; set; } public string Name { get; set; } = ""; public List<RecipeParameter> Parameters { get; set; } = new(); } — class + 默认值 - string json = JsonSerializer.Serialize(recipe) — System.Text.Json 序列化 - var recipe = JsonSerializer.Deserialize<Recipe>(json) ?? throw new JsonException() — 反序列化 + null 检查,速查 §5 - using var tx = await db.Database.BeginTransactionAsync(ct) — EF Core 事务,速查 §13/§8 - await tx.CommitAsync(ct) / await tx.RollbackAsync(ct) — 提交/回滚 - public record RecipeParameter(string Key, double Value, string Unit) — 不可变参数项,速查 §12

模块目标

配方 = 一组工艺参数（温度设定 / 压力阈值 / 时间序列）的命名版本。本模块让上位机：① 编辑 / 保存配方；② 切换产品时一键下发到设备；③ 版本化（可回滚到任意历史版本）；④ 审计（谁什么时候改了啥、激活了哪个版本）。学完你能讲清：「JSON 列 vs 关联表」的权衡、配方切换的「写入 + 回读 + 失败回滚」事务思想、版本 diff 的实现——这三点是「做过配方系统」和「只听过这个词」的分界线。

Day 1 — 配方数据模型 + 增删改查

一句话讲清楚

配方 = 命名的参数集合 + 版本号 + 创建时间 + 创建人，前端类比：Git 的 tag + package.json 的 version——同一个 Name（项目名）下可以有多个 Version（tag），任何时候只有一个「当前生效」（main / HEAD）。

前端类比秒懂（每个概念都对上）

配方管理概念 前端类比 说明
配方 Recipe package.json / docker-compose.yml 一份命名 + 版本化的参数集合
版本号 v1.2.3（SemVer） SemVer 大.中.小，可字符串比较
当前生效配方 IsActive=true Active branch（main / HEAD） 同名下只允许一个生效
切换配方（ActivateAsync） git checkout <tag> 切换前要落库审计
配方历史列表 git log --oneline 按创建时间倒序
配方 diff（Day 3） git diff v1..v2 增 / 删 / 改三类变更

分点精讲

① 数据模型 Recipe + RecipeParameter（🟦） 配方主体放关系列（Name/Version/IsActive/CreatedBy/CreatedAt），参数本身放 JSON 列（ParametersJson）。这是一个刻意权衡：参数 schema 经常变（今天加一个新温度点，明天加一个保压时间），用 JSON 列不用改表结构；但用于查询 / 唯一约束的字段仍然在关系列，索引能用。

// DaqMonitor.Core/Recipes/Recipe.cs
public class Recipe
{
    public int Id { get; set; }
    public string Name { get; set; } = "";            // 如 "饮料瓶_500ml"
    public string Version { get; set; } = "1.0.0";    // SemVer 字符串
    public bool IsActive { get; set; }                // 当前生效（同名仅一个 true）
    public bool IsDeleted { get; set; }               // 软删除标记（防误删历史）
    public string CreatedBy { get; set; } = "";       // 创建人（工号 / 用户名）
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    public string ParametersJson { get; set; } = "{}"; // 灵活参数（JSON 列）
}

// 配方里的一个参数（仅作为 JSON 反序列化的 DTO，不建表）
public class RecipeParameter
{
    public string Key { get; set; } = "";        // "temperature_setpoint"
    public double Value { get; set; }            // 85.5
    public string Unit { get; set; } = "";       // "℃"
    public string? Description { get; set; }     // 可选注释
}

逐行白话： - Name + Version：配方的「身份证」。同名下不同版本，像 docker-compose.yml 的 v1 / v2。 - IsActive：同 Name 下只允许一个 true（Day 1 末尾的坑点）。前端类比 React Router 的「当前激活路由」——同时只能有一个。 - IsDeleted：软删除——不真删行，只标记。理由：配方是工艺历史，删了就回滚不了（Day 3 的 diff / 回滚都靠历史还在）。 - ParametersJson：参数列表序列化成 JSON 字符串存进去。SQLite 自带 JSON 函数（json_extract），需要按参数查也能查（见坑点表）。

② EF Core 配置：唯一约束 + 索引（🟧，关联 M4）

// DaqMonitor.Core/Persistence/AppDb.cs（在 M4 已有的 AppDb 上加）
public class AppDb : DbContext
{
    public DbSet<Recipe> Recipes => Set<Recipe>();
    public DbSet<AuditEntry> AuditLog => Set<AuditEntry>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        // 唯一约束:Name + Version 不能重复(且只针对未软删的)
        b.Entity<Recipe>()
            .HasIndex(r => new { r.Name, r.Version })
            .IsUnique()
            .HasFilter("[IsDeleted] = 0");   // SQLite 的 partial index,软删的版本可重建

        b.Entity<Recipe>().Property(r => r.ParametersJson).IsRequired();
        b.Entity<AuditEntry>().HasIndex(a => a.At);
    }
}

逐行白话： - HasIndex(...).IsUnique()：让数据库帮我们拦「同一 Name 下重复 Version」。前端类比：唯一邮箱约束，重复注册直接拒。 - .HasFilter("[IsDeleted] = 0")：partial index——软删的版本不算重复，可以重建同版本号（小写 SQLite 语法，迁移到 SQL Server 要改 WHERE 大小写）。

③ CRUD + 激活服务 RecipeService（🟦+🟧）

// DaqMonitor.Core/Recipes/RecipeService.cs
public class RecipeService
{
    private readonly IDbContextFactory<AppDb> _factory;     // M4 / M9 的 DI 注入
    private readonly IAuditLogger _audit;

    public RecipeService(IDbContextFactory<AppDb> factory, IAuditLogger audit)
    { _factory = factory; _audit = audit; }

    public async Task<Recipe> CreateAsync(string name, string version,
                                          RecipeParameter[] parameters, string user)
    {
        await using var db = _factory.CreateDbContext();   // M4:短生命周期,用完即弃
        var recipe = new Recipe
        {
            Name = name,
            Version = version,
            CreatedBy = user,
            ParametersJson = JsonSerializer.Serialize(parameters),
        };
        db.Recipes.Add(recipe);
        await db.SaveChangesAsync();                       // 唯一约束会在这里拦重复
        await _audit.LogAsync(user, "CreateRecipe", $"{name}@{version}", null, null);
        return recipe;
    }

    public async Task ActivateAsync(int recipeId, string user)
    {
        await using var db = _factory.CreateDbContext();
        var target = await db.Recipes.FindAsync(recipeId)
                     ?? throw new InvalidOperationException("配方不存在");

        // 同名配方只允许一个 IsActive:true
        var siblings = db.Recipes.Where(r => r.Name == target.Name && !r.IsDeleted);
        foreach (var s in siblings) s.IsActive = (s.Id == recipeId);

        await _audit.LogAsync(user, "ActivateRecipe", $"{target.Name}@{target.Version}", null, null);
        await db.SaveChangesAsync();
    }

    // 软删除(保留历史,不真删行)
    public async Task DeleteAsync(int recipeId, string user)
    {
        await using var db = _factory.CreateDbContext();
        var r = await db.Recipes.FindAsync(recipeId)
                ?? throw new InvalidOperationException("配方不存在");
        if (r.IsActive) throw new InvalidOperationException("不能删除当前生效配方,先切换到其他版本");
        r.IsDeleted = true;
        await _audit.LogAsync(user, "DeleteRecipe", $"{r.Name}@{r.Version}", null, null);
        await db.SaveChangesAsync();
    }

    public async Task<Recipe?> GetActiveAsync(string name)
    {
        await using var db = _factory.CreateDbContext();
        return await db.Recipes
            .Where(r => r.Name == name && r.IsActive && !r.IsDeleted)
            .FirstOrDefaultAsync();
    }
}

逐行白话： - CreateAsync：唯一约束兜底，重复的 Name+Version 直接抛异常，不用自己加锁。 - ActivateAsync：先把同名所有配方的 IsActive 算出来「只有目标是 true」，再一次性 SaveChanges——EF Core 在一个事务里把所有兄弟置 false、目标置 true，避免「先 A 置 false 再 B 置 true」之间被人读到「没有任何生效」的中间态。 - DeleteAsync：禁止删当前生效配方——否则设备就找不到下个版本可切，必须先切到别的再删。这条规则面试讲出来直接证明你做过。

④ 审计入口 IAuditLogger + AuditEntry（🟦） 审计是「谁什么时候改了啥」的黑匣子。定义成接口便于 Mock 测试（关联 M9 的 DI 思想）：

// DaqMonitor.Core/Audit/AuditEntry.cs
public class AuditEntry
{
    public int Id { get; set; }
    public string User { get; set; } = "";
    public string Action { get; set; } = "";     // "ActivateRecipe"
    public string Target { get; set; } = "";     // "饮料瓶_500ml@1.2.0"
    public string? Detail { get; set; }          // 可选 JSON(改了哪些字段)
    public DateTime At { get; set; } = DateTime.UtcNow;
}

public interface IAuditLogger
{
    Task LogAsync(string user, string action, string target, string? before, string? after);
}

为什么审计独立成服务：① 单测能 Mock（M9 思想）；② 以后想接 Serilog（M6）或上报 MES（M7）只换实现，不动业务代码。

⚠️ 重点 & 易踩坑

项 说明
⭐ JSON 列查询性能 按参数过滤（WHERE json_extract(ParametersJson,'$.temp')>80）走不了普通索引，高频查要建 生成列 + 索引 或把热字段提到关系列
⭐ 并发激活（同名 IsActive 唯一） 用 EF Core 事务把「兄弟置 false + 目标置 true」一次性提交，避免中间态被人读到「没有任何生效」
⭐ 软删除而不是硬删 配方是工艺历史，硬删就回滚不了；partial index 让软删的版本号可重建
🔥 禁止删除生效配方 删了设备找不到下个版本，必须先切到别的再删——这条规则是面试加分点
🔥 参数验证放 Service 层 temperature_setpoint 超过物理上限（如 > 500℃）应在 CreateAsync 拦下，不是写库后才报错
🔥 审计追溯 创建 / 激活 / 删除 / 应用全部走 IAuditLogger，无审计的配方系统过不了 GMP / ISO 审计
🔥 权限控制 编辑 / 激活 / 删除必须分角色（操作员只能切，工艺工程师才能改），见 Day 3 末尾

🧪 今日三档练习

  • 🟢 基础题：建 Recipe + AppDb（含 Recipes DbSet），用 RecipeService.CreateAsync 写一份「饮料瓶_500ml@1.0.0」配方（含 temperature_setpoint=185℃、pressure_setpoint=120bar），并 GetActiveAsync("饮料瓶_500ml") 验证 null（因为还没激活）。 ✅ 答案：调用 CreateAsync("饮料瓶_500ml","1.0.0", new[]{ new RecipeParameter{Key="temperature_setpoint",Value=185,Unit="℃"} }, "u1") 后查 GetActiveAsync 返回 null（IsActive 默认 false）。再调 ActivateAsync(id,"u1") 后 GetActiveAsync 返回该对象。
  • 🟡 进阶题：同一 Name 下插两个相同 Version，验证第二次抛 DbUpdateException（唯一约束生效）；并写一个 xUnit 测试用 Moq 替身 IAuditLogger，验证激活时 LogAsync 被调用一次、action == "ActivateRecipe"。
  • 🔴 挑战题：给 RecipeService 加一个 ValidateParameters 私有方法，按一份硬编码的「参数白名单 + 范围表」（如 temperature_setpoint ∈ [0, 500]）校验，超出范围抛 ArgumentException；写测试覆盖「正常 / 超上限 / 未知 key」三种用例。

💡 工控导师说

我在某注塑厂做过一个项目：操作员误删了正在用的配方，机器停了 4 小时找不回参数，损失几万块。从那以后我们做了两条铁律：① 配方只软删不硬删；② 当前生效配方不允许删除（先切换才能删）。这两条是面试时讲「配方管理」最有说服力的故事。 另一条：JSON 列很灵活，但别滥用。如果某个参数（如 temperature_setpoint）几乎所有报表都要按它过滤，提到关系列建索引；JSON 列只放「偶尔回读、几乎不查」的参数。

🎓 职业建议

13-15K 的 JD 里，配方管理偶尔出现，但一旦出现你做过就是差异化。面试时能讲出：「我用 EF Core 的 partial index 做了软删 + 唯一约束」「激活用事务保证同名只有一个生效」「审计走独立接口便于 Mock 测试」——这三条直接证明你做过生产级配方系统，不是「写个 CRUD 就完事」。

Day 2 — 配方下发到设备 + 实时切换

一句话讲清楚

配方切换 = 把 JSON 参数按「地址映射表」转成一组 PlcDevice.Write(addr, value)，前端类比：切换主题（切换前先卸载旧主题，逐项加载新参数，加载失败回滚到旧主题）。

前端类比秒懂

配方切换 前端类比
地址映射表 _addressMap i18n 资源文件的「key → 文本」映射
暂停采集 → 写入 → 恢复 loading=true → fetch → loading=false
回读校验 写完 input 再 expect(getValue()).toBe(setValue)
失败回滚 切主题失败,回滚到原主题的 <link href>
RecipeApplyException 自定义 Error 子类,带上下文（哪步炸的）

分点精讲

① 地址映射表：参数 key → PLC 地址（🟦） 配方里存的是「逻辑参数名」（temperature_setpoint），但 PLC 只认「DB 块地址」（DB1.DBD100）。映射表是两者的桥梁——和前端的 i18n 字典一样，集中在一处维护，不散在代码里。

// DaqMonitor.Core/Recipes/RecipeApplier.cs
public class RecipeApplier
{
    private readonly PlcDevice _plc;             // M3 的 PLC 设备抽象
    private readonly RecipeService _recipes;
    private readonly IAuditLogger _audit;

    // 地址映射:参数 key → PLC DB 偏移(DB1 内的偏移,DWORD=4 字节)
    private readonly Dictionary<string, int> _addressMap = new()
    {
        ["temperature_setpoint"] = 100,   // DB1.DBD100
        ["pressure_setpoint"]    = 104,   // DB1.DBD104
        ["cycle_time"]           = 108,   // DB1.DBD108
        ["holding_time"]         = 112,   // DB1.DBD112
    };

    public RecipeApplier(PlcDevice plc, RecipeService recipes, IAuditLogger audit)
    { _plc = plc; _recipes = recipes; _audit = audit; }
}

逐行白话： - _addressMap：硬编码在工程里，也可以从配置文件读（appsettings.json 的 RecipeMaps 节）。前端类比：从硬编码常量改成 i18n 资源文件加载。 - PlcDevice 是 M3 讲过的 PLC 抽象（S7 / Modbus 都包成一个 PlcDevice），这里假设它有 Read(addr) / Write(addr, value)。

② 切换流程：暂停 → 写入 → 回读校验 → 恢复（含失败回滚）（🟦）

    public async Task ApplyAsync(int recipeId, string user, CancellationToken ct)
    {
        // 1. 取配方 + 解析参数
        var recipe = await _recipes.GetAsync(recipeId)
                     ?? throw new InvalidOperationException("配方不存在");
        var parameters = JsonSerializer.Deserialize<RecipeParameter[]>(recipe.ParametersJson)
                         ?? throw new InvalidOperationException("配方参数无效");

        // 2. 切换前快照旧值(用于失败回滚)
        var snapshot = new Dictionary<string, double>();
        foreach (var p in parameters)
        {
            if (!_addressMap.TryGetValue(p.Key, out var addr))
                throw new InvalidOperationException($"参数 {p.Key} 没有地址映射,无法下发");
            snapshot[p.Key] = _plc.Read(addr);
        }

        // 3. 暂停采集(避免写入过程被读出"中间态"值)
        _plc.SuspendAcquisition();
        try
        {
            // 4. 逐项写入 + 回读校验
            foreach (var p in parameters)
            {
                ct.ThrowIfCancellationRequested();          // 用户取消立刻停
                int addr = _addressMap[p.Key];
                _plc.Write(addr, p.Value);

                // 回读校验:写入 50.0,读出来应在 49.9-50.1 之间(1% 容差)
                double readBack = _plc.Read(addr);
                double tolerance = Math.Max(Math.Abs(p.Value) * 0.01, 0.1);
                if (Math.Abs(readBack - p.Value) > tolerance)
                    throw new InvalidOperationException(
                        $"写入 {p.Key}={p.Value},回读 {readBack},超出 1% 容差,校验失败");
            }

            // 5. 全部成功:激活 + 审计
            await _recipes.ActivateAsync(recipeId, user);
            await _audit.LogAsync(user, "ApplyRecipe",
                $"{recipe.Name}@{recipe.Version}", null, recipe.ParametersJson);
        }
        catch (Exception ex)
        {
            // 6. 失败回滚:把所有参数写回旧值
            foreach (var kv in snapshot)
                _plc.Write(_addressMap[kv.Key], kv.Value);
            await _audit.LogAsync(user, "ApplyRecipeFailed",
                $"{recipe.Name}@{recipe.Version}", null, ex.Message);
            throw new RecipeApplyException($"配方 {recipe.Name}@{recipe.Version} 应用失败,已回滚", ex);
        }
        finally
        {
            _plc.ResumeAcquisition();   // 无论成败都恢复采集
        }
    }

// 自定义异常,带上下文(对应前端的 class AppError extends Error)
public class RecipeApplyException : Exception
{
    public RecipeApplyException(string msg, Exception inner) : base(msg, inner) { }
}

逐行白话： - 快照 snapshot：切换前先把 PLC 当前值读出来备份。万一中途失败，按快照逐项写回，回到切换前的状态而不是「半个新配方 + 半个旧配方」。这是工厂最怕的「配方写到一半炸了」的兜底。 - SuspendAcquisition / ResumeAcquisition：写入期间暂停后台轮询（M2 / M3 讲过的 PollLoop），避免 UI 读到「温度已切到 200 但压力还是旧值」的中间态。 - 回读校验：写完立刻读回来比，差超过 1% 就抛异常。理由：PLC 通信可能丢包 / 写入失败但没报错（M3 讲过的「写完不回读」是现场最隐蔽的坑），必须显式校验。 - finally 恢复采集：无论成功失败，最后都要 ResumeAcquisition。finally 块保证即使异常抛出也不漏。前端类比：try { fetch() } finally { setLoading(false) }。 - CancellationToken：用户在切换中途按「取消」能立即停下，不卡 UI。关联 M0 Day7 / M9 讲的优雅退出。

⚠️ 重点 & 易踩坑

项 说明
⭐ 快照 + 回滚 切换前读旧值备份,失败时按快照写回。没有回滚的配方切换是定时炸弹
⭐ 回读校验 写完立刻读回来比,1% 容差内才算成功。PLC 写入可能「不报错但没写进去」
⭐ 暂停 / 恢复采集 写入期间停后台轮询,避免 UI 读到中间态
🔥 写入中途异常 必须 try/catch/finally,finally 里恢复采集,否则线程泄漏 + 采集永远停
🔥 大配方写入慢 几十个参数逐项写 + 回读可能要几秒,UI 要给进度条 / 可取消(CancellationToken)
🔥 并发切换 同一设备不能两个操作员同时切配方,ApplyAsync 入口加 SemaphoreSlim(1,1) 串行化
🔥 设备掉线 写入前先检查 _plc.IsConnected,掉线直接抛 RecipeApplyException,别等到回读失败

② Excel / JSON 导入 + schema 校验（🟦+🟧）

// DaqMonitor.Core/Recipes/RecipeImporter.cs
public class RecipeImporter
{
    private readonly RecipeService _service;

    // 参数白名单 + 范围(真实项目从 appsettings.json 读)
    private readonly Dictionary<string, (double Min, double Max)> _ranges = new()
    {
        ["temperature_setpoint"] = (0, 500),
        ["pressure_setpoint"]    = (0, 300),
        ["cycle_time"]           = (0, 600),
        ["holding_time"]         = (0, 3600),
    };

    public RecipeImporter(RecipeService service) => _service = service;

    public async Task<Recipe> ImportFromJsonAsync(string json, string name,
                                                  string version, string user)
    {
        // 1. schema 校验:能不能反序列化
        var parameters = JsonSerializer.Deserialize<RecipeParameter[]>(json)
                         ?? throw new ArgumentException("JSON 不符合 RecipeParameter[] 格式");

        // 2. 业务校验:key 白名单 + value 范围
        foreach (var p in parameters)
        {
            if (!_ranges.TryGetValue(p.Key, out var range))
                throw new ArgumentException($"未知参数 key:{p.Key}");
            if (p.Value < range.Min || p.Value > range.Max)
                throw new ArgumentException(
                    $"参数 {p.Key}={p.Value} 超出允许范围 [{range.Min}, {range.Max}]");
        }

        // 3. 校验通过,交给 Service 入库
        return await _service.CreateAsync(name, version, parameters, user);
    }
}

逐行白话： - 两层校验：① schema 校验（JSON 能不能解析成 RecipeParameter[]）；② 业务校验（key 在白名单、值在范围内）。前端类比：先 zod.parse() 验类型，再 if (value > MAX) 验业务。 - 校验失败抛 ArgumentException，调用方决定 UI 怎么提示（红字 / 弹窗）。永远不要把不合法的配方写库——回去重新改。

③ 版本 diff：两个配方的 key-value 对比（🟦）

// DaqMonitor.Core/Recipes/RecipeDiff.cs
public record RecipeDiff(
    IReadOnlyList<string> Added,                                      // b 有,a 没有
    IReadOnlyList<string> Removed,                                    // a 有,b 没有
    IReadOnlyDictionary<string, (double Old, double New)> Changed);   // 都有但值变

public class RecipeDiffer
{
    public RecipeDiff Compare(Recipe a, Recipe b)
    {
        var pa = JsonSerializer.Deserialize<Dictionary<string, double>>(a.ParametersJson)
                 ?? new Dictionary<string, double>();
        var pb = JsonSerializer.Deserialize<Dictionary<string, double>>(b.ParametersJson)
                 ?? new Dictionary<string, double>();

        return new RecipeDiff(
            Added:   pb.Keys.Except(pa.Keys).ToList(),
            Removed: pa.Keys.Except(pb.Keys).ToList(),
            Changed: pa.Keys.Intersect(pb.Keys)
                .Where(k => Math.Abs(pa[k] - pb[k]) > 0.001)         // 浮点比较用容差
                .ToDictionary(k => k, k => (pa[k], pb[k]))
        );
    }

    // 人可读的 diff 文本(像 git diff)
    public string FormatDiff(Recipe a, Recipe b, RecipeDiff diff)
    {
        var sb = new StringBuilder();
        sb.AppendLine($"diff {a.Name}@{a.Version} → {b.Name}@{b.Version}");
        foreach (var k in diff.Added)   sb.AppendLine($"+ {k}");                       // 新增
        foreach (var k in diff.Removed) sb.AppendLine($"- {k}");                       // 删除
        foreach (var (k, v) in diff.Changed)
            sb.AppendLine($"~ {k}: {v.Old} → {v.New}");                                // 修改
        return sb.ToString();
    }
}

逐行白话： - Keys.Except / Intersect：LINQ 集合运算，前端类比 JS 的 arr1.filter(x => !arr2.includes(x))。 - 浮点比较用 > 0.001 容差，不用 ==——浮点 0.1 + 0.2 != 0.3 是经典坑（M2 讲过 IEEE754）。 - FormatDiff 输出像 git diff 的格式：+ 新增 / - 删除 / ~ 修改。UI 绑定到文本框直接展示。
