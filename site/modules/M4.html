Day 1 — ORM 概念 + 建模 + 写入 🟡

一句话讲清楚

EF Core 是"对象 ↔ 数据库"的桥梁（ORM）：你写 C# 类，它自动建表、把对象存进去、把行读成对象，不用手搓 SQL。

前端类比秒懂

EF Core 前端后端
DbContext 数据库连接池 / Prisma Client
实体类 SensorRecord 数据模型 schema
SaveChangesAsync() prisma.user.create() 提交
IQueryable / LINQ Prisma query / SQL
Code First 迁移 用代码定义表结构

分点精讲

① 实体 + DbContext（🟧）

public class SensorRecord
{
    public int Id { get; set; }              // 自增主键
    public int PointId { get; set; }
    public double Value { get; set; }
    public DateTime Timestamp { get; set; }  // 与 SensorPoint.Timestamp 对齐
}

public class AppDb : DbContext
{
    public DbSet<SensorRecord> Records => Set<SensorRecord>();
    protected override void OnConfiguring(DbContextOptionsBuilder b)
        => b.UseSqlite("Data Source=daq.db");   // 单文件数据库
}

② 写入（🟧）

// 推荐:通过 IDbContextFactory<AppDb> 注入(见下面 Bootstrapper 注册)
await using var db = _factory.CreateDbContext();   // 短生命周期,用完即释放
db.Records.Add(new SensorRecord { PointId = 1, Value = 25.6, Timestamp = DateTime.Now });
await db.SaveChangesAsync();                          // 提交事务(异步,不堵 UI 线程)

为什么不 new AppDb():DbContext 不是线程安全,多人/多线程共享一个实例会炸(追踪缓存冲突 + 并发 SaveChanges 串行报错)。正确姿势 = DI 注册 AddDbContextFactory,每次用 CreateDbContext() 拿独立短命实例。前端类比:像 React Query 的 queryClient,不能跨组件共享 mutable state。 Bootstrapper 注册:services.AddDbContextFactory<AppDb>(o => o.UseSqlite("Data Source=daq.db"));

🔬 掰开揉碎：DbContext 到底在管什么（变更追踪 Change Tracking）

🎭 拟人秒懂:公司记账员 + 便签纸工厂(DbContext 记忆锚点)

把 DbContext 想象成"公司记账员",把 IDbContextFactory 想象成"便签纸工厂"。

DbContext = 记账员: - 你 db.Records.Add(x) → 记账员在草稿本上记"新增 SensorRecord(状态=Added)" - 你改 r.Value = 99 → 记账员标注"Modified" - 你 db.Records.Remove(y) → 记账员标注"Deleted" - 这时数据库还没动 — 记账员只在自己草稿本上画 - 你调 SaveChangesAsync() → 记账员一次性翻账本,把所有 Added/Modified/Deleted 都提交到银行(数据库) - 为什么要短生命周期:记账员的草稿本会越记越厚(实体引用),用一辈子就装满内存 + 并发改时草稿被多人乱画 → 必须每次任务用完就换人

IDbContextFactory = 便签纸工厂: - services.AddDbContextFactory<AppDb>(...) → 注册一个"便签纸工厂" - 每次 _factory.CreateDbContext() → 撕一张新的便签纸(独立 DbContext 实例) - 用完 await using → 扔掉这张便签纸(Dispose) - 谁用谁借,用完即还 — 天然线程安全,因为没人共享同一张便签

前端类比: - DbContext = React Query 的 queryClient(不能跨组件共享 mutable state) - IDbContextFactory = createQueryClient() 工厂函数,每次调一次拿新实例

为什么不用单例(Singleton): - 单例 DbContext = 一个记账员干全公司的账 → 草稿本爆炸 + 串行 SaveChanges 报错 - Factory 模式 = 公司有便签纸盒子,谁要用谁拿一张 → 完美

很多人 SaveChangesAsync() 调得好好的，但被面试官问「它怎么知道哪些改了」就懵。拆开讲： - DbContext 是个「工作单元 + 缓存」：你 db.Records.Add(x) 或改 r.Value=99，它并不立刻写库，而是把实体记进内部「追踪缓存」并标记状态（Added/Modified/Deleted）。 - SaveChangesAsync() 才一次性比对、生成 SQL、提交事务。这就是为什么你改了属性不调 SaveChangesAsync 数据库没变化。 - 为什么要「短生命周期」：追踪缓存会一直持有实体引用，一个 DbContext 用一辈子 = 缓存无限膨胀 + 并发写冲突。正确：每次操作 new AppDb() 用完 Dispose（using），或 DI 里用 Scoped（一次请求/一次批量任务一个实例）。 - 高频写入策略：每秒几千条别每条 SaveChangesAsync（每次都开事务，慢 10 倍）。攒一批（如每秒 500 条）一次 AddRange+SaveChangesAsync；或用 SQLite 的 WAL 模式（PRAGMA journal_mode=WAL）提升并发读写。

🔬 掰开揉碎：迁移（Migration）是干什么的

  • 问题：你改了 SensorRecord 加个字段，数据库表结构不会自动变。手动改表易错、不可复现。
  • 迁移 = 把「模型变化」记成一份可版本化的脚本，一路 Up/Down： bash dotnet tool install --global dotnet-ef # 装 CLI（一次性） dotnet add package Microsoft.EntityFrameworkCore.Design dotnet ef migrations add Init # 生成第一版迁移（建表） dotnet ef database update # 把迁移应用到数据库 # 以后改模型 → dotnet ef migrations add AddColumnX → update
  • 为什么 15K 必须会：企业项目表结构随需求变，靠迁移才能「代码和库结构同步、可回滚、可部署到客户机自动建库」。本项目为演示用了 Code First 运行时建库，真项目请用迁移。

⚠️ 重点 & 易踩坑

项 说明
⭐ DbContext 用完即弃 用 IDbContextFactory.CreateDbContext() + await using 短生命周期，别做成全局单例后长期不释放
⭐ 异步 API 生产用 SaveChangesAsync / ToListAsync，避免堵 UI 线程
🔥 DbContext 非线程安全 多线程共享实例会炸,用 Factory 每次新建;前端类比 = 不能跨组件共享 mutable state
🔥 小数精度 double 映射到 REAL，金额/精确量用 decimal
🔥 并发写 多设备同时写要串行化或用连接池，避免"数据库锁定"

🟢 基础题

建 SensorRecord 实体 + AppDb，插入 3 条记录并查询打印。

🟡 进阶题

插入 100 条随机温度（1~100℃），用 LINQ 查出平均值 > 50 的条数。

🔴 挑战题

写一个 BulkInsertAsync(IEnumerable<SensorRecord> batch)，用 AddRange + 单次 SaveChangesAsync 批量提交，并测量「单条循环 SaveChangesAsync」vs「攒批一次 SaveChangesAsync」的耗时差距（体会 10 倍性能差）。

✅ 答案（挑战题核心）

// 通过 DI 注入 AppDbContext(Scoped 生命周期,每次请求一个实例)
public class PointRepository
{
    private readonly IDbContextFactory<AppDb> _factory;
    public PointRepository(IDbContextFactory<AppDb> factory) => _factory = factory;

    public async Task BulkInsertAsync(IEnumerable<SensorRecord> batch)
    {
        await using var db = _factory.CreateDbContext();   // 短生命周期,用完即释放
        db.Records.AddRange(batch);                          // 一次加一批
        await db.SaveChangesAsync();                         // 一次事务提交 —— 比每条 SaveChanges 快约 10 倍
    }
}

为什么不用 new、为什么用 IDbContextFactory:DbContext 不是线程安全,多线程共享同一个实例会炸(追踪缓存冲突、SaveChanges 串行)。Factory 模式每次 CreateDbContext() 拿到独立实例,谁用谁借、用完即还。 前端类比:像 React Query 的 queryClient,不能在多组件共享 mutable state —— 一旦并发 fetch 同时写,就出 race。 Bootstrapper 注册(M9 DI 体系): csharp services.AddDbContextFactory<AppDb>(o => o.UseSqlite("Data Source=daq.db"));

🏗️ 项目任务：在 DaqMonitor.Core 加 Persistence/AppDb.cs 与 SensorRecord；建 HistoryRepository 封装"批量写入 + 查询"（参考工程里已有的 Store/PointStore.cs 双索引思路）。DAQ Monitor 的 DataReceived 事件里把点存库。（EF 历史库接进工程为下一轮落地项。）

🎓 工控导师说：现场一个真实事故——某系统每秒 2000 条数据，每条都 SaveChangesAsync()，结果数据库 CPU 跑满、写入积压、界面卡死。改成"每 500ms 攒一批 AddRange 提交"，CPU 直接掉到 5%。工业写入第一原则：攒批，别逐条提交。

💼 职业建议：数据库是 13K 必考。面试被问"EF Core 怎么优化写入"，答"短生命周期 DbContext + 攒批 AddRange + WAL 模式 + 异步 SaveChanges"这四点是满分答案，直接区分"用过"和"懂原理"。

🔬 掰开揉碎：DbContext 三大性能利器

会写 SaveChangesAsync 只是及格,知道下面三招才是 15K 的写法:

① AsNoTracking() — 只读查询关掉变更追踪,性能 2-3 倍

// 查历史曲线(只读,不修改) → 关掉追踪,跳过状态字典维护
var list = await db.Records.AsNoTracking()
    .Where(r => r.PointId == 1 && r.Time > from)
    .ToListAsync();

前端类比:像 React 的 PureComponent / useMemo,跳过不必要的 diff。读几万条历史时不开 AsNoTracking,DbContext 的追踪字典会一直膨胀,GC 压力炸裂。

② 索引策略 — PointId + Timestamp 复合索引,按时间范围查点位 100 倍速

// 用特性声明(EF Core 5+),迁移自动生成 CREATE INDEX
[Index(nameof(SensorRecord.PointId), nameof(SensorRecord.Timestamp))]
public class SensorRecord { ... }

坑:索引顺序很关键 —— (PointId, Time) 适合"按点位 + 时间段查";如果反过来,查"某段时间所有点位"才用得上。索引不是越多越好,写入要维护 B+ 树,索引过多会让攒批变慢。

③ AutoDetectChangesEnabled = false — 大批量 AddRange 前关掉自动 DetectChanges

await using var db = _factory.CreateDbContext();
db.ChangeTracker.AutoDetectChangesEnabled = false;   // 关掉自动 diff
db.Records.AddRange(batch);                            // 几千条 Add 不再每条扫一次
db.ChangeTracker.AutoDetectChangesEnabled = true;    // AddRange 完成后开回来
await db.SaveChangesAsync();

原理:Add/AddRange 默认会触发 DetectChanges,全量比对追踪字典,几千条会慢成 O(n²)。关掉后只在 SaveChanges 时一次性 diff,大批量插入提速明显。

🔬 掰开揉碎：迁移与回滚（生产必备）

讲义上面讲了正向迁移(migrations add → database update),但回滚和种子数据也是 15K 必会:

① 加迁移命令(规范)

# 把迁移文件输出到指定目录,团队协作必备(默认散在根目录难管)
dotnet ef migrations add Init -o Migrations
dotnet ef database update                          # 应用到库

② 回滚到上一个迁移(面试常考,讲义只讲了正向)

# 假设你刚加了 BadMigration,发现问题要撤
dotnet ef database update <上一个迁移名>   # 数据库回到上一个状态
dotnet ef migrations remove                  # 删掉最近一次迁移文件(还没 push 才行)

生产坑:已经 update 到客户机的迁移不能直接 remove,要写一个新的反向迁移(把字段/表删掉)再 update 上去 —— 这才是企业级「前向修复」原则。

③ 种子数据(Seed Data) —— 初始化字典表/默认点位

protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<SensorRecord>().HasData(
        new SensorRecord { Id = 1, PointId = 1, Value = 25.0, Timestamp = new DateTime(2026,1,1) }
        // ... 初始化默认点位/字典表
    );
}
// 迁移会自动生成 INSERT 语句,部署到客户机自动带初始数据

Day 2 — 查询 + 导出 CSV + 仓储模式 🟡

一句话讲清楚

存进去是为了查：按点位 / 时间段捞历史，再导出 CSV 给 Excel 分析 —— 这是"数据价值"闭环。

分点精讲

① LINQ 查询（🟧🟦，呼应 M0 Day 3）

var today = db.Records
    .Where(r => r.PointId == 1 && r.Time > DateTime.Now.AddHours(-1))
    .OrderBy(r => r.Time)
    .ToList();

double avg = db.Records.Where(r => r.PointId == 1).Average(r => r.Value);

② 导出 CSV（🟦）

var sb = new StringBuilder();
sb.AppendLine("PointId,Value,Time");
foreach (var r in today)
    sb.AppendLine($"{r.PointId},{r.Value},{r.Time:yyyy-MM-dd HH:mm:ss}");
File.WriteAllText("export.csv", sb.ToString());

③ 仓储模式（解耦数据访问）（🟦）

public class HistoryRepository
{
    private readonly IDbContextFactory<AppDb> _factory;
    public HistoryRepository(IDbContextFactory<AppDb> factory) => _factory = factory;
    public async Task AddRangeAsync(IEnumerable<SensorRecord> rs)
    {
        await using var db = _factory.CreateDbContext();
        db.Records.AddRange(rs);
        await db.SaveChangesAsync();
    }
    public async Task<List<SensorRecord>> QueryAsync(int pointId, DateTime from, DateTime to)
        => await db.Records.Where(r => r.PointId == pointId && r.Time >= from && r.Time <= to).ToListAsync();
}

⚠️ 重点 & 易踩坑

项 说明
⭐ 仓储模式 UI 不直接碰 DbContext，便于测试和替换数据库
⭐ 批量写 别每条 SaveChanges，攒一批再提交，性能差 10 倍
🔥 时区 存 DateTime 注意 Kind（UTC/Local），导出格式要统一
🔥 库文件被占用 程序运行时别手动删 daq.db，会锁

🟢 基础题

写 HistoryRepository.Query 按点位 + 时间段查询，返回列表。

🟡 进阶题

加 ExportCsv(path) 方法，把查询结果写成 CSV。

🔴 挑战题

写一个 GetHourlyAverage(pointId, date)：用 LINQ GroupBy(r => r.Time.Hour) 算出当天每小时的平均温度（M10 报表的预演）。

✅ 答案（挑战题核心）

var hourly = db.Records
    .Where(r => r.PointId == pointId && r.Time.Date == date)
    .GroupBy(r => r.Time.Hour)
    .Select(g => new { Hour = g.Key, Avg = g.Average(r => r.Value) })
    .OrderBy(x => x.Hour).ToList();

🏗️ 项目任务：HistoryRepository 接入 DAQ Monitor，后台定时（如每 5 秒）把缓冲的点批量入库；UI 加"导出 CSV"按钮。至此"数据持久化"达标，M10 报表直接复用这份历史数据。

🎓 工控导师说：客户最爱说"把昨天下午 2 点到 4 点的温度曲线导出来"。如果你的查询写成"全表捞回内存再 filter"，几十万条数据直接把程序撑爆。正确做法：查询条件下推到数据库（Where 翻译成 SQL），只取需要的字段和时间段——这是 LINQ to Entities 的本职。

💼 职业建议：仓储模式（Repository）是面试常考点，答出"UI 不依赖具体 DbContext、便于单测替换（用 InMemory 库或 Mock）"就到位了——这正对应我们 DaqMonitor.Tests 里用 Moq 测存储的思路。

🎤 M4 整体面试 3 分钟讲法(模块综合)

"EF Core 是 .NET 的 ORM,我用 Code First 模式定义实体类(SensorRecord),通过 DbContext 映射到 SQLite。

核心原则:DbContext 短生命周期 + 线程不安全,生产用 IDbContextFactory<AppDb> 每次创建独立实例,await using 自动 Dispose。绝不做 Singleton。

变更追踪:DbContext 内部有 ChangeTracker,Add/Modify/Remove 只标状态不立刻写库,SaveChangesAsync 才一次性提交事务。只读查询用 AsNoTracking() 关闭追踪,性能提升 2-3 倍。

高频写入优化:每秒几千条不能每条 SaveChanges(每次开事务慢 10 倍)。我的做法是 200ms 攒一批 AddRange 一次 SaveChanges + SQLite WAL 模式,实测 CPU 从 30% 降到 5%。

索引:[Index(PointId, Time)] 复合索引,按点位 + 时间段查 100 倍速。索引顺序很关键 — (PointId, Time) 适合按点位查时间段,反过来适合按时间段查所有点位。

迁移:dotnet ef migrations add Init -o Migrations + database update,代码和库结构可版本化同步。已上线的迁移不能 remove,要写反向迁移再 update。"

面试官可能连环追问: - "DbContext 为什么不能 Singleton?" → ① ChangeTracker 内部字典非线程安全,多线程并发 SaveChanges 会冲突 ② 实体引用一直累积内存泄漏 ③ 连接池串行化导致并发性能下降 - "AsNoTracking 什么场景用?" → 只读查询(报表、历史曲线、列表展示)。不需要修改的场景都该加,跳过追踪字典维护 - "SaveChanges 失败了怎么办?" → 默认全部回滚(事务原子性)。如果想部分成功,要拆成多个 SaveChanges 或手动开 TransactionScope - "EF Core 怎么知道改了哪个字段?" → ChangeTracker 内部存原始值快照,SaveChanges 时比对当前值 vs 快照,生成 UPDATE 语句只改变化的列(乐观锁) - "SQLite 并发怎么样?" → 默认串行写(WAL 模式可改善),读并发数高。生产场景大数据量用 SQL Server / PostgreSQL - "怎么避免 N+1 查询?" → .Include(r => r.Related) 预加载关联,或 Select 投影只取需要的字段

🧩 完整代码组装（HistoryRepository 可直接抄进工程）

// DaqMonitor.Core/Persistence/AppDb.cs
public class SensorRecord
{
    public int Id { get; set; }
    public int PointId { get; set; }
    public double Value { get; set; }
    public DateTime Timestamp { get; set; }   // 与 SensorPoint.Timestamp 对齐
}
public class AppDb : DbContext
{
    public DbSet<SensorRecord> Records => Set<SensorRecord>();
    // 注意:OnConfiguring 仅演示用;生产用 DI 注册 AddDbContextFactory(见 Day1 Bootstrapper)
    protected override void OnConfiguring(DbContextOptionsBuilder b)
        => b.UseSqlite("Data Source=daq.db");
}

// Bootstrapper / Program.cs —— DI 注册(Scoped Factory 模式)
services.AddDbContextFactory<AppDb>(o => o.UseSqlite("Data Source=daq.db"));

// DaqMonitor.Core/Persistence/HistoryRepository.cs
public class HistoryRepository
{
    private readonly IDbContextFactory<AppDb> _factory;
    public HistoryRepository(IDbContextFactory<AppDb> factory) => _factory = factory;
    public async Task BulkInsertAsync(IEnumerable<SensorRecord> batch)
    {
        await using var db = _factory.CreateDbContext();
        db.Records.AddRange(batch);
        await db.SaveChangesAsync();
    }
    public async Task<List<SensorRecord>> QueryAsync(int pointId, DateTime from, DateTime to)
        => await db.Records.Where(r => r.PointId == pointId && r.Time >= from && r.Time <= to).ToListAsync();
    public void ExportCsv(string path, List<SensorRecord> rows)
    {
        var sb = new StringBuilder();
        sb.AppendLine("PointId,Value,Time");
        foreach (var r in rows) sb.AppendLine($"{r.PointId},{r.Value},{r.Time:yyyy-MM-dd HH:mm:ss}");
        File.WriteAllText(path, sb.ToString());
    }
}
